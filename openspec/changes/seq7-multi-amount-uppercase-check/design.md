## Context

序号7此前把 A-3 的 `total_amount_*` 当作合同总价，并且只比较一笔金额。新旧字段重叠时，同一处含税报价会被重复消费，其中旧字段被错误命名成“合同总价”。此外，模型可能从比例推导金额，或因 Markdown 的自然折行而漏掉本应相邻的数字与大写。

本设计不为任何合同写特判：先保留可审计的原文事实和证据，再由服务端做确定性裁决。两阶段架构不在本 change 改动；MVP 的付款阶段大写结果继续显示在旧序号7。

## Goals / Non-Goals

**Goals:**

- 校验每个有原文证据的适用金额事实，覆盖报价、合同整体金额和付款阶段金额。
- 区分“合同是否明确总金额”与“某一价格条款的大小写是否一致”。
- 允许证据片段内的正常空白或单次自然换行，不把物理行、表格分隔符或固定金额标签当作语义规则。
- 对所有适用金额对象统一给出单侧 `WARN`、完整不一致 `FAIL`、完整一致 `PASS`。
- 以统一、可版本化的人民币中文大写格式化器生成期望值，并保留实际原文。

**Non-Goals:**

- 不从总价和比例计算付款金额，不从数字生成中文大写，不从中文大写反推数字。
- 不在无明确整体金额证据时，把含税报价、阶段合计或其他金额猜成合同总金额。
- 不改旧序号10的数字匹配，也不在本 change 修改 Prepare/Evaluate API 或把付款阶段展示迁移到新序号10。
- 上游去除了表格分隔符后，本 change 不重建表格结构；若将来需要严格识别“跨表”，上游必须传递表格/单元格边界元数据。

## Decisions

### 1. 金额事实与合同整体金额分离

`amount_pairs[]` 承载每一处金额事实；每项含 `label`、`amount_numeric`、`amount_uppercase`、`amount_evidence`。`payment_stages[]` 保留阶段名称、比例及可空金额字段和证据。

兼容字段 `total_amount_numeric` / `total_amount_uppercase` / `total_amount_match` 保留，但只有同时具备可定位的 `contract_overall_evidence` 时才能进入正式检查。该证据是能说明“这是本合同整体对价”的原文摘录；可识别“合同总金额”“合同价款”等同义语义，不能用固定标签白名单，也不能由含税、数值或合计关系推断。

同一原文的总金额既在 `amount_pairs[]` 又在兼容字段出现时，以唯一原文位置合并为一个事实；旧字段绝不更改该事实的业务名称为“合同总价”。

### 2. 有界证据配对，而非同一物理行

`sanitize_amount_payment_facts(a3_result, full_text)` 生成安全副本，并验证每个值及其证据可在 `full_text` 定位。证据比较可规范化普通空白、单次自然换行和数字千分位差异；它不是修改金额原文的手段。

金额数字、大写和关联语义只有同时处于同一个**有界证据片段**且候选唯一时才可配对：

- 可接受一段完整句子或条款内的正常折行，例如“金额为 4690000 元\n人民币（大写）肆佰陆拾玖万元整”。
- 遇到空段、标题、编号后的独立条款、已知的表格边界，或片段内存在多个可能数字/大写组合时，拒绝自动配对。
- 上游当前已删除 `|`，服务端不依赖或处理该符号。无表格元数据时，无法证明跨表，只能保守地拒绝跨独立文本块和一切歧义；这是输入结构限制，不得用猜测弥补。

模型仍是事实提取主路径。服务端只在已有 `contract_overall_evidence`、但缺少有效总金额配对时，在该有界片段中进行唯一候选恢复；不扫描全文寻找总金额。

### 3. 序号7的裁决矩阵

先独立检查合同整体金额是否明确，再检查每个已验证的金额事实：

| 事实状态 | 序号7结果 | 原因 |
|---|---|---|
| 无明确的合同整体金额 | `FAIL` | 合同没有明确总金额 |
| 数字与大写均存在且一致 | 不产生该事实的问题 | — |
| 数字与大写均存在但不一致 | `FAIL` | 回显实际大写、期望大写及可识别类别 |
| 仅数字金额 | `WARN` | `{金额名称}没有对应的大写金额` |
| 仅中文大写金额 | `WARN` | `{金额名称}没有对应的数字金额` |
| 仅比例、无金额事实 | 不产生金额大小写结论 | — |

“仅数字/仅大写”适用于所有适用金额对象，包括合同整体金额、报价和付款阶段。它不触发补全或推导。聚合优先级为 `FAIL > WARN > PASS`；保持一个序号7检查项及原有 ID/名称。

### 4. 统一大写规范与错误说明

期望大写由单一的人民币中文大写格式化器产生，以《支付结算办法》附件一的 `元/角/分/整` 书写方式为准。比较时只可忽略首尾空白和可选“人民币”前缀，不自动改写原文。

错误原因是格式化器比较结果的可行动投影，而不是仅靠两个字符的特判：

- `点` 一律说明为“小数书写错误：应使用角/分表示小数，不应使用点”。
- `圆` 暂说明为“金额单位错误：应使用元而非圆”。这是待业务确认的项目规则；实现和文档不得声称该结论直接来自支付结算规范。
- 其他差异至少回显实际大写与期望大写；后续可在不改变主比较规则的前提下增加类别。

### 5. 事实身份与阶段边界

服务端根据数字金额和大写金额在规范化原文中的唯一位置生成仅内部使用的来源键；完整配对使用两侧位置，单侧事实使用其已出现一侧的位置。位置唯一时可合并新旧字段；位置不唯一时保守保留事实，不以标签、金额值、证据字符串包含关系或最终原因文案合并。

Prepare 只输出候选值、证据与关系，不输出 PASS/WARN/FAIL；旧序号7检查层执行本设计的裁决。两阶段 Evaluate 将来可复用事实与格式化器，但本 change 不改变其接口或职责。

## Risks / Mitigations

| 风险 | 缓解 |
|---|---|
| Markdown 自然折行造成漏配对 | 在有界片段内规范化单次自然换行，并补回归 |
| 跨段落或跨表错误拼接 | 拒绝跨独立文本块；有结构元数据时额外校验边界；无元数据时不猜测 |
| 含税报价被伪装成合同总金额 | `contract_overall_evidence` 是兼容总金额字段的前提 |
| 推导金额进入正式检查 | 证据守卫拒绝无法定位的值，不改变阶段比例事实 |
| 业务对“圆”的口径变化 | 隔离为临时项目规则，后续由配置/规则版本替换，不影响格式化主干 |

## Migration Plan

1. 先补失败测试：同一含税报价重复表示、无总金额、同义总金额、全金额对象单侧、自然折行、歧义及推导金额。
2. 扩展 A-3 Prompt/Schema 的事实与证据字段，保持旧字段兼容。
3. 实现证据守卫、唯一来源键和有界候选恢复。
4. 收敛序号7原因、聚合与格式化规则；不改旧序号10和两阶段实现。
5. 完成自动化回归后，由用户执行真实 MVP 端点复测。
