# Design — review-summary-api

> 可选工件。仅记录立项过程中的方案权衡与实现收口决策；产品契约、输入输出字段与规则的完整定义以 `docs/integration/2026-10-02-review-summary-design.md` 为唯一事实源，不在此重复。

## D1 整包输出 vs 只出 AI 部分（已拍板：整包）

- 接口交付物 = 「评审智能总结」面板这个产品，而非裸模型能力；响应含原文装配字段，合同系统可整包渲染，也可对自有组件覆盖的模块忽略对应字段。
- 理由：① AI 总述本就需全量输入上下文，"传进来"省不掉，整包只多回传一步、代价≈0；② 空态矩阵、事实单点归属、source_refs 校验等展示规则归接口侧单一实现；③ 缓存与溯源以整包为单位最简单；④ 避免双数据源时序问题（原文即时、AI 数秒）。

## D2 spec 归挂方式（已拍板：新 capability `review-summary`）

- 本仓此前只有 `contract-review` 一个 capability。归挂进 `contract-review` 会与其"整包冻结"红线自相矛盾，且违反能力间零依赖的架构约定。
- 决策：delta spec 落 `specs/review-summary/spec.md`（全 ADDED），archive 后提升为 `openspec/specs/review-summary/`，本仓正式第二个 capability。

## D3 配置与依赖一期零改动

- 超时、模型参数等一期硬编码默认值，不新增 `config/*.yaml` 键；不新增第三方依赖（hash 用标准库、缓存用进程内实现）；不动 `tests/conftest.py`。
- 缓存为一期进程内内存实现（输入 hash → 响应体），无持久化组件；多副本部署下各自命中，正确性不受影响（输入 hash 即版本键）。

## D4 source_refs 校验失败的兜底（实现收口）

- 设计 §2.3 第 3 条只规定"无引用或引用悬空的结论直接丢弃"。收口：校验失败的 AI 结论（总述句/单条意见摘要）SHALL NOT 出现在响应中；丢弃不阻塞装配区返回。
- 意见摘要被丢弃时该条 `summary` 输出 `null`，前端可回落展示 `comment` 原文截断；总述被丢弃时 `review_summary.text` 输出 `null`。两者 SHALL 在 `degraded_sections` 标记（`review_summary.model` / `opinion_details.model`），与设计既有标记风格一致。
- **本节总述半句已被 D10 取代**（2026-10-08）：总述不再"丢弃即置空"，改为逐条剔除非法引用 + 服务端中性兜底稿；意见摘要的丢弃语义不变。

## D5 服务端超时与耗时预算

- 生成规模小于现行评审接口逐项检查，服务端超时建议 120s 口径；实测预期缓存命中 <100ms、新生成 3–10s。真实端点耗时联调不作为首版验收前置条件（沿用 `DEC-LTC-20261001-001` 的最小完整链路验收精神），登记为上线前补验。

## D6 数字抽验服务端兜底范围（归档前补强，2026-10-03）

- 收口验收观察「铁律 1 此前只有 Prompt 层约束」：服务端对总述与逐条意见摘要做阿拉伯数字 token 抽验（`\d+(?:\.\d+)?%?`），语料初版 = 规范化请求体 JSON 全文（与缓存键同源），**2026-10-07 口径修订见 D9：语料含服务端注入的派生文本**；语料中未逐字出现的数字判该条结论生成失败，走 D4 丢弃/降级路径（`review_summary.model` / `opinion_details.model`）。带 `%` 的 token 整串比对，"15%" 不会被输入里的 "15.5%" 放行。
- 两处已知宽松，判定可接受、不再加码：① 短数字可借长数字子串蒙混（如输入日期 `2026-09-25` 里的 "25"）；② 中文数字（"两期"）与单位换算改写（"120 天"→"4 个月"）不在射程，由 Prompt 第一道防线兜底。理由：主事故形态是编造/抄错金额与比例，均为阿拉伯数字形态，本抽验以零依赖、零误伤正面控制的高性价比覆盖主形态。
- 同批补强：`RouteReason.text` 契约收紧为非空（`min_length=1`），空串属未定义格，422+10001 直接挡在入口，不进入装配与生成。
- 时机决策：补强放在 archive 之前（"归档前补完"）。归档会把 delta spec 提升为正式 spec，若此时写下"服务端强制"而无代码兜底，不实承诺会被固化成长期契约。
- 5.4 实测补充（2026-10-05）：数字抽验本体在真实面板 s05 上零误伤（6 条含数字摘要全部逐字放行）；该面板总述被丢弃的真实原因是 D7 缺陷 A（`action_label` 悬空），非数字抽验。

## D7 真实面板联调抓出的两个缺陷与修法（5.4 第一枪，2026-10-03 晚）

真实样例（合同系统导出 7 合同×106 版本组）组装的 s05_baotou_v3 面板首枪联调（真实 vLLM，13.8s）抓出两个实现缺陷，均为单测 mock 数据形态覆盖不到、真实数据才暴露：

- **缺陷 A：prompt 输入块与引用清单不同步 → 总述误杀**。`_opinions_block` 曾向模型注入展示辅助键 `action_label`（pass→"通过"），但 `_collect_valid_refs` 只登记请求体真实字段。模型逐字引用了输入里见过的 `opinions[i].action_label`，被判悬空、整段总述丢弃——服务端日志实锤 `reason: source_refs 无引用或悬空`。模型行为守规矩，错在实现"给了看却不给引"。修法：输入块不再注入任何清单外派生键（中文语义由结论分布注记承担），spec 铁律 3 补同步条款。
- **缺陷 B：空 comment 意见计入丢弃 → 降级标记误报 + 缓存永久旁路**。批量摘要把 comment 为空的意见也计入 `discarded` 并打 `opinion_details.model`（s05 实锤：discarded=7 恰为 7 条空意见）。后果远超标记本身：`.model` 触发缓存旁路，而真实面板多数评审人只点通过不写字 → 生产上缓存基本形同虚设，每次开面板烧两次模型调用。修法：空意见不进批量输入（不占 token）、回填时跳过且不计丢弃；模型越权给空意见编摘要不写回。spec「AI 生成两处」Requirement 补条款。
- 两修法均锁在 `review_summary` 包内，回归用例 `tests/test_review_summary_realdata_fix.py` 5 例（TDD RED 5/5→GREEN）。D6"归档前补完"的时机判断在此兑现：这两条若拖进正式 spec 就是长期错误契约。

## D8 契约转向：随两缺陷修复一并落地的契约转向（用户拍板，2026-10-05）

- **废除 `action` 英文枚举与一切翻译/映射层**：`Opinion.action`/`OpinionDetail.action` 改为非空字符串，传过来是啥就是啥、响应原样回显；`_ACTION_LABELS` 翻译表删除；结论分布注记按传入原值计数（"通过 10 条、有条件通过 3 条"）。
- **铁律 5 扳机词仅「不通过」逐字一词**：词表外动作词（"驳回""退回"等）不触发中性化闸，fail-open（兜底闸宁可漏放不错杀）；口径登记于接口调用文档 §3.4——合同系统新增负面类用词须告知 AI 侧增补词表（一行常量 + 一个用例），闸不会自己学会新词。
- 教训：枚举+翻译层是与真实数据源（合同系统导出即中文结论）背离的自伤复杂度，且正是翻译辅助键 `action_label` 注入 prompt 才酿成缺陷 A 的"给了看却不给引"。

## D9 数字核对语料口径：注入 Prompt 的派生文本也是原文（5.4 联调缺陷 C，2026-10-07）

- **现象**：s06_wuhu_v1（11 条意见，通过 9 + 有条件 2）真实联调总述被丢弃，日志 `reason: 总述数字未在输入原文逐字出现：["13960000", "1.77%", "11", "9", "2"]`。逐项回查：`13960000`/`1.77%`/`9`/`2` 均逐字命中请求体，唯 `11` 不在——它是服务端 `_distribution_note` 注入的"共 11 条意见"，模型照抄自己看到的输入，被判编造。
- **根因与缺陷 A 同族**：注入给模型看的派生内容未被承认为"输入原文"。缺陷 A 是引用清单没登记注入键，本条是数字语料没登记注入文本。铁律 1 要防的是模型无中生有，不是模型抄写服务端给的事实。
- **侥幸性证据（口径必须改，不能靠运气）**：同批样例的条数是否恰好落在语料里完全随机——s05 的 13、s08 的 14/11、s09 的 10 都能蹭到 `submitted_at` 日期串（如 `2024-12-13`）里的子串而存活，s06 的 11 蹭不到就整段被杀。s05 首枪出总述属侥幸，不是抽验正确。
- **拍板口径（用户选项 1）**：语料 = 规范化请求体 JSON + 实际注入 Prompt 的派生文本。除「结论分布」注记外无其他派生数字来源（其余输入块都是请求体字段的原样序列化），故扩展面精确到此，不放宽成"什么都算原文"。
- **不放宽反面**：注记里没有的数字仍照抓。新增回归锁：同一无数字请求下，含 `888` 的总述仍判违规并弃用 AI 稿（D10 之后由兜底稿顶替，该数字不会出现在响应里）；s06 真实请求体回放中 `1.4`/`1.8%` 这类换算改写仍列为缺失 token。
- **顺带修正可观测性**：丢弃日志原先输出"文本中的全部数字 token"，联调时看不出到底哪个违规（本次即需回查 5 个 token 才定位到 `11`）。改为只输出语料中找不到的 token，新增 `_unverifiable_numbers()` 作为判定与诊断的单一来源。
- 落点：`_input_number_corpus` 单函数改动 + 上述 3 个用例（`tests/test_review_summary_number_guard.py`，TDD RED 2/9→GREEN）；spec 铁律 1 与两个 Scenario 同步语料口径。

## D10 总述永不空白：引用逐条剔除 + 服务端中性兜底稿（用户拍板，2026-10-08）

- **动机（用户原话）**："本功能最重要的就是总述，如果它总被丢弃而不显示，那这个功能的问题就太大了，不能接受。" 5.4 联调三次实测里 s06 因数字抽验被杀、s05 首枪因 `action_label` 悬空被杀，均为整段总述 `text=null`：面板最核心的字段缺席，而调用方无从分辨"没有总结"和"总结被安全闸拦了"。旧口径把三条护栏（引用、数字、正面定性）统一实现为"整段弃用 + 置空"，代价由用户端承担。
- **A：source_refs 由"一条悬空丢整段"改为逐条剔除**。`_prune_refs()` 只剔清单外的路径（顺序去重），剩余 ≥1 条合法引用即采信 AI 文本。理由：悬空往往只是模型引用了输入里见过的派生键（缺陷 A 的形态），文本本身合规；整段弃用等于用一个指针瑕疵否定整句内容。铁律 3 的溯源强度不降——面板展示的每条引用仍逐字指向真实输入路径。
- **B：AI 稿被弃用时输出服务端中性兜底稿**。`_fallback_pieces()` 只允许两类素材：请求体字段原文（合同类型/总额/毛利率、风险项 title）与服务端确定性统计（意见条数与结论分布），拼装为"该合同为 X 合同，合同总额 …；本次评审共 N 条意见（通过 …）；重点关注 …"。新标记 `review_summary.fallback` = 内容在、但不是 AI 写的（与 `.model` = 内容缺失，语义二分）。
- **兜底稿必须自证清白**：素材全部来自语料与引用清单，因此它天然通过铁律 1/3/5（`test_fallback_template_passes_its_own_guards` 锁死这一点）——把"防幻觉"换成"造幻觉"是不可接受的。兜底稿不含任何评价性修饰，`不通过` 场景天然中性。
- **缓存不对称延伸**：`.fallback` 与 `.model` 同样不落缓存（`_is_cacheable()`）。理由与 D4 后既有的"模型随机性坏结果不得钉死"一致：兜底稿是这一发的模型没说好，下一发应当重试，否则同输入永远停留在兜底稿。输入决定的空态（含"无源可写所以 `text=null`"）照旧可缓存。
- **保留的最后一层**：请求除装配区已展示字段外无可引用素材（如只有 `route_reason`）时兜底稿拼不出来，仍回 `text=null` + `review_summary.model`。这是"确实无内容可写"，不是"被闸拦掉"，与空态语义一致。
- 落点：全部在 `review_summary` 包内（`_prune_refs`/`_degrade_summary`/`_fallback_*`/`_is_cacheable` + `_collect_valid_refs` 增聚合路径 `opinions`）；新增 `tests/test_review_summary_fallback.py`（15 例，含 s05/s07/s09 真实形态回放），并把 service/number_guard/cache_wiring 中 20 条"丢弃置空"旧断言翻为新契约；spec 铁律 3、三个 Scenario、空态矩阵标记语义、缓存条款同步；`prompts/review_summary.yaml` 第一道防线措辞改为"违规即弃用、由服务端中性稿顶上"。

## D11 总述粒度中档化：必须点出附条件与否决意见的诉求（用户拍板，2026-10-08）

- **用户诉求**："感觉总述过于简单，不通过和有条件通过的情况，需要把对应的评审内容做个简单总结。" 旧口径把总述框成"一句话 / ≤120 字 / 只做话题级引用"，模型即使读到了"必须补充仲裁地""软件产品不得分包外采"这类具体诉求也没地方写——审批人第一眼看不到卡点，面板价值折损。
- **拍板粒度（三选一取中档）**：一到两句、**≤160 字**，从「有条件通过」/「不通过」意见的 `comment` 里挑最关键诉求 **最多 3 条**、**逐条点名评审节点**、用词沿用原文、数字照抄；`comment` 为空的意见不参与点名；全部为「通过」时**不硬凑**分歧。高档（≤240 字逐条罗列）与意见摘要区重复度过高且丢弃率上升，轻档（仍 ≤120 字只提一条）解决不了"笼统"，均否。
- **与铁律 2 的关系必须讲清**：铁律 2 约束的是"风险事实"（数字、标准条款、潜在影响）的单点归属，观点类内容本就在豁免范围内；本次把豁免写成明文（spec 铁律 2 + 新 Scenario），否则新要求与旧条款自相矛盾，模型会被两道规则互相拉扯而稳定走兜底稿。
- **兜底稿同步但不越位**：`_fallback_pieces` 新增"其中 X、Y 节点提出了书面意见"一片（确定性事实 = `comment` 非空 + `node_name` 原样），引用指向 `opinions[i].node_name`。**不做诉求概括**——"哪条意见算负面"要靠 action 词表判断，而词表正是 D8 废掉的东西；兜底稿更不许替模型总结主张，那会把防幻觉换成造幻觉。点名**不写个数**（写"等节点"而不写"5 个节点"），否则会引入语料外数字、砸掉 D10 的自证守卫。
- 落点：`prompts/review_summary.yaml`（任务描述 + 写法 + 字数 + 输出格式措辞）、`service._fallback_pieces`；spec 输入契约外的「AI 生成两处」Requirement 与铁律 2 改写 + 2 个新 Scenario、2026-10-02 设计文档 §2.4（连旧示例那句"各评审节点整体认可该单价值"一并换成合规示例）与 §5.3、调用文档 §1/§5.2/§6。用例 3 条（prompt 含"必须点出"/"不超过 160 字"/"不硬凑" + 兜底稿点名与截断），TDD RED 3→GREEN。

## D12 总述三段式：各方关注点按主题归并（用户拍板方案一，2026-10-08）

- **用户诉求升级**："能不能做到综合所有评审意见出一个总结？" D11 只解决了一半——它让总述点名「有条件通过/不通过」的诉求，却把投「通过」但 `comment` 里有实质内容的意见（s05 的财经复核"增补金额由 50 万改为 48 万、利润率由 2.24% 提升至 5.05%"）继续关在总述门外。**真正的缺口不是篇幅，是纳入范围**；顺带发现逐节点点名不如按主题聚合好读（13 条意见里 6 条有字，按节点写会变成流水账）。
- **拍板过程**：给出四档——① 三段式主题归并（≤200 字，仍 2 次调用、响应结构不变）② 总述 + `concern_themes[]` 主题块（响应契约新增字段，需合同系统前端配合）③ 两段式生成（先归并校验、再据清单写总述，可与逐条摘要合并成一次调用故仍 2 发，但要重写"AI 生成仅限两处"这条 Requirement）④ 三次调用版两段式。用户选 ①。②③ 未否，是"下一次带真实数据再评估"的候选。
- **上限量的理由（为什么不直接 ③）**：两段式买到的是"总述基于已校验的中间产物写作"，但 5.4 三枪没有任何实测证据表明一发式归纳会疲——s05 七条引用逐字合法、6 条含数字摘要零误伤、s07 的铁律 5 是模型自己遵守的。为一个没观测到的失败模式重开核心 Requirement + 重跑全部联调，不如先落最便宜的改动再拿数据决定。
- **三段结构与归并范围**：① 合同要素原样融入；② 结论分布**照抄服务端注记**（数字天然在语料内，等于把最容易误伤的数字段变成零风险段）；③ 各方关注点按主题归并，≤4 个主题、每主题一句、点名 ≤2 个节点（超出用"等"），**凡 `comment` 有实质内容即纳入，不看 action 值**——又一次不建 action 词表（D8 的纪律），判断标准从"哪个动作算负面"换成"这句话有没有内容"，后者由服务端与模型都能一致执行。空 `comment` 与"同意/无异议"类无实质话术不进归并。
- **主题名的溯源边界（已知宽松，照实登记）**：主题名（"金额与利润变更""开票与分包"）是模型的概括词，**不逐字溯源、服务端不校验**——铁律 4 的形容词闸只管评价性修饰，管不到概括词；铁律 1 的数字闸仍覆盖主题句里的数字。prompt 用两条硬话收紧风险：主题名只作概括词、诉求一律沿用 `comment` 原文说法、**不替评审人补理由、不引申**。这是把"归纳不可溯源"从隐性缺陷换成显性宽松，与 D6 的中文数字/单位换算豁免同一登记口径。
- **铁律 5 的澄清（防自我矛盾）**：旧写法"存在「不通过」时总述 SHALL 退化为中性陈述（只列事实 + 客观描述类措辞）"会被模型读成"少写为妙"，正好把 ③ 段的诉求复述砍掉、退回 D11 前的笼统态。新口径明文：**"中性"只禁正面评价，不禁复述否决与附条件的诉求**，③ 段照常写，只把评价性用词换成 `comment` 原文的事实说法。
- **成本**：仍两次模型调用、响应结构零变化；总述输出 token 与生成耗时上升（≤120 → ≤200 字），面板耗时预计从真 vLLM 的 10.3s 小幅上浮，D5 的 120s 客户端预算余量充足；`.fallback` 触发概率理论上随文本变长而上升，但 A+B 已保证总述不空白，且 ② 段数字改为照抄注记反而消掉一类自数条数的误伤。
- 落点：`prompts/review_summary.yaml`（三段结构 + 写法 + ≤200 字 + 铁律 5 澄清 + 文件头注释）、spec「AI 生成两处」Requirement 与两个 Scenario + 铁律 2/5 措辞、两份 integration 文档（2026-10-02 §2.4 与示例、调用文档 §1/§5.2）；用例改 1 条（`test_summary_prompt_requires_theme_synthesis`：断"必须点出/按主题归并/不超过 200 字/不硬凑/写了实质内容/观点不受此限"，并断 160 与 120 两档旧上限已消失）。

## D13 总述超长不整段弃用：prompt 反罗列 + 服务端整句裁尾（用户口径，2026-10-08）

- **触发事实（s06 真实面板）**：三段式与 ② 段照抄注记都如期生效（11/9/2 条数零误伤、四道闸全绿、12 条引用全部合法），但 ③ 段没有"归并"，退化成了逐条罗列——全文实测 **406 字**，是 200 字目标的两倍，且把每条 `comment` 的细项用顿号串进总述（"开具13%发票、外采开13%、服务开6%、分包提供6%……"），与「各节点意见详情」几乎整段重复。长度只写在 prompt 里，模型无视了。
- **用户拍板口径**："先不限制字数了，但也不能像现在这样罗列。我担心限制字数又被弃用了，那仅有的 AI 能力就没有了。" 即：**质量问题是罗列，不是长度本身；而"因为超长就把 AI 稿清零"是 D10 明令禁止的那类误杀**。
- **两层修法**：① prompt 端把反罗列写成硬禁令（一个主题只写一句、句内 ≤2 节点、每节点 ≤1 条诉求、禁止顿号串细项、装不下就减主题不减成罗列），并把"红线 300 字、超长按整句砍尾部"告知模型，让它自己安排信息优先级；② 服务端 `service._trim_to_sentences` 以 300 字为**红线**按整句从尾部丢弃，`_SUMMARY_TARGET_CHARS = 200` 只作 prompt 目标、不做校验。
- **为什么裁尾而不是别的**：①② 段天然在前，裁尾必保住合同要素与结论分布；失控的罗列必然堆在后面，砍掉的正好是信息量最低的部分。句子边界切割不留半句，避免"读到一半断掉"的观感。
- **已知代价（照实登记）**：尾部主题可能被整句砍掉，理论上存在"被砍的那句正是唯一复述「不通过」诉求的句子"的极端情形。接受这一风险的理由是：被砍内容在 `opinion_details[].summary` 里仍逐条原文可查，面板整体不丢信息；反过来若因超长退回中性兜底稿，**总述这一栏**的信息量才是真丢了。若真实数据反复出现"关键主题被砍"，再升级为按主题挑选保留（未采纳的候选）。
- **标记与缓存**：裁尾不改变文本来源，因此 SHALL NOT 打 `.model`/`.fallback`，响应照常落缓存；只在日志记 `raw_chars`/`kept_chars`。切不开（首句即超红线，或裁后不足两句）才走 D10 兜底稿。
- 落点：`service._split_sentences`/`_trim_to_sentences`/`_SUMMARY_HARD_LIMIT`、`prompts/review_summary.yaml`（③ 反罗列禁令 + 写法长度条 + 文件头注释）、spec「AI 生成两处」Requirement 与 `超长总述按整句裁尾而不是整段弃用` Scenario、两份 integration 文档（2026-10-02 §2.4/结构树、调用文档 §1/§5.2/§6）；用例 4 条（裁尾保住①段且可缓存 / 只砍尾部整句 / 单句失控走兜底 / prompt 含反罗列禁令），并把 D12 的 prompt 用例断言从"不超过 200 字"改为"目标 200 字以内 + 超长不会弃用整段"。

## D14 缺陷 D：模型按契约返回的 `summary: null` 被误判丢弃（s06 复现，2026-10-08）

- **触发事实**：s06 的 11 条意见里 7 条 `comment` 为空、1 条只写"同意。"。`opinion` prompt 第 89 行明确要求"某条 comment 无实质内容时该条 summary 输出 null、source_refs 输出 []"，模型照办；服务端旧逻辑却把"comment 非空 + summary 非有效字符串"一律计入 `discarded` → 打 `opinion_details.model` → 连带 `_is_cacheable=False`。
- **为什么这是缓存问题而不是显示问题**：真实面板多数评审人只写"同意。"，这条路径几乎每次请求都触发 → 缓存永久旁路 → 每次开面板白烧两次模型调用。缺陷 B（空 comment 计丢弃）修的是"服务端自己算错"，缺陷 D 修的是"**服务端惩罚模型遵守契约**"，同一族、方向相反。
- **判据怎么定才不算"模型自报扳机"**：护栏扳机（数字抽验、引用校验、铁律 5）仍全部服务端确定性计算，本条只改**标记语义**——显式 `null` 视为契约内的合法声明、`summary` 有内容时照样逐条过数字与引用闸；只有模型**漏交该 index**（违背"逐条对应、不得增删"这条硬契约）才算真丢弃。既不建"同意/无异议"词表，也不设字数阈值魔法数（D8 的纪律）。
- 落点：`service._apply_opinion_summaries`（跳过显式 null + 日志改记 `expected`）、spec「AI 生成两处」Requirement 与 `近空意见的显式 null 摘要不计丢弃` Scenario、调用文档 §6 的 `opinion_details.model` 行含义；用例 3 条（显式 null 不打标记可缓存 / 全员"同意。"零 `.model` / 漏 index 才打标记且旁路缓存）。

## D15 缺陷 E：总述把诉求转给了没写字的人（张冠李戴），检测→定向重试→只删错名（用户拍板，2026-10-08）

- **触发事实**：s06 第二发的总述写「财经复核与部门经理指出硬件部分亏损」，而 `财经复核`(index 4) 名下唯一意见的 `comment` 是**空的**，真正写这句话的是与它只差一个字的 `合同复核`(index 5)。数字不编（都在语料里）、引用不悬空（都在清单里）、长度合规、无正面定性——**现有四道闸一道都拦不住：它编的是归属**。
- **为什么不能只靠 prompt**：D12 已把"点名提出该主题的评审节点"写进 prompt，模型照样错；近形节点名（财经复核 / 合同复核）是采样的天然易错点。这印证了 D13 之后的一条纪律：**prompt-only 约束不能作为唯一防线**，凡是"错了会被审批人当成事实"的输出，服务端必须有确定性判据。
- **判据是确定性的**：`_silent_node_names` 按 `node_name` 聚合请求体，名下所有 `comment` 去空后全为空 → 该名字"没有话可以转述"；总述里逐字出现该名字即违规。扳机不看模型脸色（D8 纪律），也不建任何动作词表。同名多条、其中任一条有字（s06 真实形态里的"部门经理"）**不算违规**——点名这个名在事实层面成立。
- **修法演进（如实记录）**：先给的四种拦法（整段弃用 / 建"实质意见"词表 / 服务端改名 / 从 prompt 删掉点名）被用户全部否掉；再给的 E 方案"检测后按 `source_refs` 反查真名做替换"被用户质疑过度设计——**引用是整段粒度，逐主题配对本质是猜测**，替换会把"归属变窄"换成"归属变假"。最终口径（用户选"重试一次，仍错则删错名"）：检测确定性 → 定向重试一次（话术只说哪里错 + 给现成的写过字节点名清单，不替模型改句子）→ 仍错或重试这一发炸了则 `_strip_silent_names` 只删错名（连带相邻连接词，其余一字不动）。
- **标记与缓存**：删名成功 → 新标记 `review_summary.attribution`（语义 = 内容在、仍是 AI 写的，但服务端剪掉了误点名），与 `.fallback` 同属"内容可用但被服务端动过"，SHALL NOT 落缓存（下一发仍给模型自改机会）；模型重试后自己改对 → 不加标记、可落缓存；删完为空 → 按 AI 稿不可用走 D10 兜底稿。
- **调用成本**：常规仍是 2 次模型调用，误点名时最多加 1 次定向重试（`_check_ai_summary` 复用同一套四道闸，重试稿不会因为"改了名"就绕过数字与引用校验）。
- 落点：`service`（`_silent_node_names`/`_misattributed_names`/`_attribution_note`/`_strip_silent_names`/`_check_ai_summary`/`_generate_summary` 重试分支、`DEGRADED_SUMMARY_ATTRIBUTION`、`_DEGRADED_ORDER`、`_is_cacheable`）、`prompts/review_summary.yaml`（点名逐字取自写过字那条的硬要求 + `{attribution_note}` 块）、spec「AI 生成两处」Requirement 尾部 + 新 Scenario `总述张冠李戴时先定向重试再只删错名` + 标记语义分档 + 缓存调用口径、两份 integration 文档（2026-10-02 §5.3、调用文档 §6 新增 `.attribution` 行）；用例 6 条（误点名重试且模型改对 / 仍错只删名且旁路缓存 / 重试炸了不外抛 / 同名有字不算违规 / 删名不留悬空连接词 / prompt 含逐字点名与定向修正块）。
- **已知代价**：删名后该主题的归属变窄（读者看到"提出预付款比例偏低"但看不到是谁提的），意见详情区仍逐条可查——宁可窄，不可假。定向重试只在真实链路触发过 mock 路径，s06 复跑尚未观测到真实一发（记录在 tasks 8.10）。

## D16 缺陷 F：契约级重构——总述主题结构化（themes），文本归属闸整体拆除（用户拍板，2026-10-09）

- **触发事实（s05）**：真实节点名 `二级行业商务评审`(index 1，有字) 内部含沉默名 `行业商务评审`(index 2，comment 全空)，`_misattributed_names` 的子串匹配在**正确的长名内部命中了空的短名** → 判张冠李戴 → 定向重试（话术还告诉模型"你点名了「行业商务评审」"——服务端自造的假事实）→ 重试稿仍含长名 → 再判违规 → 删名把正确长名剪成残词「二级」。这是结构性死循环：只要数据里存在"沉默名 ⊂ 有字名"（LTC 真实数据常态），这道闸对正确输出永判违规。同时 s06 run1 的**真**张冠李戴（把 `合同复核` 的话安给 `财经复核`）四道闸一道没拦住——闸该抓的没抓、不该抓的抓了。实测过的两个文本级修法均不达标：替换式遮蔽在反向嵌套上漏判（漏判比误判危险，联调里无人发现），最大匹配扫描两种形态都对但仍是"在文本里猜谁被点名"。
- **病根与判据**：归属是**语义属性**，归属闸却站在**文本空间**用字符串匹配验证它。文本空间里"名字出现"既非"被点名"的充分条件（s05）也非必要条件（换写法即绕过），**误判与漏判在数学上不可兼得**——这是三次演进（弃稿→只删不替→遮蔽/最大匹配）始终按下葫芦浮起瓢的原因。判据：凡是"错了会被审批人当成事实"的输出，验证必须站在存在确定性的表示层；文本层没有，结构层有。决定性证据：模型自己给的 `source_refs` 粒度比总述文本细（s05 逐主题给了 6 对 `opinions[i].node_name`+`.comment`）——它有逐主题配对能力，只是契约没要求交出来；而 `_collect_valid_refs` 本就是逐下标路径粒度，结构化校验的地基现成。
- **拍板（用户 2026-10-09）**：契约级方案二改造版。模型从"写作文"变"填表"——只产主题句 + 指针；**节点名一律由服务端从指针派生渲染**，归属结构性不可能错。整套文本归属机器（`_silent_node_names`/`_misattributed_names`/`_attribution_note`/`_strip_silent_names`/定向重试文本版/`.attribution` 标记）删除。
- **新模型输出契约（summary 调用）**：
  ```json
  {"overall": "可选，一句整体判断 ≤40 字，禁止出现任何节点名",
   "themes": [{"text": "主题句（诉求转述）", "opinion_refs": ["opinions[3]", "opinions[5]"]}]}
  ```
  - `themes` 1–4 条、每条 `opinion_refs` 1–3 个、**只能是指向有字意见的 `opinions[i]` 整下标路径**；`text` 禁止出现**任何**节点名（点名由服务端渲染，禁令覆盖全部名字而非只沉默名——检测因此不再需要区分沉默与否，子串歧义随之消失）。
  - **①②段（合同要素、结论分布）从模型写作改为服务端装配**（两段本就确定性：① 与 D10 兜底稿要素句同源、② 即注入 prompt 的分布注记）。模型只写真正需要判断力的 ③ 段主题句与 overall——"AI 生成两处"Requirement 的落点随之变为：总述主题句 + 意见摘要。
- **服务端渲染**：`review_summary.text` = ①要素句。②分布句。overall（若有）。theme1（名A、名B）；theme2（名C）……——names 从各 theme 的 `opinion_refs` 反查 `opinions[i].node_name` 去重保序；`review_summary.source_refs` = 服务端汇总（要素引用 + 全部 theme refs 去重）；**新增响应字段 `review_summary.themes[] = {text, opinion_refs}`**（审计/前端可用可不用，`text` 仍是整段字符串——**前端零改动**）。兜底稿与无实质意见场景 `themes=[]`（缺值给空不省键）。
- **闸集合重构**：
  - 删：上述四函数 + `.attribution` 标记 + 文本级重试机器。
  - 新增三个**结构级**校验：**G1** refs ⊆ 引用清单（逐 theme，既有机制）；**G2** refs 不得指向 `comment` 为空的意见（张冠李戴在结构层的等价物——精确、无子串、无近形名、同名多条天然消解，因 index 唯一）；**G3** theme/overall 文本不得含任何节点名（最大匹配扫描 `_find_node_name_mentions`——任意名字即违规，无需沉默判定，乙方案保证不留半截名）。
  - 保留：数字闸（逐 theme + overall，D9 语料口径不变）、reject 正面定性（overall + themes）、D13 的 300 字红线整句裁尾（作用于拼接后全文）。
  - **新增完整性校验 G4**：凡有字意见未被任何 theme 引用 → 不完整——D12 遗留的"漏纳随机性"（s06 漏 `部门经理`）从此可判定。
- **违约处置阶梯（宁可窄不可假的继承）**：① 结构违规（refs 悬空/指空/句含名）或漏纳 → **定向重试 ×1**，话术全部是可核验事实（"主题 2 的 refs 指向空意见 opinions[2]""漏了 opinions[5]"——与 D15 的假事实风险本质不同）；② 重试后逐 theme 复检，违规 theme **丢弃**（不再删名改句）；③ 丢弃过 theme 或仍有漏纳 → 新标记 `review_summary.incomplete`（内容在、AI 写、覆盖不全），不落缓存；④ 0 合法 theme 且有实质输入 → D10 兜底稿；⑤ 无有字意见 → ①② only + `themes=[]`，输入决定空态照常缓存；⑥ overall 单独违规 → 只丢 overall、记日志、不打标记不触发重试。
- **标记与缓存**：`.incomplete` 加入不落缓存集合（与 `.model`/`.fallback` 同一理由：下一发应给模型补全机会）；`.attribution` 从 `_DEGRADED_ORDER` 移除（能力未部署、合同系统未按真实响应对接，无兼容负担）。

## D16.3 s06 真机"摘录器"形态的 prompt 措辞微调（纯措辞，不加闸、不改契约，2026-10-09）

> 触发事实：D16 上线后 s05/s06 真机重放**四道结构闸零误杀、拼接形状逐字自证**（tasks 9.10），但 s06 的总述读起来仍是罗列而非总结。用户提问"你觉不觉得还是在罗列"，判定为**是**，并定位到机制层——不是模型偶然失手，是当前契约形状下的最省力合法解。

- **三点改动（全部落在 `prompts/review_summary.yaml` 的 summary `system`；服务端代码 / schemas / 处置阶梯零改动）**：**① 概括优先**——新增硬要求"每个主题句必须是**你自己概括的一句话**，不是被引意见原文的搬运；逐字或近似逐字照搬 `comment` 原句视为不合格"，配一组正反例（正例"开票口径与四流一致性要按税务评审要求执行"，负例取 s06 主题 4 的搬运形态），并写明分寸：诉求的方向与限定忠于原文、数字税率比例照抄不换算（铁律 1 照旧）、拿不准怎么概括宁可把主题写窄也不许回到搬运。**② 单意见单主题**——同一条意见的多个编号诉求**合并为同一个主题的一句概括**、`opinion_refs` 都指向该条，**不得把同一条意见拆成多个主题**；只有跨意见的同类诉求才合并进同一主题，那才是"归并"的本意（顺带治掉同源拆条导致的节点名后缀重复与意见内细项随机取舍）。**③ overall 归并范式点名**——在 overall 说明处补"以'意见聚焦X、Y、Z'这种**跨意见归并句**为范式，它就是主题归并的浓缩版；不要写成结论分布的复述（②段已由服务端装配）"。
- **一处必须同步的措辞返工（不改即自相矛盾）**：`【写法】` 原句"主题下的诉求**一律沿用 `comment` 原文的说法**"与改动一正面冲突——它正是把模型推向照抄的那句话。改为"允许压缩、允许改写措辞，但不升级、不引申、不替评审人补理由——概括只能把原文说过的话收拢，不能把原文没说的话加上"，把"忠于原文"从**字面**层次挪到**语义**层次；铁律 1（数字照抄）与铁律 4（评价性修饰须溯源）不受影响。此返工与 D11 的教训同族：新加"要求模型做 X"的硬话时，必须同时把与它相邻的旧禁令改写清楚，否则两条规则互相拉扯，模型稳定退回保守形态（当时是走兜底稿，本次是回到搬运）。
- **刻意不做（防过度设计）**：不加"每主题必须 ≥2 refs"这类硬话或硬闸——s06 只有 5 条有字意见（含一条"同意。"），要求跨节点归并可能是**结构上不可满足的承诺**，模型凑不出就去改写、撞数字闸、丢主题、打 `.incomplete`，最终为"像总结"付代价的是总述缺一角（顶撞 D10"总述 SHALL NOT 空白"与"服务端不得惩罚模型遵守契约"两条纪律）。同理，`overlap_ratio` 本轮**不升为扳机**：真机已证低重叠率出现在正当压缩上（s06 主题 3 把 177 字意见收成 33 字，0.438）。
- **观测项（下一轮真机对账，判据现成、不需要新日志字段）**：复跑 s05/s06 后看三列即可判定措辞是否生效——`overlap_ratios` 是否显著低于 1.0（纯搬运 ≈1.0 为当前基线）、是否出现 `refs ≥2` 的主题、`opinion_refs` 是否不再出现同源重复下标。若真机出现"主题被大量丢弃 + `.incomplete` 高发"，判定为改写撞闸，回滚本次措辞而非加闸。

## D16.4 代答抽验（prompt 禁令 + 服务端确定性兜底，2026-10-09）

> 触发事实：D16.3 措辞微调复跑后 s05 全绿（概括形态达成，overlap 从 1.0 降到 0.15–0.909），但 `overall` 写成"意见聚焦管辖地与开票口径，**其余节点无异议**。"——而那 7 个节点只是 `comment` 为空。空意见只能证明"没写字"，证明不了"无异议"：这是**替缺席者断言立场**，且讽刺地正是铁律 5 列出的禁用语之一。用户拍板处置方式 = "prompt 禁令 + 代答抽验"。

- **为什么四道闸一条都不拦**：无节点名（G3 无对象）、无数字（铁律 1 无 token）、refs 合法且指有字意见（G1/G2 通过）、这一单没有「不通过」所以铁律 5 的禁档压根没开。四条里没有任何一条问"**这句话有没有评审人说过**"。
- **拍板的机制层结论**：这已是 prompt-only 约束第四次被真实数据绕过（D13 字数 / D15 点名 / D16.3 ≤40 字预算 / 本次代答禁令），而它的错误形态恰好是**审批人会当成事实读**的那种（把沉默记成同意）。凡"输出错了会被当事实"的类别，必须服务端有确定性判据——与铁律 1 数字抽验同构，不是新增第三种范式。
- **实现（`service.py` 一个纯函数 + 两处挂点，零新标记、零新契约字段）**：`_unsupported_positive_phrases(text, request)` = `_positive_phrases_in(text)` 里那些**不出现在任何一条 `comment` 拼接体**中的短语；挂进 `_check_theme`（数字抽验之后、reject 档之前）与 `_check_overall`。复用铁律 5 那份禁用语表，**不新增输入侧词表**，只是把触发条件从"存在 reject 才管"收紧为"没人说过就管"，两道档互不替换（reject 档仍不管出处、只要有「不通过」就禁；代答档不管分布、只要无出处就禁）。
- **判据比数字抽验更窄（实施中的自行取舍）**：数字抽验语料 = 全量输入 JSON（合同里出现的数字当然合法）；代答抽验只认 `comment`。理由：代答错的是"**哪位评审人表过态**"，风险项描述里恰好写了"无异议"不构成一句整体总结的出处。此收窄由 `test_provenance_is_comments_only_not_the_whole_payload` 锁定。代价：若评审人在**合同条款**而非意见里表态，转述会被丢——9 个真实样本实测无任何正面定性短语出现在语料中，此路目前不触发。
- **处置档位（全部沿用既有两档，不给代答开特例）**：主题 = **内容违规**，整条丢弃、**不消耗定向重试**、计入 `discarded`（因此真丢过主题仍照打 `.incomplete`）；`overall` = 只丢这一句、不打标记、不影响落缓存（D16.2-R7 同档）。理由：代答是"多加了原文没有的立场"，改一句话术救不回来，重试只多花钱；而 overall 本身可空。
- **两处既有口径必须同步（否则自相矛盾）**：`test_positive_tone_without_reject_is_kept` 与 `test_reject_trigger_word_is_exact_only` 的用例主题句"各评审节点整体认可该单价值"原本靠"没有 reject 所以放行"，现在会被代答档丢掉——它们锁的是**动作词扳机**，不是代答，故把该短语的逐字出处补进 `opinions[0].comment`（改fixture 而非改断言、不删测试），断言与 docstring 同步写明"本例只测 reject 档开不开"。
- **误伤面评估**：`_POSITIVE_TONE_PHRASES` 全部 18 个短语在 9 个真实样本（s01–s09）的语料里出现次数为 **0** → 抽验在真实数据上是全副武装的，而"评审人亲手写'无异议'"的合法转述路径由 `test_verbatim_quotation_of_a_real_no_objection_is_kept` 保底（服务端不得惩罚模型遵守契约）。真实面板的代答动机强度可量化：s05 空意见 7/13、s06 6/11、s08 10/14、s09 6/10——缺席者过半，"其余节点无异议"这种收尾句几乎必然出现。
- **本轮明确不做（防范围蔓延）**：② 关键性取舍（s05 连续两轮漏掉"预付款 50 万→48 万""综合毛利率 2.24%→5.05%"这两组真数字，却把主题槽花在"请确保原盖章文件作废"这种执行提醒上）——需要"什么算关键"的判据，属 prompt 引导 + 真机观测，下一轮再议；③ "标签：句子"的列表腔与 overall 里的标签重复（约 20 字冗余）——措辞级问题，观测到成规模再治；④ `covered/total` 的分母含"同意。"这类近空表态——口径是"**有字意见数**"，注释写明，不改代码（改成按内容判空需要词表，违反 D8）。
- **回收条件**：真机若观测到代答档高频丢弃**主题**（现只丢过 overall）导致 `.incomplete` 上升，回来把 `_POSITIVE_TONE_PHRASES` 的代答档白名单化（只留"无异议/一致认可"等真正断言立场者），而不是撤闸。

## D16.5 中文数字改写：prompt 硬话 + 只观测日志（2026-10-09，s05 真机第三枪）

> 触发事实：D16.4 复跑后 s05/s06 两发均为 AI 全绿稿，但 s05 主题 3 把原文 `50万 / 48万 / 2.24% / 5.05%` 写成"五十万 / 四十八万 / 百分之二点二四 / 百分之五点零五"。语义逐字对得上，**形态却整条绕开了数字抽验**——`_NUMBER_TOKEN` 只匹配阿拉伯数字，离线回放实测该主题"语料外数字 = []"。

- **为什么这不是观感问题**：① 同一份面板出现两种数字写法——① 合同要素句由服务端按原文装配（"综合毛利率 5.05%"），③ 主题句却写"百分之五点零五"，审批人读起来像两个不同的数；② **中文数字成了绕过数字闸的通道**：模型若把 48 万错写成"六十万"，现有闸一个字节都不会拦，而铁律 1 的全部价值就在于"数字错了会被审批人当成事实"。这正是 D6 当初登记的"中文数字/单位换算不在射程"第一次在真机出现，从理论边界升级为实测形态。
- **拍板**：用户选"prompt 硬话 + 观测日志（推荐）"。理由与既有纪律一致——**先观测后动刀**（G4 漏纳、`overlap_ratio` 都是先观测后动刀的）：升闸需要先定中文数字 token 的口径，而"第三方 / 第六条 / 一致同意"这类非数值用法是现实存在的误伤面，没有真实分布就扳闸，等于拿总述缺一角去换一个还没发生过的错数。
- **实现**：prompt 侧在铁律 1 补"**照抄包含保持写法**：原文写 `50万`/`2.24%` 就照抄，禁止转写成中文数字"，并把本轮真实负例（"五十万""百分之二点二四"）写进禁令；【概括优先】的"概括的分寸"同步加一句"并保持原文的阿拉伯写法"——**新加硬话时必须同时改写相邻的旧措辞**（D11/D16.3 同族教训第三次应验：这次冲突面是"概括允许改写措辞"与"数字必须照抄"的边界）。服务端侧新增 `_CN_NUMBER_TOKEN` + `_log_cn_number_rewrites(request, draft)`，挂在 `_log_coverage` 之后，**只出一行 INFO 观测、不丢主题、不打标记、不旁路缓存**。
- **token 口径（刻意的最小可用形态）**：`百分之[零〇一二三四五六七八九十百千万点]+` 或 `[零〇一二两三四五六七八九十百千万亿]{2,}`——要求"≥2 个连续数词字"或完整的"百分之…"写法，把"第三方/第六条/双方一致同意"排除在外。实测噪声：本轮 s05 主题 3 精确命中 4 个 token，s06 三主题 + overall、服务端 ①② 装配句、法务原文（含"第六条/第七条"）均为 **0 命中**。观测判据与数字抽验同构：token 在全量输入语料里找不到逐字出处才计入——评审人自己写中文数字时逐字转述不算改写。
- **回收条件**：真机观测到"中文数字 token 命中且数值确实错写"的实例，或该观测行长期高频出现（说明改写已成模型稳定形态），再回来把它升为内容违规闸；届时按同一份 token 口径评估误伤分布。

## D16.6 代答变体：集体指代族只观测（2026-10-09，s05 真机第四枪）

> 触发事实：D16.5 复跑后 s05/s06 两发仍是 AI 全绿稿（中文数字改写消失、`discarded=0`、零标记、可缓存），但 s05 的 `overall` 把代答换了说法——"意见聚焦管辖权、开票合规与增补变更，**其余节点无实质异议**。"离线复算实测 `_unsupported_positive_phrases` 对整句返回 **空列表**：D16.4 的代答档是固定禁用语表的**逐字子串**比对，"无异议"三个字被"实质"插开，词表零命中、整句放行。这是代答档的第一个真实漏判，也是 prompt-only 约束**第五次**被真实数据绕过（D13 字数 / D15 点名 / D16.3 ≤40 字预算 / D16.4 代答 / 本次代答变体）。

- **拍板**：用户选**"先观测不扳闸"**——加一行"集体指代（其余/其他 + 节点）但语料无出处"的观测日志，不丢句不扳闸，拿一轮真实分布再定正则口径。与 D16.5 的处置同构，也与 G4 漏纳、`overlap_ratio` 的既有纪律同构。
- **为什么不能顺手把闸放宽**：闸的形态只有两种可选——把变体补进 `_POSITIVE_TONE_PHRASES`（逐词打地鼠，"无重大分歧""未提出反对"这类无穷尽）或改用正则族 + 语料无出处（一次覆盖一族）。后者会连带把**对有字意见的正当集体概括**也扫进来：例如"其他部门的诉求集中在付款节奏"完全可能是把三条真意见收拢后的合法说法，而现有判据只能逐字比原文，正当概括必然被判"无出处"。当前这样的反例只有零到一例，**误伤面没有数据支撑**，而代答档丢的是主题整句／overall——拿"总述 SHALL NOT 空白"这条产品红线去换一个尚未量化误伤面的口径，是本 change 明令禁止的交换。
- **实现（`service.py` 一个正则 + 一份白名单 + 一个观测函数，零契约变更、零新标记）**：
  - `_PARROT_COLLECTIVE` = `(?:其余|其他|其它|剩余)` + ≤4 字 + `(?:节点|部门|角色|人员|评审|同事|单位|各方)` + ≤24 字，截到句读为止。刻意只覆盖"集体指代 + 名词"这一族，因为"各方一致认可""整体认可"这类已在 `_POSITIVE_TONE_PHRASES` 里由 D16.4 的闸管着——两档分工，不互相替换。
  - `_SILENCE_FACT_WORDS`（未填写／未提交／未发表／未写／未留／空白）= prompt 给出的唯一合法句式白名单。它陈述的是**输入事实**（`comment` 为空）而不是立场，放过它是硬性反噪声要求：真实面板过半意见是空的（s05 7/13、s06 6/11），若合法写法也记，观测行每单必刷，等于没有观测。
  - 出处判据与代答档**同源**：片段在全部 `comment` 拼接体里找不到逐字出处才计入——评审人自己这么写过就不算代答。
  - `_log_parrot_suspects(request, draft)` 挂在 `_log_cn_number_rewrites` 之后，观测面与代答档同宽（逐主题 + `overall`，真实漏判就出在 overall），清单为空时整行不打；**不丢主题、不丢句、不打 `.incomplete`/`.fallback`、不旁路缓存**。
- **本轮明确不动的东西**：`_POSITIVE_TONE_PHRASES`（放宽词表=在未知误伤面上扳闸）、`prompts/review_summary.yaml`（用户口径为只观测；已实测"其余节点未填写意见"这一合法句式模型会照写，s06 本轮直接不写代答句，说明禁令在起效，问题只在**变体**的词表覆盖）、以及既有四道结构闸与处置阶梯。
- **已知的诚实代价**：本轮不做任何拦截，所以"其余节点无实质异议"这类变体**仍会原样出稿并落缓存**，审批人读到的仍是替缺席者断言立场的句子。这一点在 `docs/integration/2026-10-02-review-summary-design.md` 的铁律 5 条目下登记为已知宽松面（与 D6 数字口径、D12 主题名概括同级），不装作有闸。
- **回收条件**：下一轮真机看两列——① 观测行里出现的**真实片段集合**（决定词表要不要补、正则族要不要升闸）；② 其中有多少属于"对空 `comment` 节点断言立场"（真违规）vs"对有字意见的正当集体概括"（误伤）。若前者占绝对多数且样本 ≥3 单，把该族升为**内容违规**档（沿用代答档的处置：主题整条丢弃不重试、overall 只丢这一句）；若正当概括大量出现，则永久停留在观测档，改走"prompt 里禁用集体指代收尾句"的第三条路。
- **回收条件进展（2026-10-10 真机第七枪，如实改读）**：真实代答累计**三例**——第二轮"其余节点无异议"（D16.4 当时命中）、第四轮"其余节点**无实质异议**"（词表插字变体，两档全漏）、第七枪 s09 `overall`"…**其余为执行层面提醒**。"（该单 10 条意见 6 条空，替未表态节点断言内容性质；词表零命中，**`_PARROT_COLLECTIVE` 也零命中**）。三例全属"对空 `comment` 断言立场"，**正当集体概括的误伤例至今 0 例**（唯一被白名单放过的是 prompt 给的合法句式"其余节点未填写意见"）。故本条回收条件的**数量门槛已达成**，但结论要反过来读：前几轮报的"代答观测零命中"不是"模型没再犯"，而是**正则形状过窄**——`_PARROT_COLLECTIVE` 要求"其余/其他"后 ≤4 字内出现"节点/部门/角色…"这类集体名词，而 s09 那句把"其余"**当代词直接用**、后接谓语，整条正则无从匹配。漏判的观测器等于没有观测，所以**先放宽观测面是确定要做的**（零风险、不动任何闸）；升闸与否单独定口径，且两档代价不对称已实测：`overall` 档处置只丢这一句（不牵连主题、不打标记、不影响缓存、总述仍有①②+主题），主题档处置是丢整条主题（才真正逼近"总述 SHALL NOT 空白"）——因此可切"overall 升闸 + 主题继续观测"，误伤上限是一句态势语。**本轮实际落地 = 该条前半段（放宽观测面）+ 病根装配，升闸按用户口径暂缓，详见 D18。**
- **顺带登记（同轮真机复算得到，非本决策主体）**：s06 `overall` 写"评审意见聚焦于**毛利率偏低**风险……"，而"毛利率偏低"在请求体里找不到逐字出处（原文只有 `gross_margin` 的数值）。这与铁律 4"评价性修饰须溯源"相关，但**不扳闸**：判它违规会直接与 D16.3 的"概括优先"正面冲突——概括本来就要求把原文说过的话收拢成新的措辞。作为已知宽松面登记，等真机出现"概括出原文没有的事实"再议。

## D17 同源主题的服务端合并（2026-10-09，s06 真机第五枪的容量违约）

> 触发事实：同一份 s06 输入，第五枪交回 **6 条主题**，refs 分布 `[5] [5] [6] [6] [7] [7]`——三条意见各拆两条、**零跨意见归并**（上一轮是 3 条主题且带 `[5]+[9]` 归并）。后果全部可量化：渲染后缀"（合同复核）""（开发评审）""（税务评审）"各出现两次；全文 283 字，距 300 红线只剩 17 字余量；容量被拆条吃满后 `[9]`「实际执行利润率需要努力提升」被挤出局，实质覆盖从 4/4 退到 3/4。

- **为什么这一条不是"先观测"**：`≤4 主题` 与 `单意见单主题` 都只写在 prompt 里，服务端从不数条数、也从不查重复下标（`_verify_summary_payload` 只做逐主题复检）——这是 prompt-only 约束第六次被真机绕过（D13 字数 → D15 点名 → D16.3 ≤40 预算 → D16.4 代答 → D16.6 代答变体 → 本次容量）。但这次和前五次的**性质不同**：它的判据是 `tuple(opinion_refs)` 的整数元组相等比对，**免费、零误伤面**——不像 `overlap_ratio` 会把正当压缩误判成搬运，也不像文字归属那样在子串空间里不可判定（D16 的教训⑤）。而它造成的伤害恰好是用户已经明确否决过的形态（"不能像现在这样罗列"）：同一个节点名后缀在一段里重复出现。
- **拍板**：用户选 **"同源合并，不丢内容"**。被否的另三项：① 尾部整条削到 4（s06 会留下 `[5][5][6][6]`——后缀重复照旧，还把整条税务评审诉求丢掉，削谁最没道理）；② 超容量触发定向重试（最尊重模型，但为凑并可能改写句子→撞数字闸→丢主题→`.incomplete`，正是 D16.3 回避的交换，且调用数 +1）；③ 只观测 + prompt 硬话（与 D16.5/D16.6 同档，但这里没有误伤面需要观测，明知违约再放一枪）。
- **实现（一个纯函数 + 一个观测函数 + 一处挂点，零契约字段变更、零新标记）**：`_merge_same_ref_themes(themes)` 按 `tuple(theme.indexes)` 分组，**完全相同**者拼接成一条，位置取**首次出现**（模型给的顺序就是它的关键性顺序，服务端不重排、不判关键性）；`_log_capacity(raw_count, draft)` 只在**合并后仍 >4 条**时出一行 `review-summary 容量观测`（同源拆条已被静默修好，不该刷屏）。挂点在所有闸与两稿取优**之后**、三条观测日志之前——观测项应当描述真正发出去的那份稿子。
- **三条不变量**：① **一字不删**——只做拼接，模型写的每一句都完整留在 `text` 与幸存 `themes[].text` 里，省掉的只有重复的节点名后缀与句末标点（s06 真机 payload 回放实测 283→265 字）；② **对四道闸封闭**——连接符不产生数字（数字抽验安全）、正面定性短语是连续子串而插入"，"令跨句边界拼不出新短语（代答/reject 档安全）、两条主题 refs 相同 ⇒ 服务端反查的名字集合相同（G3 安全）；③ **合并只作用于已通过复检的主题**——被丢弃的那条不会因为同源被"救"回来（`test_merge_only_applies_to_accepted_themes` 锁定）。
- **连接符用"，"不用"；"（易被误改的一处，理由写进常量注释）**：`_SENTENCE_ENDS` 含"；"，而 D13 的整句裁尾与 `_kept_after_trim` 靠**整段字符串匹配**回推哪几条主题幸存。用"；"拼接会让一条主题内部出现句末边界，尾部裁刀可以落在主题中间——那时稿子里残留的是**没有节点名后缀的半条主题**（归属读不出来），而 `themes[]` 里这条已整体消失（前后端不一致）。用"，"则合并后的主题仍是裁尾的原子单位。
- **合并预算上限（实施中撞出来的自行取舍，不是原方案的一部分）**：`_MERGED_THEME_MAX_CHARS = 100`，拼完超过它则**整组原样留着不合并**。这条上限是被既有测试逼出来的：`test_review_summary_fallback.py` 里两条 D13 裁尾用例的失控稿正是"一条意见拆 7 句"，合并后变成约 200 字、内部无任何句末标点的一句话，裁尾**切不动它**，只能整份退回 `.fallback` 服务端中性稿——即"为了消掉重复后缀，把用户最不能接受的『AI 内容整块没了』亲手制造出来"。两条纪律相撞时按既有红线定序：**降级不丢内容 > 形态收口**。留成多条原句，D13 才能照旧一条一条从尾部削。
  - **可复用教训（第七条）**：新增任何"服务端确定性加工 AI 文本"的步骤，先跑**既有最坏稿用例**再写新功能用例。D13 的裁尾隐含依赖"一条主题 = 一句"这个前提，任何会让主题变长或改变其内部标点结构的操作，都在动这个前提，而该前提没有写在任何测试的名字里。
- **刻意不做**：不动 `prompts/review_summary.yaml`——合并是**安全网**，模型的靶子仍是"单意见单主题、≤4 条"，把契约写软只会让拆条成为常态；不把"≤4 条"升为丢弃闸（合并后仍超量只观测，D10"总述 SHALL NOT 空白"与"不惩罚模型遵守契约"两条纪律优先）；不判关键性、不重排、不改写句子。
- **回收条件**：`review-summary 容量观测` 若持续出现"合并后仍 >4 条"，说明超量来自**不同意见**而非拆条，那时才需要真正的容量取舍判据（按什么削尾是语义判断，目前没有确定性判据，届时应先设计判据再动闸）。

## D18 代答的病根治理：意见的有字条数改由服务端装配进 ② 分布句（用户拍板"观测 + 装配，先不升闸"，2026-10-10；陈述方向同日修订见 D18.1）

> 触发事实三条，缺一不成立：① **s09 的代答句逐字来自 prompt 自己的范例**——【overall 的写法】原句是"（例如『意见集中在付款条款与开票口径两处，**其余为执行层面提醒**』）"，禁令与范例同页打架时模型跟着范例走；② **prompt 从不告诉模型有几个节点没写字**（`_coverage_note` 只列有字意见清单、`_distribution_note` 只给结论分布），而真机三例代答全部出现在"收尾处交代其余人怎么了"的位置——填的正是这个事实真空；③ 观测器自身有洞（见 D16.6 回收条件进展），代词用法零命中，报回来的分布是残缺分母。

- **拍板**：A（放宽观测面）+ E2（把事实交给服务端装配），**B（`overall` 档升闸）暂不做**，等放宽后的下一轮真实分布。用户口径原话："观测 + 装配，先不升闸。"
- **如实记录被否与暂缓的选项**（别当成没考虑过）：D 服务端把那句改写正确——撞红线"不删名、不改句"，且服务端改写 AI 文本本身就是新的造假面；C 两档同升——主题档丢整条 → `.incomplete` → 不落缓存，与缺陷 B 同族代价，而真机主题层代答 0 例；F 新标记 `review_summary.parrot`——删掉一句变体后文本仍通顺，不值前端/文档/契约三方改动；G `overall` 也填表化——它是总述里唯一保留模型判断力的位置（D16.3 概括优先的增量价值就在这），留作"升闸后仍高频出代答"的下一手；H 只登记宽松面不动——审批人会把假立场当事实读。
- **实现（三处改动，零新标记、零契约字段、零错误码、零新依赖、零输入侧词表）**：
  - `_distribution_sentence` 尾部追加"，其中 N 条填写了意见"，N = `len(_written_opinion_indexes(request))`；**全员有字时整句不追加**（既有措辞与既有回放逐字不变）。计数判据与 D16.4 代答档、G2 同源（`comment.strip()` 为空），不看模型脸色。
    - **D18.1 陈述方向同日修订（用户口令："不应该写多少条未填写意见，而应该写到多少条填写了意见"）**：同一处装配，把报**缺席条数**改成报**有字条数**。理由不在防幻觉（两个数都是服务端算的确定事实），而在**给审批人的信息价值**——读 ② 段要判断的是"这份评审有多少实质内容"，正向计数直接给答案；缺席条数由"共 M 条 − N 条"确定可推，**事实真空照样被补掉，代答的素材照样不存在**。判据、闸、标记、契约、缓存一律不变，改的只是这一句措辞与它注入 prompt 的同一份文本。
      - 副作用（如实登记）：数字闸只做逐字比对、不做减法，因此"未填写的那几个"从此**不再是语料里的字**——模型若自己写"其余 3 条未填写意见"，那个 3 会按语料外数字被拦（`test_the_derivable_but_unstated_blank_count_is_still_caught` 钉住这一行为）。prompt 的合法句式"其余节点未填写意见"本来就不带数字，因此不受影响；已同步在代答禁令里写明"别在这句里写条数"。
      - 全员有字时不追加的旧规则保留，但它现在有了第二重含义：s07 真机 4 条意见全有字（其中一条只写"同意。"），②段不追加 → 面板上会出现"②说 4 条、意见详情只有 3 条摘要"的观感。这不是本轮引入的（旧口径同样不追加），且"填写了意见"字面为真，故**不改判据**，登记为可读性观察。
  - `_PARROT_COLLECTIVE` 拆成"集体名词分支（D16.6 原样）| 代词分支"两支；代词分支先否定名词紧邻、再要求 0–2 字内出现立场谓词提示词（`异议|分歧|认可|同意|通过|一致|为|是|无|没|未`），`_parrot_suspects` 相应由 `findall` 改 `finditer`（分支含分组，整段匹配才是片段）。**噪声封顶由提示词承担**："其他付款条款按标准模板执行即可"这类普通名词短语仍不进观测清单——观测项一旦刷屏就没人再看，与 `_SILENCE_FACT_WORDS` 白名单同属"先保证可阅读，再保证可判定"的纪律。
  - `prompts/review_summary.yaml`：删掉范例里的"其余为执行层面提醒"并写明"未写字的节点由服务端在 ② 段按事实计数，你没有任何素材能替他们定性"；代答禁令补一句"这一事实服务端已经写明，既不需要你补，也不许换个说法把它说成立场"。
- **与既有三条纪律的对应关系**：
  - **注入的数字必须已在语料里**（D9/缺陷 C 的直接套用）：`_input_number_corpus` = 请求体 JSON + `_distribution_note`，而注记由 `_distribution_sentence` 起头 → 新数字**自动**进入射程，无需第二处改动。`test_the_silence_count_is_already_in_the_number_corpus` 钉住正向，`test_a_number_the_server_never_states_is_still_caught` 锁死"不因装配而对所有数字开门"。
  - **单一事实口径**（D16.1-I1）：面板 ②、prompt 注记、兜底稿共用同一函数，追加一次即三处同步，不会出现"面板说有 6 条空、模型那边从没被告知"。
  - **服务端不得惩罚模型遵守契约**（缺陷 D 族）：合法句式继续被白名单放过；且 `_log_parrot_suspects` 只扫模型稿（`draft.themes` + `draft.overall`），永远扫不到服务端自己装配的两句——新装配不会自刷观测行。
- **诚实代价（登记，不装作没有）**：
  - ②句 +12～13 字，全文预算整体下移。**离线按五个真实样例实测**（同一份请求体跑 `_distribution_sentence`）：s05 +12（13 条/7 空）、s06 +12（11 条/6 空）、s08 +13（14 条/10 空）、s09 +12（10 条/6 空）、s07 +0（4 条全有字，追加条件不成立）。按第八枪实测全文 139–214 字计，追加后距 300 红线余量 **73–149 字**，裁尾风险实际很低；但历史最长的一发是第五枪 s06 的 **283 字**（拆条失控稿，D17 之后未再出现），若那种形态复发，+12 字会把余量压到约 5 字 → **D13 整句裁尾削掉尾部主题的概率随之上升**。裁尾丢的是最后一条主题（其内容仍在「各节点意见详情」逐条可查、且不打标记不旁路缓存），真机复跑 s06/s08 时仍须专门确认这一段没被削掉。
  - 兜底稿会出现两个"其中"连用（"…其中 5 条填写了意见；其中法务评审节点提出了书面意见"）——一个数条、一个点名，语义不歧义，属形态冗余；`.fallback` 至今只有 mock 证据，本轮不动它。
  - **没有升闸 = 词表外变体仍会原样出稿并落缓存**。本轮消灭的是动机与观测盲区，不是后果；D16.6 的"已知宽松面"继续有效。
