## Context

现有 A-1a 从完整合同 Markdown 中提取 `header.parties`，B-1 对合同正文和每个附件分别调用模型，并直接采用模型生成的自然语言 `reason`。该过程既不能区分首页定义与合同/项目名称，也不能证明告警证据属于当前检查范围。

本变更不增加 B-1 调用次数，继续使用正文和附件逐段检查，以避免扩大模型上下文。

## Goals / Non-Goals

**Goals:**

- 以合同首部明确的甲乙方定义及其明确简称作为 B-1 的唯一称谓基准。
- 仅在结构化观察结果可被当前范围文本验证时生成 B-1 告警。
- 使附件中的每个甲乙方角色均有可核验的主体定义；未定义时返回 `WARN`，已定义时与正文同角色主体比对。
- 保留现有 B-1 分段名称、指标和对外响应字段。

**Non-Goals:**

- 不校验合同外部主体是否真实存在或是否为同一工商主体。
- 不把未保留页码的 Markdown 重建为原始文档页码。
- 不修改 B-4 附件内容一致性或其他检查点。

## Decisions

1. A-1a 在现有 `ContractParty` 中增加 `aliases`，只接收合同首部与甲乙方定义同时出现的明确简称。复用既有 A-1a 调用，不新增首页抽取调用，以控制延迟和 token。
2. B-1 响应使用独立的结构化观察 schema，而非复用自由文本 `reason`。观察包含 `role`、`baseline_appellation`、`found_appellation`、`evidence_quote` 和 `evidence_type`；服务端负责生成最终 `CheckItem`。
3. 服务端只接受角色和基准与首页定义一致、发现称谓及证据片段均存在于当前分段、且证据类型为签约方称谓的观察。合同/项目名称、背景引用和未知类型一律不生成告警；仅在附件中出现且未定义主体的角色引用生成 `WARN`。
4. 采用保守策略：无法验证的模型观察按非告警处理，而不输出推测性告警。
5. B-1 的 `PASS` 统一输出空 `reason`，避免兼容旧自由文本输出路径时产生“范围中：”空前缀；告警的证据片段统一由服务端包装为 `证据“原文”。`。

## Risks / Trade-offs

- [复杂别称漏报] → 仅接受首页明确声明的简称，并覆盖合法简称和真实别称回归测试。
- [模型错误标记证据类型] → 服务端同时校验角色、基准、发现称谓和证据片段均来自当前输入；不信任自由文本 `reason`。
- [完整法人名称单独出现在条款中] → 允许 `party_appellation` 类型报告，但要求证据片段来自当前文本；不因合同或项目标题触发告警。

## Migration Plan

1. 部署前运行合同评审定向测试和全量测试。
2. 保持 `checks` 字段结构不变，不需要调用方迁移。
3. 若出现漏报，可回滚本变更以恢复原有自由文本 B-1 输出路径。
