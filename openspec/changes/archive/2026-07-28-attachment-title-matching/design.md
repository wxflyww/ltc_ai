## Context

当前 A-4 先由模型提取合同正文的附件声明，再由本地代码以完整上传文件名和声明标题的字符相似度进行匹配。文件名前缀、扩展名和任意命名修饰会降低相似度，导致格式差异形成误报；同时，规则无法可靠地区分“最终版”和“补充协议”等语义差异。

系统已经通过 OpenAI 兼容接口调用私有化模型，并为合同评审提示词使用 JSON Schema。变更不得接入外部模型，也不得改变附件数量不足的硬阻断规则。

## Goals / Non-Goals

**Goals:**

- 让纯格式差异的附件名称在不调用模型时直接匹配。
- 让私有化模型只判断无法用确定性规则确认的名称对应关系。
- 对模型映射进行后端引用和一对一校验，避免模型结构性错误影响关联。
- 无法确认时输出提示，而非将附件错误关联或错误通过。

**Non-Goals:**

- 不根据有限白名单识别版本号、日期或任意尾缀。
- 不新增外部模型、模型路由或第三方依赖。
- 不改变附件正文内嵌定位和 B-4 内容检查规则。
- 不把语义匹配结果升级为新的硬阻断条件。

## Decisions

### 决策：先做最小规范化，再调用模型

规范化仅移除路径、文件扩展名、明确的“附件序号”前缀、标题包围符、空白和全半角格式差异。规范化后的标题只有在双方各自唯一时才直接匹配。

这避免维护尾缀白名单，也避免把“技术协议补充协议”仅因包含“技术协议”而自动视为同一文件。只用模糊相似度会继续受命名噪声和短标题影响；只靠模型则让完全确定的格式差异也产生额外调用和波动。

### 决策：模型以批量候选和三态结论完成语义判断

对未匹配候选一次调用私有化模型，输入声明标题和上传文件名的候选标识、序号与文本。模型逐个上传附件返回 `MATCH`、`MISMATCH` 或 `UNCERTAIN`。

模型规则要求：仅在名称表达同一附件时返回 `MATCH`；语义改变文件性质的修饰不得自动忽略；无法根据名称确认时必须返回 `UNCERTAIN`。模型不决定最终检查结果。

### 决策：后端仅接受有效的一对一 MATCH 映射

后端验证模型返回的候选标识均存在，且同一声明附件或上传附件不会被重复关联。只有校验通过的 `MATCH` 映射才更新解析后的附件标题和来源；无效、重复、`MISMATCH` 和 `UNCERTAIN` 都保持未匹配状态并生成提示。

候选标识由后端按列表位置生成，避免缺少或重复业务序号时影响模型回传校验。

## Risks / Trade-offs

- [私有化模型语义判断不稳定] → 使用严格 JSON Schema、三态结论和后端一对一校验；不确定时提示。
- [新增模型调用增加时延] → 仅在确定性匹配后仍存在候选时调用一次批量提示词。
- [模型错误关联] → 禁止模型直接输出检查结果；只接收引用有效且唯一的 `MATCH`。
- [附件文件名敏感] → 调用现有私有化模型，仅提交已有审查链路中的文件名、序号和标题。

## Migration Plan

部署后，规范化完全一致的附件将减少原有标题未匹配提示；存在语义修饰的名称由私有化模型给出关联或不确定结论。回滚时移除新增提示词调用并恢复现有本地匹配路径，不涉及数据迁移。
