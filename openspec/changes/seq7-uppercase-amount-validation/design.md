## Context

当前 MVP 的 A-3 模型步骤同时返回小写金额、中文大写金额和 `total_amount_match`。`check_amount_payment()` 只在金额缺失或模型明确返回 `false` 时让序号7失败；只要模型把格式错误的“人民币玖拾贰万肆仟伍佰贰拾捌点叁圆”判断成 `true`，后端就会把该判断直接提升为正式 `PASS`。

已确认的业务口径是：序号7不仅比较数值，还必须校验人民币中文大写的金额单位和书写形式。本次同时面对两个运行阶段：仍在验收的 MVP 旧流程需要立即修复；未来二阶段尚未实现完整 `evaluate`，但必须继承同一规则。冻结的旧流程基线只记录当时事实，后续问题以追加记录方式同步，不能改写历史结果。

## Goals / Non-Goals

**Goals:**

- 让 MVP 序号7的正式结论由服务端确定性规则产生，不再信任模型布尔判断。
- 对小写金额与中文大写金额执行可复核的数值、单位和书写形式校验。
- 用通用金额转换规则覆盖整数、角分、零位和跨万/亿分组，不为本次合同原文编写特判。
- 保持两个现有合同评审入口的请求、响应和检查点标识不变。
- 把同一责任边界写入二阶段方案：Prepare 保存事实和证据，Evaluate 执行判断。

**Non-Goals:**

- 不在本变更中实现完整的二阶段 Prepare/Evaluate API、Schema 或流水线。
- 不扩展附件金额与正文金额一致性候选项，也不改变序号8、9、10或 B-4 的语义。
- 不新增金额格式第三方依赖，不把校验移回 Prompt，也不要求模型输出新的裁决字段。
- 不改写 2026-07-31 冻结基线的提交、环境或历史测试结果。

## Decisions

### 1. 用“从小写金额生成标准大写金额”替代“解析模型结论”

服务端先把 `total_amount_numeric` 转为 `Decimal`，再使用本地纯函数生成标准人民币中文大写金额，最后与 `total_amount_uppercase` 比较。标准形式使用中文财务大写数字和 `元/角/分/整` 单位；金额为 `924528.30` 时生成 `玖拾贰万肆仟伍佰贰拾捌元叁角`。

比较前只做不改变金额语义的外层规范化：去除首尾空白，并允许大写字段带或不带前缀 `人民币`。不把 `圆` 自动改成 `元`，不把小数点表达自动改成 `角/分`，也不通过模糊匹配掩盖字符、单位或位值错误。这样既能识别本次样例，也能把规则应用到其他金额。

选择生成后比较，而不是实现一个接受大量变体的中文金额解析器，原因是当前业务已经给出目标书写形式，生成器更小、更确定，也更容易用边界样例证明正确性。现有项目未引入中文金额库，本次不为一个局部规则增加运行依赖。

### 2. 服务端结果覆盖 `total_amount_match`

A-3 暂时继续返回 `total_amount_match`，以避免扩大 Prompt/Schema 和流水线兼容性变更；序号7不再使用该值产生正式结论。即使模型返回 `true`，只要服务端比较失败，序号7仍为 `FAIL`；即使模型返回 `false`，只要服务端可靠校验通过，序号7可以 `PASS`。

这保持“模型提取事实、后端裁决”的单一责任边界。后续可以在独立兼容性变更中删除该冗余字段，但不属于本次修复。

### 3. 失败原因按可行动类别输出

- 数值或大写金额缺失：沿用“无法校验”的硬阻断语义。
- 小写金额无法转为非负、最多两位小数的 `Decimal`：硬阻断并说明小写金额格式无法可靠校验。
- 中文大写金额与标准结果不同：硬阻断，并区分明显的金额单位/书写形式错误与数值不一致；原因至少回显实际大写和期望大写，便于测试人员复核。

本次不改变序号7的 `id`、名称、`FAIL` 和“硬阻断”等外部契约。

### 4. 在独立金额模块实现，在现有检查函数中消费

新增一个合同评审金额工具模块，封装 `Decimal` 规范化和人民币中文大写生成；`checks.py` 只负责将校验结果转换为序号7检查项。这样金额算法可独立单测，检查结果契约仍由现有规则层维护，也不会把未来二阶段代码提前耦合进 MVP。

未来二阶段可以复用同一无状态纯函数。Prepare 的 `amount_payment` 只保留小写金额、大写金额、币种、金额类型、原文及证据引用，不保存 `PASS/WARN/FAIL` 或类似 `total_amount_match` 的模型判断；Evaluate 在证据和事实覆盖充分时调用该函数生成正式结论。

## Risks / Trade-offs

- **严格标准形式可能暴露历史合同中的非标准变体**：这是本次“校验书写形式”的预期结果。通过保留实际值和期望值使问题可复核，不静默纠正。
- **中文金额零位和大数分组容易出现算法边界错误**：先为 0、整数、角分、内部零、跨万/亿和两位小数建立参数化失败/通过用例，再实现最小算法。
- **A-3 提取错误仍可能导致误判**：本变更消除“模型直接裁决”，但没有消除提取风险。MVP 保持现有提取契约；二阶段通过事实证据、字段状态和覆盖状态控制是否可裁决。
- **同一工具未来扩展到付款阶段时必须保持结果归属**：本变更只接入 MVP 序号7。后续两阶段方案已确认，付款阶段数字/大写书写核验仍归序号7；序号10只处理阶段数字金额、比例和合同整体金额关系的算术核验，不得因复用金额工具而重复生成大小写问题。

## Migration Plan

1. 先添加金额生成器和参数化失败测试，证明本次原样例在修复前失败。
2. 修改序号7规则，使服务端结果成为唯一正式判断，并运行合同评审定点回归。
3. 更新 Prompt/Schema 测试仅用于确认现有提取契约继续兼容，不删除 `total_amount_match`。
4. 追加旧流程基线后的新问题记录，并同步二阶段 Prepare/Evaluate 责任边界。
5. 完成 MVP 代码级验证后将测试台账置为“待复测”，由原测试场景执行真实端点复测。

回退时仅撤销金额工具和序号7接入；请求/响应契约无迁移数据，不需要数据回滚。

## Open Questions

无。当前已确认规则足以实施本次范围；其他未确认的中文金额同义写法或新币种格式如后续出现，作为独立测试反馈处理，不在本变更中静默扩展。
