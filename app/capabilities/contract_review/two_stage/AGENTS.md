# 合同评审两阶段模块工作约束

本文件适用于 `app/capabilities/contract_review/two_stage/`，以及根目录 `AGENTS.md` 明确路由到本文件的相关 API、配置、测试、OpenSpec 和文档任务。本文件继承仓库根目录及 `app/capabilities/contract_review/AGENTS.md` 的通用约束，只补充两阶段模块长期有效的专用边界。

## 权威来源与冲突处理

- 现有代码和真实运行证据用于说明当前实现实际做了什么；当前有效的 OpenSpec、Schema 和接口契约用于说明实现应当做什么。两者冲突属于实现漂移，必须停止扩散并修复，不得选择其中一个掩盖矛盾；自动化测试只是验证证据，不单独构成业务权威。
- 两阶段整体架构和已确认业务边界以 `docs/superpowers/specs/2026-07-28-contract-review-two-stage-upgrade-draft.md` 为权威；字段级和接口级要求以对应的当前有效 OpenSpec 及正式 Schema 为权威。活动 change 归档后，以归档形成的有效规范和正式 Schema 为准，不继续依赖历史 change 目录。
- OpenSpec 可以细化其作用域内的接口和行为，但不得静默取代整体架构或有效业务决定；发现冲突时必须进入决策完整性门禁。尚未形成对应 OpenSpec 或 Schema 时，只能依据已确认设计继续 Explore，不得自行发明接口、字段或错误语义。
- `docs/superpowers/specs/2026-08-03-contract-review-two-stage-field-glossary.md` 只统一术语；`docs/superpowers/baselines/2026-07-31-contract-review-legacy-baseline.md` 记录旧流程行为与已知问题；`docs/superpowers/specs/2026-08-15-contract-review-mvp-two-stage-sync-ledger.md` 记录检查点覆盖和迁移状态。三者不得越权替代 OpenSpec、Schema 或整体设计。
- `docs/integration/2026-07-28-contract-system-two-stage-review-communication-draft.md` 只用于合同系统协作沟通；实施计划、任务清单、聊天记录和交接 Prompt 只辅助执行，不得单独创造或改写业务契约。
- 项目决策台账入口为 `docs/decisions/index.md`。台账管理决定身份、作用域、有效状态、取代关系和传播状态，不复制详细业务规则，也不替代上述权威来源。

本文件不得重复维护业务枚举、字段定义、请求响应结构、错误码、检查点判断条件、附件目录、确定性算法或阶段进度。实现者必须读取当前作用域的有效权威文档；权威缺失或相互冲突时停止实现并请求确认，不得凭经验补全。

## Explore 与决策门禁

- 以一个完整业务分支作为确认单位，每轮只讨论真正未确认的问题；仅当两个问题强依赖且能够一次明确回答时，最多同时提出两个，用户要求“一次一个”时严格一次一个。问题和结论必须明确来源、对象、位置、字段及所属阶段，不得用含糊称谓跨坐标推导。
- Prepare Explore 只确认事实、候选、状态、关系、证据和覆盖；Evaluate Explore 才确认比较、适用性、检查点和正式裁决。技术结构由助手先自检，只有会改变业务范围或结果的分歧才提交用户确认。
- 已确认决定统一进入项目决策台账，不另建平级“冻结台账”。未确认候选不得取得正式决策 ID 或状态，也不得让两个冲突口径同时有效。
- 确认、澄清、取代或传播持久决定，以及实施交接、提交或归档前，必须读取项目台账并执行决策完整性门禁。个人 `decision-integrity-gate` Skill 可用时使用该 Skill；不可用时也必须至少核对决定身份、权威证据、冲突、取代关系和全部必需传播目标，不得跳过门禁。
- 新说法与有效决定冲突时先暂停传播并确认取代意图。明确确认后，必须在同一次授权更新中创建新 `active` 记录、通过 `supersedes` 关联旧记录并把旧记录标为 `superseded`；普通“ok”“同步文档”或实现指令不得静默取代旧决定。
- 进度只报告“本次完成项 + 剩余进度”。上下文已无法可靠区分来源、阶段、有效决定或未决问题时，暂停引入新规则，并先提供包含 Git 状态、受保护改动、权威来源、当前 change、已确认与已取代决定、未决问题、下一步和操作禁区的交接内容。

## 架构不变量

- 在当前仓库内增量建设，两阶段新代码保持在 `app/capabilities/contract_review/two_stage/`，不得另建独立项目。
- 旧流程基线所识别的旧流水线、接口和测试只作为现状与回归基线；未经明确批准，不先行重构，也不作为新流程的隐式生产回退。
- 新旧流程不得共享请求状态、混合检查结果或通过隐式开关互相切换。
- 本项目保持无业务状态；调用方负责合同文件、上下文、结果、跨版本关联和业务流程的持久化。具体责任以当前有效设计和 OpenSpec 为准。
- `prepare` 只生产合同来源的事实、候选、状态、关系、证据、覆盖和准备问题；`evaluate` 才生产正式裁决。两阶段的具体触发、输入输出、刷新和兼容行为以各自当前有效契约为准，不得跨阶段补值、裁决或回写事实。
- 受保护的运行时预设只允许在 `evaluate` 的确定性校验链路中按当前有效契约使用，不得进入 `prepare`、模型、业务持久化、日志、Trace、指标或正式结果中的原始值、正确值。
- 必须保留合同来源及其证据完整性，不得静默删除、合并或伪造来源，也不得由模型或实现者自行扩充业务目录、检查点或适用范围；输入、附件、重复判定和安全扫描的具体规则以当前有效 Prepare 契约为准。
- `evaluate` 的迁移范围必须覆盖旧流程全部当前有效检查点；任何专项实现或验证样例都不代表完整范围。检查点是否废弃必须由业务方明确确认。

## 变更与验证门禁

- Prepare 后续执行遵循 `docs/superpowers/playbooks/2026-09-07-prepare-execution-guide.md`；当前有效治理 DEC 以该指南和 `docs/decisions/index.md` 为准，不在本文件重复枚举。日常只保持主控制与实现两个活跃窗口，Gate 才临时派发独立只读复核。主控制是唯一任务派发出口，实现窗口是唯一代码/测试写入者；每张实现、SITE 或复核 Task Card 的定点读取与派发前自检硬门槛，以及风险、证据复用、测试取证和 SITE 探针的详细 SOP，只以执行指南为准。该指南不替代业务权威或当前任务状态；成本控制不得放宽必要独立复核、两轮熔断、保护配置或真实环境分层证据。

- 通用 TDD、自动化验证、Codex 主控制/实现/独立复核窗口分工和真实端点复测责任遵循仓库根目录及 `app/capabilities/contract_review/AGENTS.md`；本节只增加两阶段模块的专用门禁。
- 调用方可见行为变化必须遵循当前有效 OpenSpec 和实施计划；下游变更不得绕过尚未验收的上游契约。具体 change 名称、依赖顺序和当前进度只在整体设计、OpenSpec、实施计划及迁移台账中维护。
- 旧流程基线和全检查点迁移矩阵是持续验收依据。已知失败必须如实保留，不得修改旧测试期望制造全绿基线；每个变更都必须验证其阶段边界、新旧隔离、接口契约和受影响的旧流程回归。
- 未完成当前有效检查点覆盖、契约测试、新旧结果对比和必需传播前，不得宣称两阶段方案或实现已经收口，也不得切换生产调用。

## 跨会话交接

- 新开、替换或切换 Codex 窗口角色，以及当前上下文不再可靠时，使用个人通用 `session-handoff` Skill 生成临时交接摘要；同一窗口在阶段门禁通过后继续下一个 Task 时，只发送新的单任务指令，不触发 handoff。该 Skill 基于上游 `handoff` 增强，交接摘要只搬运当前工作，不是业务权威或当前事实源。
- 所有新窗口均由用户手动创建并选择模型；主控制窗口负责在需要 handoff 时主动生成临时文件并给出新窗口首条粘贴指令，但不得自动创建或 fork 窗口。
- 新会话开始后必须重新读取本文件；当前有效 OpenSpec、设计和实施计划只读取主控制在 Task Card 中列出的精确章节、定义或行段及其直接依赖。只有接收门禁确认基线、来源或语义无法可靠判定时，主控制才可明确要求扩大读取；不得仅依据 handoff 摘要推定规则或完成状态。
- 新会话必须现场读取 branch、HEAD、tracked 与 untracked 状态，并保持 `config/config-dev.yaml` 等无关用户修改不变。
- 每次交接只派发一个明确 Task，写明 `TARGETED_READS`、`FORBIDDEN_BROAD_READS`、允许范围、禁止操作、必要验证和停止条件，并可见确认执行指南要求的派发前自检；完成后停止，不自动进入下一 Task、批次或 change。
- 自动化验证与真实 vLLM、真实合同、真实端点和外部集成验证分开报告；实现者声明或 handoff 摘要不能替代独立复核。
