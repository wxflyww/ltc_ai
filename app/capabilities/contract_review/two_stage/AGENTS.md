# 合同评审两阶段升级实施约束

本文件适用于合同评审两阶段升级的新模块，以及根目录 `AGENTS.md` 明确路由到本文件的相关 API、测试、OpenSpec 和文档任务。

## 权威来源

- 当前生产行为：现有代码、已生效 OpenSpec 和接口契约。
- 未来升级设计：`docs/superpowers/specs/2026-07-28-contract-review-two-stage-upgrade-draft.md`。
- 合同系统沟通摘要：`docs/integration/2026-07-28-contract-system-two-stage-review-communication-draft.md`，与升级设计冲突时以上述升级设计为准。

不得在本文件重复维护各检查点的完整业务规则、哈希或附件判定规则；实现前读取升级设计中的对应章节。B-1/B-4 只是专项示例，不代表第二阶段的全部范围。

## 架构边界

- 在当前仓库内增量建设，不新建独立项目。
- 新代码位于 `app/capabilities/contract_review/two_stage/`，与旧流水线保持清晰边界。
- 现有 `router.py`、`service.py`、`run_review_pipeline`、旧接口和旧测试仅作为测试与回归基线；未经明确批准，不先行重构，也不作为新流程的生产回退。
- 新旧流程不得共享请求状态、混合检查结果或通过隐式开关互相切换。
- 本项目保持无业务状态：不新增合同、Markdown、`ReviewContext`、预设主数据或正式检查结果数据库。

## 两阶段责任

- 第一阶段 `prepare` 在文档异步解析完成后自动调用，只生成事实、证据、来源清单和准备问题，不输出正式 `PASS/WARN/FAIL`。
- 第二阶段 `evaluate` 只能由合同管理员操作触发。首期同步返回；只有实测 P95 或超时数据证明必要时才评估异步化。
- 第二阶段必须覆盖旧流程全部现有有效检查点，不得只实现 B-1/B-4；仅当业务方明确确认某检查点废弃时才允许不迁移。
- 合同系统持久化 Markdown 和 `ReviewContext`；正式检查结果由本项目返回 JSON，合同系统是否保存由合同系统决定。
- 系统预设签署人主数据在第二阶段实时读取，只用于本次检查，不进入 `ReviewContext`、本项目持久化、日志或正式结果。

## 输入与附件边界

- `prepare` 接收原始完整主 Markdown，以及当前合同版本全部有效的 `uploaded_attachments`；后者是完整快照，不是本次上传增量。
- 正文内嵌附件由本项目从主 Markdown 重新识别，不得作为 `uploaded_attachments` 再次传入。
- 合同系统负责跨批次合并、稳定业务身份、历史去重和销售侧提示；本项目在任何模型调用前完成单次请求重复兜底。
- 只有明确身份重复或“规范化标题/文件名 + 内容哈希”共同成立时拒绝；仅同名或仅同内容属于疑似重复，不得静默合并或删除。
- 合同正文和附件中的身份证号按审核内容处理；首期不引入 HMAC、密钥轮换或专用等值令牌架构。

## 变更顺序

创建第一个 OpenSpec 前，先运行旧流程基线测试并形成全检查点迁移矩阵。矩阵必须记录每个检查点的旧输入/依赖、第一阶段事实和证据、第二阶段判断、结果契约、新旧回归用例及迁移状态；存在已知失败时如实记录，不得通过修改旧测试期望制造全绿基线。

按以下 OpenSpec 顺序推进，每个变更单独验收：

1. `contract-review-context-foundation`；
2. `contract-review-prepare-api`；
3. `contract-review-evaluate-api`；
4. `contract-review-two-stage-pilot`。

未完成当前有效检查点覆盖、契约测试和新旧结果对比前，不切换生产调用。

## 实现与验证要求

- 先建立失败用例或契约测试，再实现最小代码；不为单一样例增加固定称谓、附件标题或 `definition_label` 枚举。
- 所有检查点都必须有明确的第一阶段事实/证据依赖和第二阶段判断实现；B-1、B-4 等语义提取采用高召回事实和证据，正式判断优先使用可测试的确定性后处理。
- 新测试与旧回归测试独立组织；新路径不得通过修改旧测试期望来制造通过。
- 每个变更至少运行定点测试、接口契约测试和受影响的旧合同评审回归测试。
- 无法完成真实端点或模型联调时，必须明确记录未验证项；单元测试和 mock 测试不能表述为真实运行验证。
