## 0. 治理原则与风险分级

Prepare 后续采用“风险分级的纵向切片 TDD + 主控制/实现双角色常驻 + Gate 式独立审计”。主控制是唯一 Task 派发与最终 Gate 决策出口；实现者只在 Task Card 白名单内实现、测试并返回现场证据，不扩大范围、不自行放行。能力可以按“必要组件 → Service → API → 最小真实链路”形成可验证纵向切片，但组件、Service、API 与真实链路的 GREEN 必须分层记录，互不替代。

- **LOW**：局部 helper、简单字段转换或不影响公共 Contract 的修改。实现 → 必要定点测试 → GREEN → 下一 Task，通常 `AUDIT_TYPE=NONE`。
- **MEDIUM**：Service 编排、重要业务逻辑或多模块内部协作。最小契约确认 → RED → 实现 → GREEN → 直接回归；仅异常、跨层影响或连续失败时升级审计。
- **HIGH**：公共 API/Contract、安全或权限边界、跨模块公共接口、真实模型接入和阶段完成 Gate。完整契约矩阵 → 一次性最小 RED 集 → 有界实现 → GREEN → 必要回归 → 按 Gate 选择独立审计。

测试、诊断和审计必须服务于当前 Gate 的核心判断：每次执行前，主控制应能说明其任一结果将改变的实现、归因或 Gate 决策。不能改变该判断的覆盖率增长、重复证据或孤立 harness 验证不得派发；相邻层已有充分证据时，不重复构造低收益链路测试。测试优先验证 P0 主链路、已实际发生缺陷、数据/安全/API 契约故障及阻塞 M1/M2 的问题；有明确风险或真实暴露的 P1 补最小验证；低概率 P2 或仅为覆盖率的组合待真实暴露后再补回归。行为变更与修复仍须 `RED → GREEN`。既有冻结行为的纯补证据/特征化测试允许首次 `GREEN`，但回执必须记为 `RED_N/A + negative-control discrimination verified`；不得为制造 RED 修改生产实现，也不得将变异反例记为标准 TDD RED。

同一跨层契约簇应尽可能一次性闭合矩阵与最小 RED 集；连续两轮仍不能闭合时，沿用熔断规则冻结零散 P1/P2 补丁，先做只读归因与矩阵闭合审计。现场未变化的有效证据可以复用，不因形式重复读取无关历史或重跑无关全量验证。

## 1. 用户如何参与

日常只保持主控制和实现两个活跃窗口。主控制同时是唯一 Task 派发与最终 Gate 决策出口。复核是独立角色，但只在本指南第 3 节的 Gate 触发时启用；普通定点 RED 补强不自动进入复核。用户仅在需要新建或替换某一窗口时创建并选择模型；助手不得自动创建、fork、替换或静默切换窗口。

| 窗口 | 唯一职责 | 读写与指令边界 |
|---|---|---|
| 主控制 | 定义边界、核对证据、派发唯一下一动作 | 仅在用户明确授权时同步决定/规范/计划；是唯一可向实现或复核窗口派发任务的出口。每条指令须包含执行窗口、唯一 Task、权威位置、允许范围、禁止操作、验证、停止条件。 |
| 实现 | 在白名单内实现与验证 | 只接收主控制指令；可写当前白名单内代码/测试，完成即停。不得改业务规则或权威文档，不自我放行，不直接进入下一 Task。 |
| 复核 | 独立只读审计与门禁判断 | 只读变更、证据和直接依赖；不写入。向主控制给出唯一门禁结论、证据位置和最小修复方向。其建议不构成对实现窗口的直接授权。 |

| 时点 | 助手负责 | 用户介入 |
|---|---|---|
| 启动一个普通 Task | 主控制向既有实现窗口给出可直接粘贴的单任务指令 | 仅在实现窗口需新建/替换时创建或选择窗口与模型，粘贴指令 |
| 实现与验证 | 实现者在白名单内实现、测试，完成后停止 | 无需逐步批准；将完成报告及证据位置转给主控制 |
| 普通 Task 核对 | 主控制检查关键差异、验收覆盖及证据有效性 | 无需重新确认已确认业务规则 |
| 独立复核门禁 | 仅在第 3 节触发时，主控制向复核窗口给出只读指令；reviewer 向主控制输出结论 | 复核窗口不存在或需替换时，创建/选择窗口与模型并粘贴指令 |
| 业务或范围存在实质分歧 | 主控制说明权威、差异、选项及影响 | 决定业务含义、范围、公共契约、权限或重大成本取舍 |
| 模型停滞或通道异常 | 报告原因、已完成内容和建议接替模型 | 切换模型；不静默替换，不并行增加写入者 |
| 真实合同、vLLM、API 验收 | 准备测试步骤和预期，分层记录证据 | 提供或执行实际环境复测 |
| 提交、推送、归档及既有红线操作 | 先完成必要验证与具体范围审查，再提出明确操作建议 | 按既有规则单独授权；实现者不提交 |

用户无需手工算哈希、设计测试矩阵或判断所有技术细节。助手不得为可由已确认规则推导的局部技术选择反复请示；业务权威不明确时不自行推断。

## 2. 每个 Task 的固定步骤

1. **接收并定位当前阶段。** 只有新建、替换、角色切换、上下文不可靠、权威/工作区基线漂移或用户明确要求的窗口才完整执行 receiver startup gate，读取适用 AGENTS、决策台账及主控制列出的当前 change、设计和实施计划的定点章节，并核对 cwd、branch、HEAD、tracked/untracked 与保护哈希。仅当该定点读取仍无法可靠判定基线、来源或语义时，主控制才可明确扩大读取范围。既有窗口复用未失效结论，不从 Explore/Propose 重启。
2. **检查变化并定点重读。** 主控制先用 Git/哈希识别本 Task 相关的权威、代码、测试和依赖变化，并在指令中列出需重读的具体文件或段落。实现和复核窗口只重读该清单及其直接依赖；文件未变无需通读。没有可用基线、发生上下文压缩/理解冲突或来源不可靠时，将该窗口按接收门禁处理。
3. **发出单任务指令。** 主控制是唯一派发出口。指令必须写明执行窗口、唯一 Task、验收范围和权威位置、`TARGETED_READS`、`FORBIDDEN_BROAD_READS`、允许修改/只读范围、禁止操作、必要验证、可复用证据及有效条件、报告要求与停止条件。主控制发送前逐项自检：执行窗口、唯一 Task、权威位置、定点读取、允许范围、禁止操作、验证/停止条件；任一项缺失即不得派发。Retry 指令还必须按第 2.2.1 节写明上次核心阻断、本轮解除动作与新增可判事实；涉及 PowerShell 自动执行时，还必须写明同一 `cluster` 的无终结回执计数及是否已达 `USER_REQUIRED`。指令还必须以 `DISPATCH_SELF_CHECK=PASS` 可见确认上述七项及适用的 Retry Gate / PowerShell 切换规则均已核对。`TARGETED_READS` 每项必须写明“文件 / 精确章节、定义或行段 / 目的”；确无读取需求时显式写 `none`。复核窗口的出站内容只向主控制提供门禁结论和最小修复方向，不直接派发实现。护栏是权威与验证的临时索引，不建立第二套规格。
4. **实现并取得证据。** 唯一实现者优先复用已有代码与有效测试；缺验证时补最小有效用例。行为变更或修复先取得失败证据；既有冻结行为的纯补证据/特征化测试按第 0 节记录首次 GREEN 与判别性反例，不人为破坏生产实现。运行受影响测试及本阶段明确要求的回归/校验。记录实际命令、退出码、结果与证据位置，不把成功数当作业务正确性的充分证明。
5. **停止写入并核对。** 实现者报告后停止。主控制看关键 diff、测试断言、验收覆盖、残留问题及证据时效；不重做完整独立审计。复核期间全部窗口冻结写入。保护配置只比较哈希，不输出内容。
6. **必要时独立审计，然后推进。** 按第 3 节触发独立复核。通过后主控制给出一个下一动作；下一 Task 用新的单任务指令。同一范围的独立审计已满足一致性审计要求时，不因技能名称不同再审一次。提交前再次核对实际暂存范围、证据及授权。

### 2.2 低消耗且不降门禁的执行预算

- 主控制在 Task 指令中一次列出该契约簇的同类边界（如 0/1/N、重复/冲突、引用闭合、稳定键、失败语义、跨文档隔离）；首次建立或语义变化时才附完整闭合矩阵。实现者先以该清单自检，reviewer 仍用同一清单独立审计，不以零散新用例反复重启同一问题。
- RED 测试或纯测试收紧默认只运行定点测试；GREEN 实现默认运行定点测试和直接受影响回归。全量 `tests/two_stage`、严格 OpenSpec 校验保留给阶段门禁、独立复核收尾、服务/API 接通、公共契约变更或影响范围无法确定时。跳过全量时须在回执写明“未运行”和适用的复用证据，不能伪称已重跑。
- 文件、测试、fixture 与环境未变时复用已有有效结果；检索只读取命中段和直接依赖，测试使用短摘要，不回传整段 traceback、完整 Git 状态或重复日志。若复核期间发生写入，相关证据按第 4 节标为 `STALE`。
- 每个窗口只在停止、阻断或请求确认时输出终结回执；中间过程不重复输出矩阵、基线或命令日志。正常回执最多包含 `GATE`、`SCOPE/WRITE`、`VERIFY`、`BASELINE`、`BLOCKERS/NOTES`、`NEXT` 六项；`BLOCKED` 时每个 P1/P2 各用一行附正式依据与最小方向。完整矩阵和逐项证据只在首次建立、语义变化或审计需要时提供。
- 同一根因连续两轮没有有效闭合时，仍严格执行第 2.1 与第 3 节的熔断归因；成本控制不得成为跳过真实 P1/P2、独立复核或生产证据的理由。
- 指令与回执按“稳定规则在前、动态事实在后”组织：稳定部分只引用当前有效决定、当前 Task 和固定格式；动态部分只写 `cluster / repair_cycle / fuse_state`、本轮变化胶囊、权威行段和必要验证。不得重复粘贴历史 P1/P2、完整回执、完整 Git 状态、traceback、矩阵或未变基线；需要原始证据时给出文件定位并按需读取。历史 DEC 保留取代链和追溯价值，不得仅为节省 token 而合并、删除或重写；日常以活跃决定和本指南作操作索引。
- 不得为了提高缓存命中而替换窗口、切换模型或推理档位、绕过现场核对或新增常设复核。模型、推理档位和窗口替换仍按第 1、2、5 节的既有触发条件与用户选择执行；平台仅提供汇总 token 指标时，只报告已测得的未命中输入、缓存命中和输出，不臆造详细未命中原因或可复用 token，也不得仅为该诊断新增 API 调用、日志采集或项目持久化。

### 2.2.1 Retry Gate

再次执行是为解除当前核心阻断或获得可推进判断的新增证据，不是对同一条件的默认重复。主控制在派发 Retry 前至少明确：上一次失败或不可判定的核心阻断；本轮将采取何种最小动作解除或补足该阻断；以及本次相比上次能够验证的新事实或已修复行为。若原样 Retry 仍大概率得到同一不可判定结果，应优先解决导致无法推进的主要问题，例如最小观测、证据、环境条件或有正式依据的最小修复，再决定是否 Retry。

失败原因已经明确且修复已完成时，可以直接 Retry 验证，不要求额外增加观测。原因尚不明确时，优先补足能定位主要失败边界的最小证据，不追求低概率边缘覆盖。该规则适用于测试、接口/模型调用、构建、部署、审计和 SITE 验证；不新增常设审计、日志体系、测试矩阵或形式化层级。既有 Gate、熔断和每项 Task 的停止条件继续有效；Retry 完成后仍按原停止条件停止，由主控制判断下一步。

同一 `cluster` 的同一 PowerShell 自动执行通道连续两次未获得可用终结回执（包括卡住、被执行通道中断或摘要未产生）后，主控制必须停止助手侧第三次尝试，明确切换为用户在持久 PowerShell 终端执行。交付给用户的指令只包含一次执行、预期等待/完成标识、脱敏回传边界和停止条件；该切换不绕过 Retry Gate、契约簇熔断或真实环境的 Gate。用户终端执行所得结果是为定位该执行通道或当前核心阻断的一次受控证据，不得据此自动连续重试。

### 2.1 跨层契约簇闭合

同一事实域中相互依赖的 Prompt、候选 Schema、装配、证据/coverage、稳定键和测试构成一个**跨层契约簇**。Task 启动时，或首次出现跨层阻断时，主控制必须建立并在任务指令中引用闭合矩阵：`正式要求 → 各层实现位置 → 测试证据`。实现者报告覆盖到的矩阵项；独立 reviewer 用同一矩阵检查护栏遗漏、测试断言充分性和跨层调用路径，不另起一套验收范围。

同一契约簇连续两轮修复后仍出现新的 P1/P2 阻断，即使此前单个失败用例已关闭，也视为“无有效闭合”：立即冻结写入，先判定问题属于规则、实现、测试矩阵还是环境，再补齐该簇必要的 RED 用例并重新派发有界修复。通过数增长或单点用例变绿不单独构成有效闭合。完成矩阵闭合后再进行一次独立审计；无变化、无新证据和无已知遗漏时不得重复打开已关闭问题。

### 2.1.1 熔断状态与不可达 RED 断言

- 主控制在同一契约簇首次 `BLOCKED` 时固定记录 `cluster`、`repair_cycle=0` 与 `fuse_state=OPEN`。每次为关闭该簇 P1/P2 的写入结束后，`repair_cycle` 加一；新任务卡、失败数、测试函数拆分或 P1 改写均不得重置该计数。
- 连续两轮后仍出现新的、具正式依据的 P1/P2 时，将 `fuse_state` 改为 `FROZEN`。此时唯一下一动作是只读归因和闭合矩阵审计；不得继续测试写入、派发 GREEN，或以新的 P1 文案绕过熔断。只有归因结论固定最小必要 RED 集后，主控制才可重新派发一次有界写入。
- `BLOCKED` 的每个 P1/P2 必须引用当前有效的 OpenSpec、设计、计划、决策或仓库约束。仅有聊天指令、实现报告或测试行号的意见是审计观察，先归入矩阵核对，不得单独成为写入派发依据。
- 若缺失前置模块使目标测试在断言体前一致终止，验证结果标为 `MODULE_ABSENT_RED`：它只证明导入门禁和归因，不证明新增断言语义。reviewer 对该 RED 契约一次性按闭合矩阵进行静态审计；未取得新的正式依据或矩阵变化时，不得反复以同一导入失败驱动零散测试补丁。

## 3. 独立复核、修复和提交边界

主控制在需要独立性时先判定 `AUDIT_TYPE = NONE | MATERIAL | SITE | BOTH`：

- `NONE`：普通低/中风险 Task 已有直接充分证据，无公共契约、跨层或安全边界变化时不启动独立审计。
- `MATERIAL`：主控制生成最小 `AUDIT_PACKET`，由用户交给 ChatGPT 根据已有材料独立判断。Packet 只含 `AUDIT_TARGET`、`AUTHORITATIVE_CONTRACT`、`CHANGE_SCOPE`、`CHANGED_FILES / DIFF`、`TESTS`、`TEST_RESULTS`、`KNOWN_NOTES`、`QUESTIONS`、`EXPECTED_VERDICT`，不得复制无关历史。`AUTHORITATIVE_CONTRACT` 必须给出与审计目标直接相关的文件/段落定位及足以独立判断的原文节选；只列文件路径不构成材料审计证据。HIGH、公共 API 或公共 Contract Gate 还必须给出“权威条款 → 实现/测试证据”的最小映射，并明确每项是已覆盖还是缺口。
- `SITE`：需要独立确认可复现测试、HEAD/工作区、保护哈希、环境或真实服务/端点事实时，由能进入现场的独立代理取证。探针必须命中项目实际调用边界和有效运行时配置；辅助端点只能作旁证。目标边界未执行时只能结论 `INCONCLUSIVE`，不得据此归因环境根因；与既有真实调用证据冲突时，先降级并复核真实路径。
- `BOTH`：固定顺序为 SITE 独立取证 → 主控制整理最小现场证据与 `AUDIT_PACKET` → 用户交给 ChatGPT 做材料审计 → 主控制根据 PASS/FAIL/NOTES 决定 Gate。

实现者自己的测试结果可作为实现证据，但在明确要求 SITE 的 Gate 中不得替代独立现场取证。

主控制接收 SITE 失败回执时固定按以下顺序判断：先核对 `TARGET_BOUNDARY` 是否为本次结论要证明的生产真实边界；`TARGET_EXECUTED=false` 时结论固定为 `INCONCLUSIVE`，禁止 `BLOCKED`、根因归类或派发修复；`CONTRADICTORY_EVIDENCE` 非空时暂停分类，先解释冲突并复核真实路径；只有前两项均通过，才可根据目标边界返回的 HTTP 状态、异常类型或现场输出判断根因与 Gate。

- 上游成果首次被下游依赖前必须完成必要验收；公共 Schema、稳定键、引用、覆盖、失败或模型调用语义发生变化，以及已确认高风险问题修复后，进入独立复核。不能带着未验收的上游契约推进。
- 不改变已验收公共契约、相互独立的局部实现可合并复核；主控制根据实际依赖确定边界，不按 Task 编号预先硬分批。
- 服务/API 接通和阶段收口保留相应整体验收；最终所需全量回归、OpenSpec 校验及真实端点证据不因日常精简而取消。
- 独立 reviewer 按主控制提供的增量清单读取变更的权威段落、代码、测试和直接依赖，核对完整验收范围并检查护栏遗漏；其报告可同时承担一致性审计，不能只看实现者报告。主控制只补冲突和证据缺口，并输出唯一推进结论。
- 复审检查原问题关闭、修改影响与有新证据支持的新问题；无变化、无新证据、无已知遗漏时不重复打开已关闭问题。严重问题不得因轮数或预算耗尽自动放行。
- 同一问题连续两轮修复仍无有效进展时，先定位是规则、实现还是环境问题，再决定澄清、缩小问题或升级模型；不无限循环补丁。单纯等候较慢的模型不等于失败。
- 提交候选必须范围明确、可验证、可解释；可按 Task 或闭合依赖批次提出。未解决高风险问题、证据漂移、混入无关修改时不建议提交，不先做 WIP commit。不得 `git add -A`，不得自动 commit/push/archive。

## 4. 证据如何复用

证据至少能说明：证明的约束及范围、当时的内容指纹和相关环境、实际命令、退出码/结果位置。指纹可附在现有报告或临时交接中，不新建状态数据库、事件系统或依赖台账。

| 变化 | 处理 |
|---|---|
| 只有无关文件变化，原验证范围与环境可确认未变 | 复用证据，不因换一条消息而重跑 |
| 被测代码、测试或 fixture 变化 | 补验受影响范围 |
| 共享 Schema、公共处理、Prompt、依赖版本或相关配置变化 | 查直接依赖，扩大相关回归；影响无法确定时保守补验 |
| 真实服务、模型部署或外部环境状态无法确认 | 原结果只作历史记录，不能据代码哈希推定端点仍有效 |
| 复核期间被写入，或提交对象与已验证内容不符 | 相关证据标为 STALE，重新确定影响并补验 |

HEAD 和文件列表不足以标识未提交内容；比较需覆盖实际工作区/暂存区以及本次相关未跟踪文件。哈希证明内容一致，不证明语义理解正确。无法取得旧内容基线时重读对应文件，不用 `git diff HEAD` 冒充两轮差异。

组件/mock、生产服务/API 调用链、真实 vLLM/合同/端点分别报告。已有有效证据可复用，但不得用历史结果伪称本轮重新运行，也不能用组件结果勾选尚待生产入口验证的要求。
