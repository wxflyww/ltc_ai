## 1. 目的与权威边界

本文固定旧流程在升级启动时的可复现状态，并为全部现有检查点建立迁移入口。它回答三类问题：

1. 旧接口实际接收和返回什么；
2. 旧流水线实际调用哪些 Prompt、模型和规则；
3. 每个现有检查点迁移到两阶段架构时需要哪些事实、证据和第二阶段判断。

发生冲突时按以下顺序判断：

1. 已由业务方在升级讨论中确认的新规则，是未来架构的业务权威口径；
2. `docs/superpowers/specs/2026-07-07-contract-review-design.md` 记录旧设计意图；
3. 当前代码和测试记录旧流程实际行为；
4. `docs/superpowers/specs/2026-07-28-contract-review-two-stage-upgrade-draft.md` 记录未来架构边界，并应在差异确认后同步结论。

本文不会用修改旧测试期望的方式消除差异。旧代码与业务规则冲突时，同时记录“代码现状”和“未来目标”。

## 3. 旧接口和结果契约

### 3.1 接口

| 方法与路径 | 输入 | 当前行为 |
|---|---|---|
| `POST /api/v1/contract-review` | JSON：`contract_md`、`attachments[]` | 同步执行完整旧流水线 |
| `POST /api/v1/contract-review/upload-md` | multipart：`contract_file`、`attachment_files[]` | 只接受 UTF-8 `.md`，转换成同一个 `ContractReviewRequest` 后同步执行 |

附件输入字段为 `index?`、`filename`、`file_type?`、`text`。当前旧接口没有 `contract_id`、`revision_id`、`document_id`、`attachment_id`、内容哈希、解析器元数据或版本字段。

### 3.2 结果

统一响应外层为：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "traceId": "",
  "duration_seconds": 0.0
}
```

`data` 为 `ContractReviewData`：

- `overall_result`: `PASS | BLOCK`；
- `check_time`: 检查时间；
- `checks[]`: `id`、`name`、`result`、`block_level`、`reason`；
- `metrics[]`: 每个模型步骤的耗时、token 用量和可选分段指标。

单项结果为 `PASS | WARN | FAIL | NA`，阻断等级为 `通过 | 提示 | 硬阻断 | 不适用`。只要存在 `FAIL + 硬阻断`，`overall_result` 才为 `BLOCK`。同一检查点可以同时输出 FAIL 和 WARN 两条记录，结果数组允许重复 `id`。

模型输入过长和输出截断会被转换为特殊硬阻断检查项；其他模型格式、超时和调用异常仍由统一错误响应处理。

## 4. 旧流水线和调用边界

### 4.1 预处理

`_preprocess_request` 先从完整 `contract_md` 拆出正文内嵌附件，再将拆出的附件与上传附件直接拼接。后续正文检查消费的是移除内嵌附件后的文本。旧流程不计算文档哈希，也没有跨批次或单次请求重复附件拒绝逻辑。

### 4.2 执行顺序

| 顺序 | 内部步骤 | 调用条件 | 产物/用途 |
|---|---|---|---|
| 1 | `a1a_party_extraction` | 始终 | 首页、签约方、签章方、正文分段 |
| 2 | 签署地预设值接口 | 对供应方和中性候选逐个尝试，命中即停 | 识别我方和取得预设主数据 |
| 3 | `a1b_our_signature` | 成功识别我方 | 我方签章页人员、身份证号、日期、账户及联系字段 |
| 4 | 序号1、2、3、11 确定性规则 | 始终 | 首页、签章、日期和账户检查结果 |
| 5 | `a3_amount_payment` | 始终 | 币种、付款方式、总价、付款阶段 |
| 6 | 序号7、8、9、10 确定性规则 | 始终 | 金额与付款类检查结果 |
| 7 | `a4_copies_attachments` | 始终 | 合同份数和附件声明 |
| 8 | `attachment_title_matching` | 同时存在未匹配的声明附件和上传附件 | 三态语义标题匹配 |
| 9 | 序号12、附件数量/标题规则 | 始终 | 份数、附件数量和标题结果；形成可检查附件集合 |
| 10 | `b1_appellation` | 正文一次，每份可检查附件一次 | 称谓候选，经后端证据校验、去噪、去重和排序 |
| 11 | `b4_attachment_content` | 每份可检查附件一次 | 附件内容候选，经后端金额证据校验和结果归一化 |

每次 `_invoke_json_prompt` 遇到非 JSON 或缺少必需顶层字段时最多再调用一次模型。B-1 返回过于笼统的旧式原因时，还可能额外执行一次“补充说明”调用。模型适配层自身不重试；实际调用模型由运行配置决定，本次 mock 基线没有验证默认模型 `qwen3.6-35b-a3b` 的真实行为。

按 `N` 份可检查附件估算，无格式或 B-1 补充重试时，常见模型调用数为：

```text
A-1a + A-1b(可选) + A-3 + A-4 + 标题语义匹配(可选) + B-1(1+N) + B-4(N)
```

- 序号1 签订地点规则；
- 序号10 阶段金额与比例、阶段大写金额规则；
- 序号12 份数缺失规则；

### P-medium：旧流程缺少版本化和输入身份

## 8. 冻结后追加记录

### 2026-08-12：序号7金额单位和大写书写形式漏检

- 测试事实：小写金额 `924528.30` 对应大写“人民币玖拾贰万肆仟伍佰贰拾捌点叁圆”时，MVP 序号7错误返回 `PASS`。
- 已确认口径：序号7既要比较金额数值，也要校验金额单位和中文大写书写形式；该样例正确文本为“人民币玖拾贰万肆仟伍佰贰拾捌元叁角”。
- 技术根因：旧流程仅依赖 A-3 模型返回的 `total_amount_match`，后端没有独立的确定性金额大写校验。
- 处理边界：已创建 OpenSpec change `seq7-uppercase-amount-validation`，修复 MVP 并同步未来二阶段规则；不改写本基线的历史测试结果，也不在该 change 中实现完整二阶段 Evaluate。
- 当前状态：已立项，尚未修改业务代码或执行修复后真实复测。

### 2026-08-13：序号7仅校验单一含税总价，漏检报价表其他金额，且不一致原因未分类

- 测试事实：真实复测发现序号7 `FAIL` 原因写作"实际大写金额"玖拾捌万圆"，期望大写金额"玖拾捌万元整""，只对含税报价 `980000` 输出；不含税报价 `924528.30`（大写"…贰拾捌点叁圆"）未被检测，两处金额错误类别（金额单位错误/小数书写错误）也未被分别指出。
- 已确认口径：序号7需校验合同报价中出现的每一处"小写金额 + 中文大写金额"配对（不含税总价、含税总价及各付款阶段）；不一致时应分别列出金额单位错误（`圆` 应为 `元`）和小数书写错误（`点` 应为 `角/分`），并回显每处实际值与期望值。
- 技术根因：A-3 提取契约把 `total_amount` 定义为含税总价，序号7只消费该单一字段；生成器本身无缺陷，是提取范围不足导致漏检；原因格式无分类。
