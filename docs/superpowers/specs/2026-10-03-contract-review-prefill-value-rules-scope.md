### 根因（#1 + #4）

本合同用 `【】` 填空，**模型对同一份合同、同一个 `【】` 形态给出 4 种不同取值方式**：

| 字段 | 原文 | 返回 | 括号边界处理 |
|---|---|---|---|
| `service_content` | `1.1 甲方委托乙方开发【…】项目。` | 整句，保留 `【】` | 全文照抄 ✅ |
| `service_valid_months` | `…之日起【两】年。` | `"两"` | **只取括号内** ❌ |
| `finance_info.contract_amount` | `（¥：【763200】元…` | `"763200"` | **只取括号内** ❌ |
| `service_end_date` | `在【2018】年【11】月【30】日完成。` | `"2018年11月30日"` | 拼接内外、去 `【】` —— 本合同为**非服务类**（技术开发合同）→ ❌ **源条款错**（见 R3） |

**同一份响应内自相矛盾**（更硬的证据）：`payment_amount` 来自「相当于合同总价款的【80】%」→ 返回 `"80%"`，**保住了括号外的 `%`**；而 `contract_amount` 来自「（¥：【763200】元」→ **丢了括号外的 `¥`/元**。

→ 结论：不是模型能力问题，是**括号边界没有规则、全靠概率**。用 `【】` 填空的政府/国央企合同极普遍，故该缺陷会**稳定复现**。

## 2. 修改项

### R1 · `【】` 填空边界规则（修 #1、#4）

统一为：**去掉 `【】` 标记本身，保留其前后紧邻的单位、货币符号与量纲**；取值必须自带单位（不得返回裸数字/裸量词）。

### R2 · 金额型字段统一不带货币符号（修 #4、定 #5 的一半）

**涉及字段仅 3 个**（已核 `prefill_response_formats.py:47 / 54 / 63`）：

`contract_plan[].payment_amount`、`finance_info.contract_amount`、`guarantee[].amount`

| | 内容 |
|---|---|
| 删除 | `¥` `￥` `$` `€` `£`、币种词「元」「人民币」「RMB」、千分位 `,`、首尾空白 |
| **保留** | 数字、小数点、`%`、数量级「万」「亿」 |
| **禁止** | 任何换算（不折「万」、不折 `%`、不转中文大写数字） |
| 大写兜底 | 优先取阿拉伯数字那一处；全文只有大写 → 返回大写原文 |
| 小数位 | 原样保留，不规整 |

> 🚨 **`payment_amount` 是比例/金额混合字段**（实测多为 `"50%"`）。规则**不得**写成"去除非数字字符"，否则 `"50%"` → `"50"`，语义灾难。`%` 必须在保留集。
>
> 🚨 **「万」「亿」不得折算**：`"46.9万"` 去掉「万」会差 10000 倍；折成 `469000` 又是服务端计算（违反"不换算"）。

### R3 · `service_start_date` / `service_end_date` 补取值来源规则（修 #2）

> 🔷 **2026-10-05（第十六轮）就已按「合同类型分路」定稿** —— 下面这段是最终口径，已落到 prompt / spec delta / 接口文档 / 测试四处。

**第一步：判合同类型。** 依据 = **合同名称**（正文最前面的一级标题，如 `…运维服务合同`）。**判据从宽**：名称里出现**服务性质词**（`服务` / `运维` / `运营` / `维护` / `技术支持`）→ **服务类**；看不出服务性质、**或根本读不到合同名称** → 一律 **非服务类**。不得因正文内容像服务而改判。⚠️ 下列词**不算**服务性质词（单凭其一不得判服务类）：`开发` / `咨询` / `设计` / `集成` / `实施` / `监理` / `勘察` / `检测` / `评估` / `外包` / `培训`。
⚠️ **反例词没有否决权**：名称只要含「服务」二字就一律判**服务类** —— 如「集成**服务**合同」「设计**服务**合同」「服务**外包**合同」均为服务类。

> 🔴 **⚠️ 第十七轮（2026-10-07）词表按"软件公司的服务类合同"收窄 —— 分两轮**
> **第一轮**，用户指出：「服务类合同的范围太大了，比如开发、咨询、设计等等这些都不是服务类合同，我们公司是软件公司，按软件公司的服务类合同来缩小范围」→ 16 词删至 **7 词**（`服务` / `运维` / `运营` / `维护` / `技术支持` / `外包` / `培训`），`开发` / `咨询` / `设计` / `集成` / `实施` / `监理` / `勘察` / `检测` / `评估` 列为反例。
> **第二轮**，用户追加「外包、培训**也去掉**」→ 正向词表再删至 **5 词**（`服务` / `运维` / `运营` / `维护` / `技术支持`）；**反例词增至 11 个**（上述 9 个 + `外包` / `培训`）。
> **判据**：反例词本身不表示"持续投入人力或技术为对方提供服务"，其标的多为**一次性交付成果**、**劳务事项**，或属**独立的合同类型**（《民法典》技术合同族：技术开发 / 技术转让 / 技术许可 / 技术咨询 / 技术服务）；名称带「技术」二字也不因此归服务类。
> 🔴 **关键边界：反例词没有否决权** —— 名称中只要出现「服务」二字，一律判**服务类**，哪怕同一名字里还带着反例词。用户 2026-10-07 专门问了「如果是**集成服务合同**，会判断为什么类型？」→ 答：**服务类**（命中「服务」二字）。同理「设计**服务**合同」「服务**外包**合同」「软件实施**服务**合同」均为服务类。**删掉「集成」这个词对「集成服务合同」的判定没有任何影响** —— 它原来也不是靠「集成」判进去的。
> ✅ **2026-10-07 用户拍板：保持现状（方案 A）** —— 曾评估过**方案 B**（把反例词升级为**否决票**：名称含 `集成`/`设计`/`实施`/`咨询`/`外包`/`培训` 等交付型词时一律判非服务类，哪怕含「服务」二字，则「集成服务合同」→ 非服务类）。用户明确选择 **A**。
> 🔴 **故：反例词 SHALL 继续只作"补充判据"（单凭其一不得判服务类）、SHALL NOT 作否决票 —— 不要改成 B。** 代价已知并接受：名称含「服务」二字但实为项目交付型的合同（如「集成服务合同」）仍判服务类。
> **影响面**：三份样例结论**不变**（`c1`/`c2` 无标题 → 非服务类；`c3` `…建设及技术**服务**合同` → 服务类）；`YDZB1812336A`（技术开发合同）仍为**非服务类** → **#2 缺陷结论不变**。接口文档 §4.3 与 §9 第 17 条自检（⑥ 项已专门写「集成服务合同」这个最容易判反的例子）、消费方说明 §2.3 类型表、spec delta（新增 Scenario `含「服务」二字的复合名仍按服务类`）、`tasks.md` §15 均已同步。

> 🔴 **⚠️「开发」不属服务性质词（踩坑记录，2026-10-05）**
> 初版词表里放了「**开发**」，于是 `【2018年诈骗电话共享平台建设平台TD】 技术开发合同` 被「技术**开发**」四字命中 → 误判为**服务类** → 连带把 2.1 的「开发完成日」合法化成 `service_end_date`，**等于把 #2 这条真缺陷洗成了合法取值**。
> **用户当即指出「技术开发合同不是服务类」**。核对《民法典》：技术合同是**独立合同类型**（技术开发 / 技术转让 / 技术许可 / 技术咨询 / **技术服务**），**技术开发合同的标的是交付开发成果，不是持续提供服务** → 应归**非服务类**。
> **已修**：把「开发」移出服务性质词表，并在 prompt 与 spec 里写成**显式反例**（「技术开发合同」「技术开发（委托）合同」一律非服务类；名称带「技术」二字也不因此归服务类；但「技术**服务**合同」因含「服务」二字仍属服务类）。
> **同时纠正的连带错误**：spec delta 原先拿「…平台建设 技术开发合同」当**服务类的正例**（`spec:151` 与 Scenario 的 WHEN 行），已换成「…运维服务合同」「…平台建设及技术服务合同」，并把 Scenario 里的完成日示例也换成中性日期，避免再引用本合同原文。
> **反向断言已固化**：`test_prefill_prompt_carries_contract_type_rule` 增加两条反向断言 —— ① 必须显式写明「技术开发合同」按非服务类；② 服务性质词表里不得再出现裸露的 `服务/开发`。→ 有人再把「开发」加回词表会立刻红。
> 📌 **教训**：一份"从宽"的正向词表，只要混进一个**与目标语义相反的词**，就会把缺陷洗成合法 —— 而这类错误**不会报错、只会静默改变结论**。故判据类词表必须配反向断言。

| 类型 | `service_start_date` | `service_end_date` | 两者关系 |
|---|---|---|---|
| **非服务类** | 只从服务 / 售后 / 质保条款取，且**只认绝对日期**；取不到 → `null` | 同上 | **必须成对**：同为 `null` 或同为有值 |
| **服务类** | **仍**只从服务 / 售后 / 质保条款取；取不到 → `null` | 上述条款取不到绝对日期时，**可以**改取**合同自身的完成 / 交付截止日**（如合同中写明的「本项目应于 2020 年 6 月 30 日前完成」） | **允许**只有 `service_end_date` 有值 |

**两类共同**：条款只写「事件起算 + 期限」（如「初验合格之日起两年」）或纯相对表述 → 对应字段 `null`；**不折算成具体日期、不按期限推算**。

> ⚠️ **这是一项口径决策，不只是 bug 修复**：补规则后，这两个字段在**多数合同上会收敛为 `null` 或相对表述**（合同普遍只给"初验合格之日起 N 年"）。**须先确认消费方能否接受"更正确但常常为空"**。
>
> 🔴 **本规则对 #2 那条缺陷的影响（已纠正后的最终结论）**：`YDZB1812336A` 是**技术开发合同 → 非服务类** → 其 `service_end_date="2018年11月30日"`（取自 2.1 开发完成日）**仍是缺陷**，`service_start_date=null` / `service_end_date` 有值这条「起止不成对」判据**对它依然成立**。
> 「允许只有 `service_end_date` 有值」这一条**只适用于服务类合同** —— 目前三份样例（`c1`/`c2`/`c3`）里仅 `c3`（`智慧园区综合管理平台建设及技术服务合同`，含「技术服务」）命中服务类，且它无「合同完成日」可被误取，故**该分支目前无实测覆盖**，需在真机上单独验一次。

### R4 · `evidence②` 返回口径（修 #3）

当「出处条款存在、但不含分阶段预计完成时间」时，明确 evidence② 的返回：**建议直接返回 `{"section": null, "quote": "无"}`**（落回文档已定义的态），或为文档判定表补第三档。

### R5 · `currency` 口径定死（修 #5）

明确为 **ISO 4217 三位大写码**（`CNY` / `USD` / `JPY` / `EUR`）。`max_length=8` 一并收紧为 3 —— **2026-10-05 用户拍板执行**。

> ⚠️ **实施后必须用美元/日元合同实测一次** —— 现有样例全是人民币，该字段从未被真正考验过。
>
> ⚠️ 去符号后金额里再无 `¥`/`$` 冗余，**币种完全依赖该字段**（原先金额自带符号是一层保险）。R2 与 R5 应同批实施。

## 3. ⛔ 实现约束（关键）

**R1–R5 必须全部通过 `prefill_prompts.py` 实现，服务端不得做任何字符串后处理。**

依据三条：

1. 设计原则：接口文档 §10 第 4 条「**服务端不对取值做任何二次加工** —— 拿到的字符串原样放进响应」。
2. 现有测试即以此为前提：`tests/test_contract_review_prefill.py:294` 的 `_ok_payload()` 注释为「模拟新取值口径下模型的输出：除 `milestone_seq` 外一律原文原样字符串」，断言 `:312` / `:330` 校验的是**原样透传**（`"¥10,492,500.00"` 进 → `"¥10,492,500.00"` 出）。
3. 若改为服务端 strip，将**打穿上述断言**，并改变「服务端零加工」的既有契约。

→ 走 prompt 方案时，服务端代码**零改动**，上述用例**不受影响**（仅建议把 `_ok_payload()` 的金额用例改为不带符号的形态，以忠实反映新口径）。
