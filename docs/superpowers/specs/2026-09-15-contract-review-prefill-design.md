## 1. 背景与范围

在**现行单阶段旧流程**（`POST /api/v1/contract-review`）内新增「从合同正文抽取字段做智能预填」的能力，用于 3 天后的一次最小版本演示。

**硬边界**：`app/capabilities/contract_review/two_stage/**` **零改动**。两阶段仍在精雕细琢，D-02 / D-03 后续再并入 Prepare 事实域，届时单独设计。

飞书原文档「已确认的前提」第 1 条「只扩展 Prepare 的事实域」已由用户删除，该约束解除；本方案不触碰 two_stage 的任何已冻结契约。

## 2. 目标 / 非目标

**目标**
- 一次调用，从合同正文抽出 D-02（13 项）+ D-03（8 项）共 **21 个需求项**，落为 **26 个返回字段**（§4.1 9 + §4.2 8 + §4.3 2 + §4.4 7）。其中 **§4.3 的 2 个字段（`finance_info`）由 D-02 / D-03 共用**（2026-09-18 第十四轮），故 26 是**去重后**的字段总数。
- 取不到则为 `null`（数组类为空数组）；允许**基于已抽到事实的推算**（口径见 §5.3），不允许无依据臆造。
- 复用现有模型适配层、重试与错误码体系。

**非目标**
- 不做前台适配；返回文档列出的全部字段即算交付。
- 不解析附件（沿用文档前提 4）。
- 不改 `mode=review` 的现有行为。
- 不做证据索引 / 覆盖度 / 事实域的通用抽象（那是两阶段的形态）。

## 3. 接口设计

### 3.1 请求

服务提供**两个入口**，二者的 `mode` 语义、字段口径与响应结构完全一致（第十三轮补齐，见 §11）：

**① JSON 入口（推荐）** `POST /api/v1/contract-review`，请求体如下（**仅 `mode` 与 `prefill_scope` 为本次新增**，其余两个字段原样不变）：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `mode` | `"review"` \| `"prefill"` | `"review"` | **调用方新增的请求参数**，用来区分本次调用是预填还是检查；不传 = 老行为 |
| `prefill_scope` | `"all"` \| `"d02"` \| `"d03"` | `"all"` | **调用方新增的请求参数**，仅 `mode=prefill` 时生效，按场景只抽一半；不传 = 抽全部 26 字段（见 §3.5） |
| `contract_md` | string | — | 不变 |
| `attachments` | array | `[]` | 保持接收，本期不参与抽取；**正文里内嵌的附件章节视同正文**（见 §11 第十三轮） |

**② Markdown 文件入口** `POST /api/v1/contract-review/upload-md`，`multipart/form-data`：`contract_file`（必填，UTF-8 编码 `.md`）、`attachment_files`（可多个，同样须为 `.md`）、`mode`（默认 `review`）、`prefill_scope`（默认 `all`）。表单字段 `mode` 同样走 `Literal` 校验，**取值非法返回 422 + `code=10001`，不再静默落回评审**；不传 `mode` 时行为与改造前逐字段一致。两个入口共用 `router._dispatch()` 一处分流。

| mode | 行为 | `data` 段包含的键 |
|---|---|---|
| `review`（默认） | 与今天**完全一致**：跑现有评审链路 | `overall_result` / `check_time` / `checks` / `metrics`（**4 个键，一个不多**）|
| `prefill` | **不跑评审**，只跑预填 | `mode` / `prefill_status` / `prefill`（**没有** `overall_result` / `check_time` / `checks` / `metrics`）|

> 判据 1：`mode=prefill` 时不出现 `overall_result`，避免"没评审却返回 PASS"的误判。
> 判据 2：`mode=review` 时 `data` 不含 `mode`，保持老响应**完全一致**（见 §3.2）。
> 判据 3：`review` 分支**不碰** `review_contract()`，只在路由层分流；预填与评审是两条独立路径。

> **第三态 `review_prefill`（评审 + 预填一起返回）已砍（2026-09-16）**：它源自 09-15 讨论中"甲顺带支持"的一个提议，并非需求方要求。本次只交付预填，保留它要多做响应合并、多一组测试，且合同系统多写一个分支；将来真要"一次拿两样"，在路由加一个 `if` 分支即可，属加性改动，不是返工。

### 3.2 响应（`data` 段）

`mode=prefill`：

```json
{
  "mode": "prefill",
  "prefill_status": "ok",
  "prefill": {
    "contract_info": { "...": "见 §4.1" },
    "contract_plan": [ { "...": "见 §4.2" } ],
    "finance_info": { "...": "见 §4.3" },
    "guarantee": [ { "...": "见 §4.4" } ]
  }
}
```

`mode=review`：**与今天完全一致**，`data` 里只有 `overall_result` / `check_time` / `checks` / `metrics`，**不新增、不回显任何字段**（`check_time` 沿用现有格式，不受 §4.5 的 `YYYY-MM-DD` 约束——那条只管预填字段）。

> **"完全一致"的口径**：指**结构层面**——键集合、类型、语义逐字段相同，不存在任何因本 change 新增/删除的键。
> 取值层面允许有一处已知差异（**不来自本 change**）：§4.6 的"关闭思考模式"（独立 change）会使模型输出略有出入。第八轮 3 次对照复测确认：`header.parties[].role` 的波动**在现状下本就存在**（不关思考时三次为「甲方/乙方」「招标人（甲方）/供应商（乙方）」「招标人（甲方）/供应商（乙方）」），**关思考后三次全部收敛为「甲方/乙方」**——即关思考消除波动、取值更贴合 `prompts/contract_review.yaml:23` 的 few-shot 示例（`"role": "甲方"`）。同期 `sections` 三次均为 `16`、顶层键集合完全一致。`temperature` 非 0，该类差异本就存在，非回归。

> **响应侧不回显 `mode`（2026-09-16 定案，取代原"回显"结论）**
> 规则：**`mode` 只出现在预填响应里**（`prefill`）。
> 理由：要让 `review` 也回显，就必须给 `ContractReviewData`（`schemas.py:45-49`）加字段；而本方案已定**预填用独立响应模型、`ContractReviewData` 零改动**（隐患 1 选乙），两者互相拆台。
> 收益对比：回显的唯一价值是"两类调用走同一地址时便于查日志"，但调用方本就知道自己传了什么、且响应已有 `traceId` 可关联——**薄收益换掉"老响应完全一致"这条最强回归判据，不划算**。

### 3.4 两个场景与调用形态的关系（2026-09-16 补充澄清）

**澄清**：D-02 = **合同管理员预填**，D-03 = **销售预填**，是两个业务场景，**触发时机不同**。

**结论：不为它们拆分调用形态，仍共用同一个 `mode=prefill`。** 理由不是"赶进度"，是接口形态本身不区分场景：

1. **返回值不依赖调用时机**：`mode=prefill` 是单请求单响应的**无状态**调用，输入只有 `contract_md` + `mode`，输出不随"谁调的""什么时候调的""第几次调的"变化。两个场景的差异属于**调用方的调度问题**，不是接口问题——合同系统在各自时点调一次即可。
2. **响应结构已经按场景分组**，各取各的组，不会糊：

| 场景 | 取用的组 | 返回字段数 |
|---|---|---|
| D-02 合同管理员预填 | `contract_info`（9）+ `contract_plan`（8）+ `finance_info`（2） | **19** |
| D-03 销售预填 | `finance_info`（2）+ `guarantee`（7） | **9** |

> 📌 **`finance_info` 由 D-02 与 D-03 共用**（2026-09-18 第十四轮定，见 §4.3）—— 两行都含它，**去重后合计仍是 26 个返回字段**（不是 28）。它按「基础信息」而非「场景专有」归属。

3. **重复抽取的真实代价（2026-09-16 实测修正，取代原"耗时 ×2、成本 ×2"的说法）**：两场景各自触发 → 同一份合同可能被**抽两遍**，**调用次数 ×2、输入 token ×2**，但**不是"耗时 ×2"**。原表述混了口径，实测如下（`tmp/samples/c1.md` 归一化后 5,838 prompt tokens；模型 `Qwen3.6-35B`；11 次调用共享 GPU）：

| 方案 | 输出 tokens | 耗时 |
|---|---|---|
| 合并抽 21 字段 | 1,074 | **7.42s** |
| 分开 · D-02（当时 17 字段） | 661 | **5.66s** |
| 分开 · D-03（9 字段） | 423 | **3.01s** |

> 📌 **2026-09-18 补充**：`finance_info` 已并入 `d02`（§4.3、§3.5），`d02` 场景现为 **19 字段**、输出 token 约 +30，对耗时的实测影响 **<0.5s**，故上表「合并 vs 分开」的结论（分开仅 +17%、并发压力不变）**不变**。本节数值为 2026-09-16 的测量快照。

拟合结果：**prefill ≈ 4,400 tok/s（compute-bound），decode ≈ 154 tok/s（memory-bound）**。**decode 占总耗时 84%，prefill 仅 16%** —— 重复喂全文多花的只是一次很快的 prefill（5,838 tokens ≈ 1.3s），而两种方案要生成的 JSON 总量几乎相同（1,074 vs 1,084）。故：

- **分开的总代价** = 5.66 + 3.01 = **8.67s**，对比合并 7.42s，**仅 +17%**（"×2"是错的）。
- **分开的收益** = 各场景只等自己那一份：D-03 从 7.42s → **3.01s（快 2.47 倍）**，D-02 从 7.42s → 5.66s（快 1.31 倍）。两场景错峰触发时**显存峰值反而更低**。
- **并发压力与"分开还是合并"无关**：decode 是 memory-bound，压力正比于**输出 token 总量**（两者几乎相同）；分开多出的 prefill 是 compute-bound，**几乎不吃显存带宽**。实测 16 并发下每请求延迟约翻倍（1.0s → 1.98s）但服务稳定、总吞吐仍上升——要防退化该调 vLLM 的 `--enable-chunked-prefill` / prefix caching，**不是改接口形态**。

> 结论：**"避免重复浪费"不构成采纳 `prefill_scope` 的理由**（代价只有 17%，且并发压力不变）；**"让销售场景少等 4 秒"才是**。演示只演一次调用，两条都无影响。

合同系统侧若两场景传入的 `contract_md` 是同一份，可自行合并为一次调用后缓存结果；**本方案不做服务端缓存**（属 §10 明确不做）。
4. **`prefill_scope` 进本次范围**（2026-09-16 第七轮改定）：让两个场景各取所需、少等时间。契约见 **§3.5**。

> 另需与合同系统确认（见 §9.5）：两场景传给接口的 `contract_md` 是否**同一份快照**。D-03 在合同流程更早的时点触发，若当时正文尚未定稿，抽到的字段会少于 D-02 时点——这不是设计缺陷（各传各的内容），但会影响演示预期与"抽两遍是否值得"的判断。

### 3.5 `prefill_scope`：按场景只抽一半（本次实现）

`mode=prefill` 时**可选**传入 `prefill_scope`，取值与行为如下（**仅 `mode=prefill` 生效**，`mode=review` 传了也无效、不影响老行为）：

| `prefill_scope` | 抽取的组 | 场景 |
|---|---|---|
| `all`（**默认**） | `contract_info` + `contract_plan` + `finance_info` + `guarantee` | **无业务场景** —— 仅测试与兜底（见下） |
| `d02` | `contract_info` + `contract_plan` + `finance_info` | D-02 合同管理员预填 |
| `d03` | `finance_info` + `guarantee` | D-03 销售预填 |

> 📌 **`finance_info` 同时属于 `d02` 与 `d03`**（2026-09-18 第十四轮定）。理由：D-02 的 `contract_plan[].payment_amount` **多为比例**（实测 `"50%" / "40%" / "10%"`），合同系统只拿到比例、拿不到合同总额就**无法折算出金额**；故把 `contract_amount` + `currency` 归为**两场景共用的「基础信息」组**，各调各的都能拿到，**不需要为了补总额额外再调一次 `d03`**。这是**分组归属的调整**，**不新增字段、不改字段名、不改取值口径**。

**未请求的组如何表达**：仍**返回四组结构、不省略键**，未请求的组按"未取到"表达（对象组字段全 `null`、数组组为空数组）—— 具体到本版：`d02` 下只有 `guarantee` 为 `[]`；`d03` 下 `contract_info` 各字段为 `null`、`contract_plan` 为 `[]`。复用 §4.5 / §6 已有规则，**不引入新语义**（响应上无法区分"没请求"与"没抽到"，与 §6"不提供字段级覆盖度"一致）。

**收益（实测，§3.4 第 3 条）**：D-03 场景 **7.42s → 3.01s**，D-02 场景 7.42s → 5.66s。

**默认值向后兼容**：不传 = `all` = 今天定义的完整 26 字段，**演示可以不传**。**但生产必须显式传 `d02` / `d03`** —— `all` 没有任何业务场景需要（D-02 / D-03 触发时机不同，合并反而让先触发的那个白等），且它是当前**最慢**的一条路径：实测 `all` 8.8s vs `d03` 2.2s，并发下会显著放大超时风险（联调文档 §11.4 第 5 条已列为首推建议）。

**成本**：3 套 schema 本就需分写（D-02 / D-03 字段组不同，`all` 由前两者拼装，无重复内容）；真正新增的只有请求模型加 `Literal["all","d02","d03"] = "all"`、按 scope 选 prompt / schema、未请求组填 `null`/空数组，以及 3 个测试用例。**纯加性，半天以内。**

**唯一代价**：联调多一个沟通项（合同系统需知道有这个可选参数）。

## 4. 字段清单与 JSON 结构

### 4.1 `contract_info`（D-02 合同信息，9 个字段 / 文档计 8 项）

| # | 页面标签 | JSON key | 类型 | 说明 |
|---|---|---|---|---|
| 1 | 付款条件 | `payment_terms` | string | **整段原文**，不结构化拆分 |
| 2 | 付款方式 | `payment_method` | string | 原文，如「电汇」 |
| 3 | 服务内容及方式 | `service_content` | string | 原文 |
| 4 | 服务有效期限（月） | `service_valid_months` | string | **原文写法**（第十轮：原为 `number`） |
| 5 | 服务级别（SLA） | `service_sla` | string | 原文 |
| 6 | 服务开始时间 | `service_start_date` | string | **原文写法**，不归一成 ISO 日期（第十轮：原为 `date`） |
| 7 | 服务结束时间 | `service_end_date` | string | **原文写法**，不归一成 ISO 日期（第十轮：原为 `date`） |
| 8 | 现场服务次数 | `onsite_service_count` | string | **原文写法**（第十轮：原为 `number`） |
| 9 | 巡检次数 | `inspection_count` | string | **原文写法**（第十轮：原为 `number`） |

> 页面上另有 合同编号 / 合同类型 / 签订部门 / 业务类型（汽车）——**不在 D-02 清单，不返回**。
> 本组**不附** `evidence`（理由见 §5.1：`payment_terms` / `service_content` / `service_sla` 自身即整段原文）。
> **「付款条件」与「付款方式」的边界（已定）**：合同里这两项常在同一章节（样例 `c1.md` 只有 `# 第六条 付款方式` 一处），若不划界会抽出同一段。划分口径——
> - `payment_method` = **支付手段**（电汇 / 转账 / 汇票 / 承兑…），通常是短词或一个短语；
> - `payment_terms` = **分期与条件条款的整段原文**（比例、触发条件、期限），即 `contract_plan` 各行的来源。
> 两者确实只有一处原文时，`payment_method` 只取其中的支付手段词，其余归 `payment_terms`，**不整段重复**。

### 4.2 `contract_plan`（D-02 合同计划，数组，每项 8 个字段 / 文档计 5 项）

| 页面标签 | JSON key | 类型 | 说明 |
|---|---|---|---|
| 里程碑（标准名） | `milestone_name` | string | 从 §5.2 的 13 个标准名中选，取不到为 `null`（不用空串）|
| 里程碑（标准名 code） | `milestone_code` | string | 如 `begin`，与 name 配对 |
| 里程碑（原文） | `milestone_text` | string | 付款条件里的原文描述，供用户核对 |
| 里程碑序号 | `milestone_seq` | **integer** | 付款阶段顺序，从 1 起。**全响应唯一的非字符串字段**（第十轮） |
| 计划完成时间 | `plan_finish_date` | string | **原文写法**，不归一成 ISO 日期（第十轮：原为 `date`）。**来源按序取到即止**（第十一轮）：① 有独立「合同计划 / 进度计划」章节 → 该章节；② 无 → 交付 / 验收条款；③ 都无 → `null` |
| 计划回款时间 | `plan_payment_date` | string | **原文写法**。**只**取自付款条件里本阶段的时间表述（第十一轮：明确不依附 `plan_finish_date` 的出处，服务端也不做推算） |
| 回款金额 | `payment_amount` | string | **原文写法**；原文写比例就返回比例、不折算（第十轮：原为 `number`） |
| 依据 | `evidence` | object[] | 该行**全部字段**的原文出处，**固定 3 条**（付款条件 / 合同计划章节或交付·验收条款 / 合同金额条款），**每条带章节位置**（元素结构见 §4.5）；某出处原文确实不存在时该条为 `{"section": null, "quote": "无"}`（第十一轮） |

> 表格里的「序号」列由合同系统按数组顺序生成，**不作为字段返回**。`milestone_seq` 回的是**该阶段在付款条件原文中的顺序**，供排序与核对；两者通常同序，但来源不同（一个由合同系统生成，一个来自原文）。
> 「已开发票金额」非 AI 字段，不返回。
> **数组顺序（已定）**：按 `milestone_seq` 升序，即**付款条件原文中的阶段顺序**。不用日期排序——有阶段可能取不到日期，用日期排会把它们挤到未定义位置。

> **`evidence` 为什么是数组、且要带章节位置（2026-09-16 定案）**：一行的字段常横跨多处原文，逐字段的出处如下——
>
> | 字段 | 出处 |
> |---|---|
> | `milestone_name` / `milestone_code` / `milestone_text` / `milestone_seq` | 付款条件（该阶段原文） |
> | `plan_finish_date` | **有**「合同计划」章节 → 该章节；**无** → 交付 / 验收条款的时间节点 |
> | `plan_payment_date` | 付款条件里本阶段的时间表述（第十一轮：与该行 `plan_finish_date` 的出处**无关**） |
> | `payment_amount` | 合同金额条款 **+** 付款条件中的比例 |
>
> 一行的出处**固定 3 条**（第十一轮起）。要点：**有无「合同计划」章节只改变 `plan_finish_date` 的出处归属，不改变条数**（有该章节则出自该章节，没有则出自交付 / 验收条款）。
>
> 每处出处**各列一条**，并**标注它来自合同里的哪个章节 / 条款**。这样用户点开「AI 依据」时，不只看到"数字是怎么算的"，还能直接定位到原文位置去核对。
>
> 以一行 `contract_plan` 为例（为简明省略 `milestone_code` / `milestone_seq`）：
>
> ```json
> {
>   "milestone_name": "启动",
>   "milestone_text": "合同签订及预付款",
>   "plan_finish_date": "2026年8月15日",
>   "plan_payment_date": "合同签订后7个工作日内",
>   "payment_amount": "30%",
>   "evidence": [
>     { "section": "第四条 付款方式及条件", "quote": "合同签订后7个工作日内支付合同总额的30%" },
>     { "section": "合同计划",             "quote": "2026年8月15日前完成合同签订" },
>     { "section": "第三条 合同金额",       "quote": "本合同总金额为人民币3,865,000元" }
>   ]
> }
> ```
>
> 单个字符串装不下多来源、也无法标注位置（要么丢信息、要么挤成一团没法定位），故为对象数组。

> **两个时间字段的口径（第十一轮，2026-09-17 定案）**
>
> | 项 | 约定 |
> |---|---|
> | 来源 | `plan_finish_date`：合同计划章节 → 交付 / 验收条款 → `null`，按序取到即止<br>`plan_payment_date`：只取自付款条件里本阶段的时间表述 |
> | 绝对基准日 | 合同签订日期（**由消费方使用**，服务端不拿它做任何计算） |
> | 服务端是否推算 | **不推算**。不做日期加减、不把「120天」折成具体日期、不用完成时间推回款时间。原文是绝对日期就给日期，是相对表述就照抄（如 `"自合同签订之日起120天（自然日）内"`） |
> | 算不出时 | 返回 `null`，并在该行 `evidence` 的第 2 条写 `{"section": null, "quote": "无"}` |
> | 消费方规则 | 该行 `plan_finish_date` 为 `null` → `plan_payment_date` 无从推算，按「无法推算（缺预计完成时间）」呈现 |
>
> **「无」的语义是「按出处」而不是「按字段」**：`evidence` 是行级、按出处的（固定 3 条）；某处出处原文确实不存在时该条写 `"无"`。若理解成"某字段没有原文"会**自相矛盾** —— 同一行的 `payment_amount` 明明有依据。
> 判定必须用**全等**（`"无".equals(quote.trim())`），不能用包含，否则原文里的「无违约条款」会被误判。
> ⚠️ **方向性提醒**：只给 `found | absent` 两个出口会逼模型在漏抽时"自信地说没有"；写 `"无"` 的前提是**通读全文确认原文没有该处内容**，抽取困难、看不清、不确定都**不算**。
>
> **为什么不给对象组（`contract_info` / `finance_info`）也加字段级 evidence**：① 其中的值**本身就是原文片段**（`"¥10492500.00"`、`"1年"`、付款条件整段）—— **值即证据**；② 真正对不上原文的只有 `currency`（映射成 `CNY`），以及 `milestone_seq` / `milestone_code` / `milestone_name` 这类**生成或映射**的值，它们**物理上没有原文可引**；③ 字段级 evidence 会撞上开发边界 6.5「不引入证据索引 / 覆盖度（含字段级抽取状态）/ 事实域」，且实测代价是 +700 tokens ≈ **+4.6s**（约占 `all` 现耗时的一半），还会摊薄注意力、加剧归属漂移。

### 4.3 `finance_info`（D-02 **与** D-03 共用，财务信息）

| 页面标签 | JSON key | 类型 | 说明 |
|---|---|---|---|
| 合同额 | `contract_amount` | string | **原文写法**（第十轮：原为 `number`） |
| 币种 | `currency` | string | 如 `CNY` |

> 本组**不附** `evidence`（理由见 §5.1）。

> 📌 **归属（2026-09-18 第十四轮定）**：本组**不专属于 D-03** —— `prefill_scope=d02` 与 `d03` **都返回它**。设计初衷是把「有合同总额」当作两场景共同的前置信息：D-02 拿它把 `contract_plan[].payment_amount` 的比例折成金额，D-03 拿它填充销售侧的合同额字段。因此它**不改变 §3.4 / §3.5 的分组数量口径**（合取去重后仍是 26 字段），只是**把归属从「D-03 专有」改为「两场景共用」**。

### 4.4 `guarantee`（D-03 履约保证金 / 保函，数组，支持多笔、**不设上限**，无则空数组）

| 页面标签 | JSON key | 类型 | 说明 |
|---|---|---|---|
| 申请类型 | `type` | enum | `履约保函` \| `履约保证金`，二选一 |
| 申请金额 | `amount` | string | **原文写法**；原文写比例就返回比例、不折算（第十轮：原为 `number`） |
| 收款单位/受益人 | `payee` | string | 甲方开户名称 |
| 银行名称 | `bank_name` | string | 甲方开户行 |
| 银行账号 | `bank_account` | string | 甲方账号 |
| 归还条款 | `return_clause` | string | 原文 |
| 依据 | `evidence` | object[] | 同 §4.2：按出处各列一条、去重、**每条带章节位置**（元素结构见 §4.5）；拿不到为空数组 |

> 页面上多出的 申请时间 / 支付时间 / 付款方式 / 预计归还时间 **不返回**（不在文档清单内）。

### 4.5 通用约定

- **类型口径（第十轮重写）**：**除 `milestone_seq`（`integer`）外，本响应所有业务字段都是 `string`**，承载原文原样摘录。表中写「**原文写法**」的字段，服务端**不做任何加工** —— 不换算、不去符号、不补或截断小数位、不归一日期。
- **为什么不用 `number` / `date`（第十轮）**：值一旦被声明成 JSON 数字或 ISO 日期，**转换过程本身就是误差来源** —— `float` 会把模型输出的整数 `13` 序列化成 `13.0`（下游按整型反序列化即失败）；`int` 遇到原文 `13.5` 直接报错；而为满足 JSON number 语法，模型还得被迫丢掉货币符号与千分位、按类型补/截小数位。**类型与展示格式交由合同系统自行定夺。**
- **对调用方的影响（第十轮）**：合同系统须全部按 `String` 接收（金额不要声明为 `BigDecimal` / `Integer` / `Long`，日期不要声明为 `Date`）。需要数值或绝对日期时自行解析，**换算口径（`"50%"` 要不要折成金额、`"1年"` 算几个月）由合同系统界定**。
- **不在"原样"范围内的字段**：`currency`（`CNY`）与 `guarantee.type`（`履约保函` / `履约保证金`）属**分类编码**而非原文摘录，保持归一。
- **`*_date` 字段名有误导性（第十一轮）**：`plan_finish_date` / `plan_payment_date` / `service_start_date` / `service_end_date` 都是 `string`，**值未必是日期** —— 可能是绝对日期，也可能是相对/事件表述（实测样例：`"自合同签订之日起120天（自然日）内"`、`"自系统上线并最终验收合格之日起计"`）。调用方须**先尝试解析、解析失败就原样展示**，不要直接丢给日期类型转换。这是刻意选择：原文怎么写就怎么给，怎么算由消费方决定。
- **服务端不推算（第十一轮）**：预填链路**不做任何日期计算** —— 不加减天数、不把「120天」折成具体日期、**不用完成时间推算回款时间**。绝对基准日（合同签订日期）只供消费方使用。
- **`evidence` 元素结构（§4.2 / §4.4 通用）**：`{ "section": string | null, "quote": string }`
  - `section`：该条原文所在**章节 / 条款标题，取原文原样**（如 `"第四条 付款方式及条件"`、`"合同计划"`）；原文无标题结构时（如换行归一化后仍无标题的正文）为 `null`。
  - **`section` 取哪一级标题（已定）**：取**顶层条款标题**（如 `# 第四条 付款方式及条件`）。**不取子层级**——实测 `tmp/samples/c1.md` 归一化后有 16 个 `# 第N条` 顶层标题，但另有 26 个 `## N.M`（如 `## 1.1分阶段支付合同款：招标人分三次…`），这些子层级的内容**是正文段落而非章节名**，取下去会让 `section` 塞进一整句话。原文若只有一层标题，即取该层。
  - `quote`：原文片段，≤300 字（**第十二轮**：原为 60 字，实测常截断在句中，放宽至 300 让常规条款整句容纳）。
    ⚠️ 它是**上限而非目标**——原文只有一句就照抄一句，**不要为了凑长度把整段抄进来**。
  - **`contract_plan` 每行固定 3 条**（第十一轮）：① 付款条件 ② 合同计划章节或交付 / 验收条款 ③ 合同金额条款。**「无」按出处而非按字段** —— 某处出处原文确实不存在时该条为 `{"section": null, "quote": "无"}`，判定用全等。语义与理由见 §4.2 末的专题块。
  - 不预设 `section` 的枚举、不做标题白名单——**取原文写法**，与 §5.1「不写死规则」一致。
- **缺失表达**：拿不到一律 `null`（数组类为空数组），不用空字符串占位。**唯一例外是 `evidence` 里的 `"无"`**：它是"该处出处不存在"的显式声明，不是空值占位。

### 4.6 输出形态：思考模式必须关闭（硬约束）

**约束：预填这一次模型调用的返回值必须是纯 JSON，不得混入任何思考（thinking）内容。**

**为什么是硬约束（实测证据，2026-09-16）**：`Qwen3.6-35B` 默认开启思考模式，会先输出一大段英文 `Here's a thinking process: ...`，且**思考里会写出结构草稿**。现有解析链 `parse_json_object`（`prompts.py:52`）在严格 `json.loads` 失败后，用 `_extract_json_object`（`prompts.py:38`）**扫描全文找第一个能成功解析的 JSON 对象**。实测：

| | 耗时 | 输出 tokens | 输出字符 | 解析结果 |
|---|---|---|---|---|
| **不关思考（即今天的行为）** | **40.58s** | **6,103** | 16,710 | ⚠️ **"成功"，但抽到的是思考草稿** |
| 关思考 / 结构化输出 | **7.42s** | 1,074 | 2,598 | ✅ 正确 |

不关思考时，`_extract_json_object` 命中的是**第 4,911 字符处的思考草稿**（`Let's structure \`contract_plan\`: [{...}]`），返回的顶层键是 `milestone_name / milestone_code / ...` 而不是 `contract_info / contract_plan / ...` —— **静默返回错误结果，不抛任何异常**。若预填定义了 `required_keys` 则会触发一次重试（`service.py:348`），再花约 40s 后仍大概率失败。

> 也就是说：不关思考**不只是慢 5.5 倍，而是会静默返回错误数据**。这是本约束的真正理由。

**实现手段（实测可行 · 定案，2026-09-16 第八轮收窄）**：**在合同评审自身的调用点显式关闭** —— 在 `app/capabilities/contract_review/service.py` 的 `_invoke_json_prompt` 中，`model = get_chat_model()` 之后按开关追加 `model = model.bind(extra_body={"chat_template_kwargs": {"enable_thinking": False}})`。

- **`app/models/llm.py` 零改动**（第八轮改定）。实测 `model.bind(...)` 返回的 `_ChatModelBinding` 会透传底层模型属性：`getattr(model, "model_name", "")` 仍返回 `Qwen3.6-35B`，`invoke_model` 的 Prometheus 标签不退化；且与 `response_format` 共存无冲突。既然三条链路已收窄为一条，就不必再动通用适配层这个共享文件。
- `_invoke_json_prompt` 是评审链路全部模型调用的**唯一入口**（`service.py:316` 首次调用与 `:357` 格式错重试共用同一个 `model` 变量），**一处接线即覆盖 `mode=review` 与 `mode=prefill`**。

| 手段 | 实测效果 | 结论 |
|---|---|---|
| **`extra_body={"chat_template_kwargs":{"enable_thinking":false}}`**（经 `model.bind` 透传）← **定案** | thinking 关闭（同一用例 689 → 7 tokens） | 生效；**与 `response_format` 共存无冲突**（实测同传两者仍为 7 tokens） |
| `response_format` = `json_schema`（strict） | 结构化输出链路下 thinking 亦消失 | 保留为**格式约束**（见下），**不作为关思考手段** —— 它只覆盖"为了要 JSON"的调用，非 JSON 调用（如 `translate`）够不到 |
| ❌ `chat_template_kwargs` 直接作为 invoke kwargs | **报错** `TypeError: Completions.create() got an unexpected keyword argument` | 不可用（LangChain 把未知 kwargs 直接塞给 openai SDK） |
| ❌ prompt 里加 `/no_think` 文本 | **无效**，实测照样 thinking | 不可用 |

**生效链路与排除项（2026-09-16 第八轮定案：两条红线 + 一条排除）**：

| 调用点 | 现状实测 | 本次 |
|---|---|---|
| `contract_review` 评审链路（`service.py:316`） | 带 `response_format`，**未被污染**（head 即 `{`，48.19s） | **关思考**（唯一改动）→ 42.19s，消除不确定性。除此之外一律不碰 |
| `contract_review` 预填链路（本次新增） | — | **关思考**（必需，见上表） |
| `two_stage` prepare（`prepare_model.py:369`） | 带 `response_format` | **零改动（红线）** —— 两阶段正在并行精雕，不得引入任何不可控变量 |
| `translate`（`translate/service.py:53`） | **无 `response_format`；实测输出 25,782 字符中约 67% 是思考文本**，44.08s | **零改动** —— 该能力由其他同事负责，本次不得影响其行为 |

> 两条红线（用户 2026-09-16 明确）：① **不碰 `two_stage`**；② **`mode=review` 只关思考，别的什么都不碰**。
> `translate` 的思考污染是一条**真实缺陷**（用户实际拿到的"译文"混着英文思考），已登记为 §9 第 7 条知会责任人，**本方案不修**。

**后端兼容逃生门**：`chat_template_kwargs` 是 vLLM / Qwen 特有参数，切到不支持它的后端会 400。故在 `app/core/config.py` 的 `LlmSettings` 新增配置项 `disable_thinking`（环境变量 `LTC__LLM__DISABLE_THINKING`，默认 `true`），**仅评审链路（含预填）**读该值决定是否绑定；后端不兼容时置 `false` 即一键退回现状。该配置项是加性字段，`two_stage` / `translate` 不读取它，故对两者无任何行为影响。

**与 `response_format` 的分层关系（不是替代，是各管一层）**：

- `disable_thinking`（**调用层**）＝ **输出确定性**：保证返回内容只是答案，不含思考。
- `response_format`（**格式层**）＝ **结构约束**：把 §4 的 26 个返回字段变成机器强约束，并因 schema 内所有字段 `required` 而**保证 `prefill` 键必定齐全**（与 §6"结构仍在，不省略键"一致）。

**预填两者都要用**。此外仍须传 `required_keys`：schema 只约束**格式**，`required_keys` 是**内容兜底** —— 万一后端降级、schema 未生效，它能让错误显式暴露（抛 `ModelFormatError` 并触发重试），而不是像上表第一行那样静默返回错误结构。

## 5. 抽取与计算规则

### 5.1 基本原则

- **单次调用**抽全全部字段：21 个需求项 / 26 个返回字段（现有评审链路每个 prompt 已各塞一遍全文，预填单独一次即可，不再叠加）。
- **输出必须为纯 JSON**：预填调用必须**同时**配 `disable_thinking`（关思考）与**结构化输出**（`response_format` json_schema）——前者保证不含思考内容，后者把 26 个字段变成机器强约束。见 **§4.6**（硬约束，非优化项）。
- 输入先做**换行归一化**：合同系统实际传来的正文可能是「一整行 + 字面量 `\n`、无真换行」（样例 `tmp/samples/c1.md` 即为此形态），不归一化会丢掉 markdown 结构（尤其付款计划表）。归一化在预填 prompt 边界内完成，不改动评审链路。
- **不写死计算规则**：不做句式白名单，不让模型套固定模式；**先抽事实，再基于抽到的事实分析计算**。
- **原文依据的粒度**：§4.2 / §4.4 的**每一行**都带 `evidence` **对象数组**（每处出处一条，**带 `section` 章节位置** + ≤300 字原文，去重）——因为这些行的事实可能来自付款条件、合同计划章节、交付 / 验收条款、合同金额条款等多处，具体构成见 §4.2 的说明；元素结构见 §4.5。§4.1 / §4.3 的字段**不另附** `evidence`——`payment_terms` / `service_content` / `service_sla` 本身就是整段原文，日期与次数类字段的原文核对由合同系统按页面定位完成。

### 5.2 里程碑标准名（固定枚举，13 个）

`begin` 启动 · `confirm` 环境确认 · `deliver` 交付 · `design` 设计 · `develop` 开发 · `end` 维护期 · `finalaccept` 终验 · `midmaintain` 阶段维护 · `plan` 策划 · `preaccept` 初验 · `require` 需求 · `test` 测试 · `testrun` 试运行

- 合同里的写法千差万别（如"合同签订及预付款""设备到货及安装调…""质保期满尾款"），**靠语义理解**归一，不做词表硬匹配。
- 该清单为**固定值**；合同侧后续若给到完整版本，仅替换清单内容。

### 5.3 计算口径（目标丙，退路乙）

| 字段 | 目标（丙） | 退路（乙，先出结果） |
|---|---|---|
| 回款金额 | 合同额 × 付款条件中的比例 | 仅当比例与合同额在同一处可直接得出时计算 |
| 计划回款时间 | 计划完成时间 + 付款条件中的期限（如"7 个工作日内"） | 只取明确写出的日期 |
| 计划完成时间 | 无合同计划章节时，参考交付/验收的时间节点推算 | 只取明确写出的日期 |
| 申请金额 | 如"按合同金额的 5% 收取"→ 计算 | 只取明确写出的金额 |

**以上均为"基于已抽到的事实"的推导，不是臆造**；推导不出则该字段为 `null`。演示以**先出结果**为准，丙做不动就退乙。

## 6. 异常与兜底

| 情形 | 行为 |
|---|---|
| `mode=prefill` 且模型调用失败 / 超时 / 输出超长 | 返回 `prefill_status: "failed"`，`prefill` 内各字段为 `null`、数组为空数组（结构仍在，不省略键）；HTTP 仍是成功响应，**不抛 5xx** |
| 模型正常返回并解析成功（含"合同里确实没有某字段"） | `prefill_status: "ok"`，未抽到的字段为 `null` / 空数组 |
| `mode=review` | 完全走现有链路与现有异常行为，一行不改 |

> **`prefill_status` 语义（2026-09-16 收窄，取代原"最小覆盖度替代"的说法）**
> 取值 `ok` / `failed`，**只表示本次预填调用成没成**：
> - `ok` = 模型正常返回且 JSON 解析成功
> - `failed` = 调用失败 / 超时 / 输出超长
>
> **它不区分「合同里确实没有」与「我们没抽到」。** 未抽到的字段一律 `null` / 空数组，响应上无法判断属于哪种原因——本方案**不提供字段级覆盖度**（要给每个字段挂抽取状态，属 §2 非目标明确排除的覆盖度抽象，即两阶段的形态）。合同系统侧若需展示"该字段未填"，一律按"未取到"处理，不区分原因。

## 9. 待确认项 / 风险

1. 合同系统实际入参形态（字面量 `\n`）是否稳定一致；若不稳定，归一化需做得更宽容。
2. ~~单次调用输出较长，需实测输出长度，必要时收紧 `evidence` 条数或字数。~~ **已实测（2026-09-16），风险解除**：21 字段合并抽取输出 **1,074 tokens / 2,598 字符**，`max_tokens` 余量充足，**无需收紧** `evidence` 条数或字数。需关注的是**抽取质量**而非长度——`c1` 实测 `contract_info` 9 个字段只填出 **4 个**（缺 `service_start_date` / `service_end_date` / `onsite_service_count` / `inspection_count`），`contract_plan` 三行的 `plan_finish_date` / `plan_payment_date` **全为 `null`**。演示前需与用户确认属"合同确实没写"还是"没抽到"。
3. **D-03 页面按钮标签未对齐**：D-03 前台无截图，JSON key 沿用飞书文档原名；联调时若有出入再小改（用户口径：返回文档列出的全部字段即算交付，前台不关注）。
4. 样例计划 5 份，实到 2 份（本轮先用 `c1` / `c2`）。
5. **两场景传入的 `contract_md` 是否同一份快照**（2026-09-16 新增）：D-02 与 D-03 触发时机不同，若 D-03 触发时正文尚未定稿，同一接口在两个时点会返回不同结果。需与合同系统确认；若确认是同一份，则应考虑合并为一次调用（省一半模型调用），否则接受抽两遍。详见 §3.4。
6. **`chat_template_kwargs` 是后端特有参数**（2026-09-16 第八轮重写）。关思考靠请求体传 `chat_template_kwargs`，这是 vLLM / Qwen 特有字段，**切换后端（如换非 vLLM 网关）会 400**。缓解：配置项 `LTC__LLM__DISABLE_THINKING` 可一键退回现状；§7 的回归测试守住"这个参数确实被传了"。**作用域已收窄**：只有 `contract_review` 的评审链路（含预填）读取该开关，`two_stage` 与 `translate` 都不读它，故后端不兼容时对两者本就无影响。
7. **`translate` 存在思考污染缺陷，本方案不修**（2026-09-16 新增）。`translate` 走 `invoke_model(model, messages)` **无 `response_format`**，输出直接 `content.strip()` 当译文返回（`translate/service.py:68`）；实测 25,782 字符中约 **67% 是英文思考文本**，44.08s。按用户口径该能力由其他同事负责，**本次不得改动其行为**。仅知会责任人：单独关掉思考后实测 11.21s、输出纯译文。

> 已定结论（2026-09-16 更新）
> - `mode` 请求侧新增，取值**仅** `review` / `prefill`；**响应侧不回显**（`mode` 只出现在预填响应里）。
> - `prefill_status` 保留，语义**仅**「本次预填调用成 / 失败」（`ok` / `failed`）；**不区分**"合同里没有"与"没抽到"，**不提供字段级覆盖度**（§6）。日期返回 `YYYY-MM-DD`，展示格式由合同系统自行格式化。
> - `evidence` 为 **`{section, quote}[]`**，按出处各列一条、去重，**每条标注原文的章节 / 条款位置**（§4.2 / §4.4 / §4.5）。
> - 隐患 1 选**乙**：预填用独立响应模型，`ContractReviewData` 零改动。
> - 立 OpenSpec change（`contract-review-mvp-prefill`），取代原先"演示先豁免"的建议。
> - **思考模式必须关闭**（2026-09-16 第七轮修正，**第八轮再次收窄**）：手段为在**合同评审自身的调用点**用 `model.bind(extra_body=...)` 关思考（§4.6）——**第六轮"首选 response_format 压住 thinking"已废**（它只覆盖 JSON 链路，够不到 `translate`）。**生效范围：仅 `contract_review`（`mode=review` + `mode=prefill`，同一处调用点）**；~~`two_stage` prepare~~、`translate` **均零改动**（两条红线，第八轮定案），`app/models/llm.py` 亦零改动。另须配 `response_format`（格式）与 `required_keys`（内容兜底）。
> - **`prefill_scope` 提前进本次范围**（2026-09-16 第七轮）：`all` / `d02` / `d03`，默认 `all`（§3.5）。实测收益 D-03 场景 7.42s → 3.01s。
