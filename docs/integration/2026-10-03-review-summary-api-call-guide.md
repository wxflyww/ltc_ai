# 评审智能总结（review-summary）· 接口调用文档

> 状态：对外调用文档（2026-10-03），供合同系统侧实现接口调用。契约唯一事实源为
> `docs/integration/2026-10-02-review-summary-design.md`（本文是其对外子集，冲突以设计文档为准）；
> 接口路径、字段与错误码均已按已实现代码核对。实测耗时 / token 等数据待真实端点联调后回填，届时升级为正式版。

## 1. 这是什么

合同审批详情页的「评审智能总结」面板接口。审批人打开页面时，合同系统传入评审环节结构化数据，
接口返回**整包面板 JSON**，合同系统按区块渲染，零业务理解。

| 方 | 职责 |
|---|---|
| 合同系统 | 数据的**生产者与筛选者**：传什么（只传高风险项、只传当前有效轮意见）、数据正确性与一致性 |
| AI 接口 | 面板的**组织者、写作者与兜底者**：面板结构、AI 文本（总述的概览句与主题句、意见摘要）、总述拼接与防幻觉校验、空态降级 |

面板三部分：**一、评审总结**（一段总述，由服务端把四部分**拼接**而成——① 合同要素句、② 结论分布句（这两句由服务端按请求体确定性装配，不经模型）③ AI 概览句（overall，可为空）④ AI 的**主题归并句**（每主题一句，禁止把单条意见的细项顿号罗列；主题句后括号里的**节点名由服务端按该主题的 `opinion_refs` 反查得到**，不是模型写的）。目标 ≤200 字，超红线 300 字按整句裁尾；覆盖所有写了实质内容的意见，含投「通过」者）；**二、重点关注**（提级原因 + 高风险项 + 处置参考，全部原文照搬）；**三、各节点意见详情**（骨架照搬 + 每条 AI 摘要）。

## 2. 接口定义

| 项 | 值 |
|---|---|
| 方法 / 路径 | `POST /api/v1/review-summary` |
| Content-Type | `application/json` |
| 鉴权 | 请求头 `X-API-Key: <key>` 或 `Authorization: Bearer <key>`（与现有合同评审接口同一套 key） |
| 客户端超时 | 建议 **≥ 120 秒**（新生成通常 3–10s，缓存命中 <100ms，留慢端点余量） |
| 追踪 | 响应头/响应体携带 `traceId`（可用请求头 `X-Trace-Id` 传入以串联日志） |
| 调用方式 | 页面**异步加载**该面板，不要同步阻塞审批操作 |

同一输入重复调用命中服务端缓存、直接返回相同结果；评审数据任何变化会自动失效重新生成，**无需合同系统做任何缓存通知**。

## 3. 请求体：四组数据

通用约定：

1. **缺值给空、不省键**：可选字段没有就传 `null`（对象/字符串）或 `[]`（数组），不要整个键消失后再猜语义。
2. **所有文本原样传递**：接口只引用不加工，不要预先摘要、翻译或格式化。
3. **数字按系统内展示的原文传字符串**："¥126 万元" 就是 `"¥126 万元"`，`27.7%` 就是 `"27.7%"`。接口及 AI 对数字零换算、零改写，展示什么就传什么。
4. **数组顺序即展示顺序**：接口不重排、不过滤。
5. 未列出的新增可选字段不会导致请求失败（向后兼容，如后续 CRM 客户字段）。

### 3.1 `contract_meta` 合同要素（整组可选）

| 字段 | 必填 | 示例 | 说明 |
|---|---|---|---|
| `contract_type` | 否 | `"硬件集成"` | |
| `contract_amount` | 否 | `"¥126 万元"` | 展示原文字符串 |
| `gross_margin` | 否 | `"27.7%"` | 多口径毛利率可后续新增字段并列传入 |

### 3.2 `route_reason` 提级原因（整组可选）

```json
"route_reason": { "text": "合同总额超过 ¥100 万，按权限规则触发副总经理终审节点" }
```

`text` 必须是合同系统侧**已生成好的人话原文**（审批人填写或规则引擎产出），接口照搬不润色。
**传入 `route_reason` 时 `text` 不能为空串**（空串按非法请求拒绝）；没有提级就整组缺省或传 `null`。

### 3.3 `risk_register[]` 高风险项（只传高风险，12 字段全可选）

| 字段 | 示例 | 说明 |
|---|---|---|
| `risk_id` | `"RSK-001"` | 风险编号 |
| `title` | `"付款风险"` | |
| `level` | `"高"` | 原样展示，接口不做枚举映射 |
| `source` | `"财经评审"` | 来源 |
| `description` | `"客户预付款比例 15%，低于我司标准 30%"` | |
| `standard_clause` | `"《合同签订标准》第 3.2 条：预付款比例不低于 30%"` | |
| `potential_impact` | `"项目前期资金压力较大，资金占用 96 天，可能影响交付进度"` | |
| `measure_type` | `"缓解"` | 措施类别 |
| `measure_desc` | `"要求客户签署补充付款承诺函，并将首付款拆分为两期"` | 展示为「处置参考」，引用原文 |
| `decision_type` | `"接受风险"` | 中文文本原样展示 |
| `decision_note` | `"考虑客户战略价值，同意让步"` | |
| `decision_by` | `"陈总"` | |

识别部门/识别人/识别日期/计划完成/完成状态等执行跟踪字段**不要传入**（不进审批视图）。

### 3.4 `opinions[]` 评审意见全集（必填键，可为 `[]`）

| 字段 | 必填 | 说明 |
|---|---|---|
| `node_name` | 是 | 评审节点名 |
| `approver_name` | 是 | 评审人姓名 |
| `role` | 是 | 角色，自由文本（同一角色保持称谓稳定） |
| `action` | 是 | **原样照搬**：非空字符串，传过来是啥就是啥——接口不枚举、不翻译、不映射，响应原样回显。建议直接传贵方展示原文（"通过 / 有条件通过 / 不通过"），兜底闸触发词见本节末说明 |
| `comment` | 是 | 综合评审意见**原文**，无文字给空串（该条只出骨架、不生成摘要、不算降级）；超过约 2000 字请截断并在末尾标注「（原文有截断）」 |
| `submitted_at` | 建议 | ISO 8601 带时区，如 `"2026-09-25T14:32:00+08:00"` |

`action` 用词约定（5.4 真实联调后契约转向：废除英文枚举与翻译层，中文原值直传）：

| 合同系统展示 | 传入值 |
|---|---|
| 通过 / 认可 | `通过` |
| 有条件通过 | `有条件通过` |
| 不通过 | `不通过` |

约定：**一人多角色**拆成多条记录；评审未完成时传 `[]`（合法空态，不是错误）；
**回退重审**场景接口不做新旧甄别——推荐只传当前有效轮，或全量传入并在 `comment` 或后续扩展字段带上轮次标记（口径请先定，联调时对齐）。

## 5. 响应

### 5.1 响应壳

```json
{ "code": 0, "message": "ok", "data": { ... }, "traceId": "9f3c2a1e7b4d4e8f", "duration_seconds": 4.38 }
```

`code=0` 即成功；`data` 为整包面板，四个键恒在。

### 5.2 `data` 结构

```text
data
├── review_summary                 一、评审总结
│   ├── text                       拼接后的总述全文：①合同要素句。②结论分布句。③overall。④主题1（节点名…）；主题2（节点名…）。
│   │                              ①② 由服务端按请求体确定性装配；③④ 来自 AI。③④ 未通过校验时整段改为服务端中性兜底稿，
│   │                              仅极端无素材时为 null（面板不会拿到空白总述）
│   ├── source_refs[]              溯源引用（服务端汇总：要素字段 + `opinions` 聚合 + 各主题采信的 refs；前端可忽略）
│   └── themes[]                   主题结构（与 text 里的主题片段对应；兜底稿/无有字意见时为 `[]`，不省键）
│       ├── text                   主题句原文（AI 写的是什么就是什么；拼接时其自带句末标点被收到整段末尾，主题之间用"；"连接）
│       └── opinion_refs[]         该主题采信的意见（`opinions[i]` 路径；前端可忽略）
├── key_concerns[]                 二、重点关注（有序，数组序=展示序=编号序）
│   ├── type                       "escalation" 提级原因 | "risk" 风险项
│   ├── …escalation: text          提级原因原文
│   └── …risk: 传入的 risk_register 字段照搬 + measure { measure_type, measure_desc }
├── opinion_details[]              三、各节点意见详情（传入序）
│   ├── node_name / approver_name / role / action    骨架照搬
│   ├── summary                    AI 摘要；被丢弃时该条为 null
│   └── source_ref                 指向 opinions[i]（前端可忽略）
└── degraded_sections[]            降级标记清单，正常请求为 []
```

### 5.4 渲染要点

- `key_concerns` 风险块中未传入的字段会以值为 `null` 的键出现（如未传 `decision_type` 则输出 `"decision_type": null`，`measure` 块同理）——与入参"缺值给空不省键"对称；前端对 `null` 字段不渲染对应行即可，**无占位文案**。
- 处置参考永远来自清单措施原文（`measure` 块），AI 零参与；接口不输出任何"建议通过/建议驳回"类决策建议。
- `source_refs` / `source_ref` / `themes` 为溯源与结构元数据，前端渲染可整体忽略（总述只需渲染 `text` 这一整段），排查问题时可提供给 AI 侧。
- 总述里的节点名（括号内）由服务端按每个主题的 `opinion_refs` 反查 `opinions[i].node_name` 得到，**不是模型写的**：合同系统无需校对模型有没有点名、点错名。
- **同一条意见被模型拆成多条主题时，服务端已把它们合并成一条**（`opinion_refs` 完全相同的主题按首次出现位置拼成一句，句子逐字保留，见 change design.md D17）。因此 `themes[]` 与 `text` 里的主题片段本就一致、**不含重复引用组**：前端不要再自行去重、也不要假设"一条意见只会出现在一条主题里"之外还要补合并逻辑。合并后仍可能超过 4 条（服务端只观测、不裁条数），渲染请按数组实际长度排布。

## 6. `degraded_sections` 与前端处理建议

正常请求为空数组。出现的标记与含义：

| 标记 | 含义 | 前端建议 |
|---|---|---|
| `key_concerns` | 无提级原因且无高风险项 | 重点关注区显示「无重点关注事项」 |
| `opinion_details` | `opinions=[]`（评审未完成） | 意见详情区显示「评审意见尚未提交」 |
| `review_summary.opinions` | 没有任何写过实质内容的意见（`opinions=[]` 或全部 `comment` 为空）：总述只有 ①合同要素 + ②结论分布两句（服务端装配，不触模型），`themes=[]` | 正常渲染返回的 `text` 即可 |
| `review_summary.fallback` | 总述的 **AI 稿**未通过服务端校验被整块弃用，`text` 改由**服务端中性兜底稿**填充（内容只有合同要素原文 + 意见条数分布 + "哪些节点写了字"，无评价性修饰、无诉求概括、**不提风险项**——风险由「重点关注」区单点承载）| **照常渲染 `text`**，前端无需特殊处理；如需排查可把该标记与 `source_refs` 一并提供给 AI 侧 |
| `review_summary.model` | 总述 AI 稿弃用后**连兜底素材都没有**（请求除提级原因等装配区已展示内容外无可引用事实），`text=null` | 隐藏总述行或显示占位文案，**不影响其余区块渲染** |
| `review_summary.incomplete` | **覆盖不全，但内容仍是 AI 稿**：AI 的某几条主题句未通过结构校验（采信的意见引用不存在/指向空 `comment`、或句中点了本主题 `opinion_refs` 未背书的节点名），且定向重试一次后仍不改。服务端**整条丢弃该主题**（不删名、不改句、不替换成真名），其余合法主题照常保留并照常拼接（见 change design.md D16/D16.1） | **照常渲染 `text`**；该主题的内容在 `opinion_details` 里仍逐条原文可查，面板不丢信息，无需提示错误 |
| `opinion_details.model` | **模型漏交某条意见的 `index`**（未按"逐条对应"覆盖输入），该条 `summary=null`、其余条正常。`comment` 为空、或近空（"同意。"）而模型按 prompt 契约显式返回 `null` 的，属契约内正确输出：**不计丢弃、不打本标记、不旁路缓存**（s06 后修正，见 change design.md D14） | 该条回落显示 `comment` 原文截断，或仅显示骨架（角色·姓名·动作）；`summary=null` 且无本标记时按"该节点没写实质内容"渲染即可 |

说明：数字抽验的"输入原文"除请求体字段外，还包含服务端为模型统计的派生事实（如意见条数分布"共 11 条：通过 9 条"），
模型照抄这类服务端给的数字不算编造（口径见 change design.md D9）。
总述的结构校验（2026-10-09 契约调整，change design.md D16/D16.1）：模型不再自己写"整段总述 + 引用清单"，
而是交 `overall`（一句态势）与 `themes[]`（主题句 + 每主题的 `opinion_refs`），①② 两句与节点名一律由服务端装配。
校验因此落在**指针层**而不是文字层：某条主题引用的意见不存在或越界 → 逐条剔除该引用，剩下 ≥1 条合法引用就照常采信；
剔除后一条不剩、或引用指向空 `comment`、或句中点了本主题 refs 未背书的节点名 → 定向重试一次；重试仍不改 → **整条丢弃该主题**
（打 `.incomplete`）。文字层不再做归属比对，因为节点名互为子串（如"行业商务评审"⊂"二级行业商务评审"）时文字比对不可靠。
`overall` 单独违规只丢这一句，不打标记、不触发重试。模型**漏纳了某条有字意见**属覆盖不足，服务端只记录观测、不判违规
（主题上限 4 条 × 每条 3 refs，面对上百条意见时不可能逐条收全，见 D16.1-R1/D16.2-R5）。
只有整段总述被判定不可信时才弃用 AI 稿，且弃用时由服务端中性兜底稿顶上——**面板不会拿到空白总述**
（宁可给一句不带任何评价的事实句，也不让最核心的区块缺席）。
兜底稿的每个数字、每条引用都出自请求体或服务端自算统计，天然通过同样的校验，不会把"防幻觉"换成"造幻觉"。
这类请求整体仍是 `code=0` 成功，装配区内容不受影响；带 `.model`、`.fallback` 或 `.incomplete` 标记的响应不写缓存
（同样的输入下次请求会重新给模型生成机会）。
**总述长度**（口径见 change design.md D13/D16.1-I5）：200 字是 prompt 目标值，服务端红线 300 字，红线量在**拼接后的全文**上；
超长时服务端**按整句从尾部裁**（一条主题一句，从最后一条起削）到红线内后照常返回，**不整段弃用、不打 `.fallback`/`.model`、
照常写缓存**，前端拿到的永远是完整句子（不留半句）。被裁掉的尾部主题在 `opinion_details` 里仍逐条原文可查，面板不丢信息；
极端情况下裁到只剩 ①② 两句、连一句 AI 成稿都没保住，才改用兜底稿。

**关于"存在不通过意见时禁止正面定性"这道兜底闸（铁律 5）的用词约定**：该闸的触发条件是服务端对
`action` 值做逐字比对，当前词表仅一个值——**`不通过`**。词表之外的结论用词（如"驳回""退回"）不会报错、
不会误伤，面板与总述照常生成，只是这道闸对这类单子**静默不生效**（fail-open 设计：兜底闸宁可漏放，
绝不错杀）。闸命中时作用在**主题句层**：含正面定性的那一条主题句被整条丢弃（不触发重试，因为重试只会让模型
换个说法再写一遍正面定性），其余中性主题照常保留。因此：① 请合同系统保持"通过 / 有条件通过 / 不通过"三个约定用词；② 将来若新增负面类
结论词，请**告知 AI 侧在词表中增补该词**（一行常量 + 一个用例即可生效），而不是默默传新词等闸自动
识别——闸不会自己学会新词。

**关于"替未填写意见的节点断言立场"这道兜底闸（铁律 5 的第二档，口径见 change design.md D16.4）**：该闸与
`action` 分布**无关、常驻生效**。服务端把主题句与 `overall` 里的正面定性短语（无异议、一致认可、整体认可、
一致通过、充分肯定等）逐条拿去**所有 `opinions[].comment` 原文**比对，找不到逐字出处的即判内容违规：
主题整条丢弃、`overall` 只丢这一句，两者都**不触发重试**、不新增错误码、装配区内容不受影响。
空 `comment` 只代表该节点**没写字**，服务端不会把它转述成"无异议"，合法写法只有"其余节点未填写意见"。
调用方需要注意的是：**如果某位评审人确实想表达无异议，请把这几个字写进 `comment`**——原文有出处的转述
永远安全，反之一个没写字的节点不会被 AI 替他表态（真实样本里空意见常占到半数，这道闸的默认收益就是
不让"沉默"被读成"同意"）。判据只认 `comment`：`risk_register`/`contract_meta` 文本里恰好出现这些词，
不构成一句整体总结的出处。

## 7. 错误码

| code | HTTP | 含义 | 前端处理 |
|---|---|---|---|
| `0` | 200 | 成功（含部分 AI 字段降级的成功） | 正常渲染 |
| `10001` | 422 | 参数校验失败（`data` 为 `null`、`message` 为固定文案，**不返回逐字段错误明细**） | 视为调用方 bug：按 §3 字段表自查请求体；必要时凭 `traceId` 找 AI 侧查日志定位 |
| `10002` | 401 | 鉴权失败（key 缺失或不合法） | 检查 API Key |
| `20001` | 500 | 模型调用失败（重试耗尽） | 面板整体降级「智能总结暂不可用」或隐藏，**不阻塞审批** |
| `20002` | 504 | 模型调用超时 | 同上 |
| `20003` | 500（输入超长场景为 400） | 模型输出格式异常 | 同上 |

## 8. 缓存与性能

- 耗时预估：缓存命中 < 100ms；新生成约 3–10s（随意见条数与文本长度增长）。**正式版将回填真实端点实测值。**
- 一次未命中缓存的请求发几次模型调用：常规 **2 次**（总述主题稿 1 次 + 全部有字意见的摘要批量 1 次）；没有任何有字意见时**0 次**（总述只由服务端装配 ①② 两句，摘要没有对象）。仅当总述主题稿未通过**结构**校验（输出形状失守 / 某主题采信引用剔到剩 0 / 引用指向空 `comment` / 句中点了本主题未背书的节点名）时追加**至多 1 次**定向重试（上限 3 次，见 §6 的 `review_summary.incomplete`）。重试不改变响应结构，调用方无需处理。
- 超时口径：客户端 120s 是余量上限而非预期耗时；服务端单次模型调用超时现配置为 **30 秒**（既有全局配置，非本接口独立键），超时返回 `20002`，前端按整体降级处理即可。
- 一期缓存为服务进程内实现：服务重启、多副本部署时同一输入可能在个别副本上重新生成一次——调用方感知仅是耗时差异，结果始终由输入决定。
- 本接口与合同评审、预填共用同一 vLLM 实例；上线初期的并发节奏建议联调时同步沟通。

## 9. 调用方准备清单（合同系统侧）

1. 环境与凭据：AI 服务地址、API Key（找 AI 侧对接人领取）。
2. `action` 用词：按 §3.4 表确认贵方展示词（中文原值直传，不再映射英文枚举），有异议联调首日对齐。
3. 样例数据（建议至少 4 组，直接给原始导出数据即可，AI 侧负责整理成请求体）：
   - 典型全集：提级 + ≥2 条高风险 + ≥3 条意见（含"有条件通过"）；
   - 含"不通过"意见的一组（验证总述中性化表现）；
   - `opinions=[]` 的一组（评审未完成态）；
   - 数字密集的一组（金额/比例/天数按展示原文）。
4. 回退重审传参口径确认（§3.4）。
