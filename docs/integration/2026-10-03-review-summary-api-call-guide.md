# 评审智能总结（review-summary）· 接口调用文档

> 版本 v1.0。供合同系统侧实现接口调用：接口路径、字段、错误码与降级语义均按已实现代码核对，
> 耗时与 token 为部门真实模型端点实测（§8）。**本文是唯一对外件，单独即可用，不需要配合其他文档阅读。**
> AI 侧内部另有契约事实源；两者若有出入，由 AI 侧裁决并同步修订本文，有疑问按 `traceId` 联查。

## 1. 这是什么

合同审批详情页的「评审智能总结」面板接口。审批人打开页面时，合同系统传入评审环节结构化数据，
接口返回**整包面板 JSON**，合同系统按区块渲染，零业务理解。

| 方 | 职责 |
|---|---|
| 合同系统 | 数据的**生产者与筛选者**：传什么（只传高风险项、只传当前有效轮意见）、数据正确性与一致性 |
| AI 接口 | 面板的**组织者、写作者与兜底者**：面板结构、AI 文本（总述的概览句与主题句、意见摘要）、总述拼接与防幻觉校验、空态降级 |

面板三部分：**一、评审总结**（一段总述，由服务端把四部分**拼接**而成——① 合同要素句、② 结论分布句（这两句由服务端按请求体确定性装配，不经模型；存在 `comment` 为空的意见时，② 句尾部由服务端写明「其中 N 条填写了意见」；两句都可能缺席：未传 `contract_meta` 时没有 ①，`opinions=[]` 时没有 ②）③ AI 概览句（overall，可为空）④ AI 的**主题归并句**（每主题一句，禁止把单条意见的细项顿号罗列；主题句后括号里的**节点名由服务端按该主题的 `opinion_refs` 反查得到**，不是模型写的）。目标 ≤200 字，超红线 300 字按整句裁尾。**总述是"关键性"视图，不是全集视图**：主题归并的目标形态是 4 条以内、每条引 1–3 条意见（实际条数由当次生成决定，服务端不裁条数），写了实质内容但没被总述提到的意见（含投「通过」者）**不代表信息丢失**——它的原文与 AI 摘要在第三区逐条可查）；**二、重点关注**（提级原因 + 高风险项 + 处置参考，全部原文照搬）；**三、各节点意见详情**（骨架照搬 + 每条 AI 摘要）。

## 2. 接口定义

| 项 | 值 |
|---|---|
| 方法 / 路径 | `POST /api/v1/review-summary` |
| Content-Type | `application/json` |
| 鉴权 | 请求头 `X-API-Key: <key>` 或 `Authorization: Bearer <key>`（与现有合同评审接口同一套 key） |
| 客户端超时 | 建议 **≥ 120 秒**（新生成实测 2.86–12.58s，缓存命中 0.005–0.006s，见 §8，留慢端点余量） |
| 追踪 | 响应头/响应体携带 `traceId`（可用请求头 `X-Trace-Id` 传入以串联日志） |
| 调用方式 | 页面**异步加载**该面板，不要同步阻塞审批操作；**一次打开面板调一次**——不要轮询，超时后也不要自动重试（重试= 再烧一次模型调用；同一输入的结果完全由输入决定，重试不会变好。只有 §7 的 `20001`/`20002`/`20003` 按整体降级处理） |

同一输入重复调用命中服务端缓存、直接返回相同结果；评审数据任何变化会自动失效重新生成，**无需合同系统做任何缓存通知**。

## 3. 请求体：四组数据

通用约定：

1. **缺值给空、不省键**：可选字段没有就传 `null`（对象/字符串）或 `[]`（数组），不要整个键消失后再猜语义。
2. **所有文本原样传递**：接口只引用不加工，不要预先摘要、翻译或格式化。
3. **数字按系统内展示的原文传字符串**："¥126 万元" 就是 `"¥126 万元"`，`27.7%` 就是 `"27.7%"`。接口及 AI 对数字零换算、零改写，展示什么就传什么。
4. **数组顺序即展示顺序**：接口不重排、不过滤。
5. **`comment` 为空的记录照常传**：不要在取数层过滤掉"只点了结论、没写字"的记录。缺席条数由服务端在总述里统一陈述（见 §6 末段），传之前先过滤会让那个数字失真。评审人真要表达无异议，请把"无异议"写进 `comment`——原文有出处的转述永远安全，没写字的节点不会被 AI 替他表态。
6. 未列出的新增可选字段不会导致请求失败（向后兼容，如后续 CRM 客户字段）。

### 3.1 `contract_meta` 合同要素（整组可选）

| 字段 | 必填 | 示例 | 说明 |
|---|---|---|---|
| `contract_type` | 否 | `"硬件集成"` | |
| `contract_amount` | 否 | `"¥126 万元"` | 展示原文字符串 |
| `gross_margin` | 否 | `"27.7%"` | 多口径毛利率可后续新增字段并列传入 |

### 3.2 `route_reason` 提级原因（整组可选）

```json
"route_reason": { "text": "合同总额超过 ¥100 万，按权限规则触发副总经理终审节点" }
```

`text` 必须是合同系统侧**已生成好的人话原文**（审批人填写或规则引擎产出），接口照搬不润色。
**传入 `route_reason` 时 `text` 不能为空串**（空串按非法请求拒绝）；没有提级就整组缺省或传 `null`。

### 3.3 `risk_register[]` 高风险项（只传高风险，12 字段全可选）

| 字段 | 示例 | 说明 |
|---|---|---|
| `risk_id` | `"RSK-001"` | 风险编号 |
| `title` | `"付款风险"` | |
| `level` | `"高"` | 原样展示，接口不做枚举映射 |
| `source` | `"财经评审"` | 来源 |
| `description` | `"客户预付款比例 15%，低于我司标准 30%"` | |
| `standard_clause` | `"《合同签订标准》第 3.2 条：预付款比例不低于 30%"` | |
| `potential_impact` | `"项目前期资金压力较大，资金占用 96 天，可能影响交付进度"` | |
| `measure_type` | `"缓解"` | 措施类别 |
| `measure_desc` | `"要求客户签署补充付款承诺函，并将首付款拆分为两期"` | 展示为「处置参考」，引用原文 |
| `decision_type` | `"接受风险"` | 中文文本原样展示 |
| `decision_note` | `"考虑客户战略价值，同意让步"` | |
| `decision_by` | `"陈总"` | |

识别部门/识别人/识别日期/计划完成/完成状态等执行跟踪字段**不要传入**（不进审批视图）。

### 3.4 `opinions[]` 评审意见全集（必填键，可为 `[]`）

| 字段 | 必填 | 说明 |
|---|---|---|
| `node_name` | 是 | 评审节点名 |
| `approver_name` | 是 | 评审人姓名 |
| `role` | 是 | 角色，自由文本（同一角色保持称谓稳定） |
| `action` | 是 | **原样照搬**：非空字符串，传过来是啥就是啥——接口不枚举、不翻译、不映射，响应原样回显。直接传合同系统审批界面上的展示原文（"通过 / 有条件通过 / 不通过"），兜底闸触发词见本节末说明 |
| `comment` | 是 | 综合评审意见**原文**，无文字给空串（该条只出骨架、`summary` 为 `null`、不算降级）。接口不做长度校验、也不会自动截断，超长原文会整段进模型（成本随输入长度近线性，见 §8）：超过约 2000 字请截断并在末尾标注「（原文有截断）」 |
| `submitted_at` | 建议 | ISO 8601 带时区，如 `"2026-09-25T14:32:00+08:00"` |

`action` 用词约定（接口不做枚举、不翻译、不映射，直接传审批界面上的展示原文；下表同时是**服务端护栏的词表**，逐字生效）：

| 合同系统展示 | 传入值 |
|---|---|
| 通过 / 认可 | `通过` |
| 有条件通过 | `有条件通过` |
| 不通过 | `不通过` |

约定：**一人多角色**拆成多条记录；评审未完成时传 `[]`（合法空态，不是错误）；
**回退重审**场景接口不做新旧甄别——推荐只传当前有效轮，或全量传入并在 `comment` 或后续扩展字段带上轮次标记（口径请先定，联调时对齐）。

## 5. 响应

### 5.1 响应壳

```json
{ "code": 0, "message": "ok", "data": { ... }, "traceId": "9f3c2a1e7b4d4e8f", "duration_seconds": 4.38 }
```

`code=0` 即成功；`data` 为整包面板，四个键恒在。

### 5.2 `data` 结构

```text
data
├── review_summary                 一、评审总结
│   ├── text                       拼接后的总述全文：①合同要素句。②结论分布句。③overall。④主题1（节点名…）；主题2（节点名…）。
│   │                              ①② 由服务端按请求体确定性装配；③④ 来自 AI。③④ 未通过校验时整段改为服务端中性兜底稿，
│   │                              仅极端无素材时为 null（面板不会拿到空白总述）
│   ├── source_refs[]              溯源引用（服务端汇总：要素字段 + `opinions` 聚合 + 各主题采信的 refs；前端可忽略）
│   └── themes[]                   主题结构（与 text 里的主题片段一一对应；兜底稿/无有字意见/被裁尾的主题不出现在本数组，不省键）
│       ├── text                   主题句原文（AI 写的是什么就是什么，**不含服务端渲染的节点名后缀**；拼接时其自带句末标点被收到整段末尾，主题之间用"；"连接）
│       └── opinion_refs[]         该主题采信的意见（`opinions[i]` 路径；需要展示"这句归谁"时只读这里，前端可忽略）
├── key_concerns[]                 二、重点关注（有序，数组序=展示序=编号序）
│   ├── type                       "escalation" 提级原因 | "risk" 风险项
│   ├── …escalation: text          提级原因原文
│   └── …risk: 传入的 risk_register 字段照搬 + measure { measure_type, measure_desc }
├── opinion_details[]              三、各节点意见详情（传入序）
│   ├── node_name / approver_name / role / action    骨架照搬
│   ├── summary                    AI 摘要；被丢弃时该条为 null
│   └── source_ref                 指向 opinions[i]（前端可忽略）
└── degraded_sections[]            降级标记清单，正常请求为 []
```

### 5.4 渲染要点

- `key_concerns` 风险块中未传入的字段会以值为 `null` 的键出现（如未传 `decision_type` 则输出 `"decision_type": null`，`measure` 块同理）——与入参"缺值给空不省键"对称；前端对 `null` 字段不渲染对应行即可，**无占位文案**。
- 处置参考永远来自清单措施原文（`measure` 块），AI 零参与；接口不输出任何"建议通过/建议驳回"类决策建议。
- `source_refs` / `source_ref` / `themes` 为溯源与结构元数据，前端渲染可整体忽略（总述只需渲染 `text` 这一整段），排查问题时可提供给 AI 侧。
- **需要"这句归谁"时只读 `themes[].opinion_refs`，不要对 `text` 做正则抽取**：括号里的节点名由服务端反查生成，而主题句自己已经逐字提到某个节点名时，服务端**不会再重复输出那个后缀**（例：主题句写成"税务评审要求按标准名称开票"，括号里就没有"税务评审"）。抽文本必漏，抽 `opinion_refs` 不会。只渲染整段 `text` 的话本条不适用。
- 总述里的节点名（括号内）由服务端按每个主题的 `opinion_refs` 反查 `opinions[i].node_name` 得到，**不是模型写的**：合同系统无需校对模型有没有点名、点错名。
- **同一条意见被模型拆成多条主题时，服务端已把它们合并成一条**（`opinion_refs` 完全相同的主题按首次出现位置拼成一句，句子逐字保留）。因此 `themes[]` 与 `text` 里的主题片段本就一致、**不含重复引用组**：前端不要再自行去重、也不要假设"一条意见只会出现在一条主题里"之外还要补合并逻辑。合并后仍可能超过 4 条（服务端只观测、不裁条数），渲染请按数组实际长度排布。

## 6. `degraded_sections` 与前端处理建议

正常请求为空数组；**标记非空不代表请求失败**（`code=0` 仍是成功，见 §7），不要把"有标记"当成重试条件。出现的标记与含义：

| 标记 | 含义 | 前端建议 |
|---|---|---|
| `key_concerns` | 无提级原因且无高风险项 | 重点关注区显示「无重点关注事项」 |
| `opinion_details` | `opinions=[]`（评审未完成） | 意见详情区显示「评审意见尚未提交」 |
| `review_summary.opinions` | **只在 `opinions=[]`（评审未完成）时出现**：总述最多只有 ①合同要素句（未传 `contract_meta` 时为 `null`），`themes=[]`，零模型调用。另有**相似但不带本标记**的一种：`opinions` 非空而所有 `comment` 都为空时，总述同样只由 ①② 两句构成、零模型调用（② 尾部写明「其中 0 条填写了意见」），`degraded_sections` 里可能只有 `key_concerns` | **照常渲染返回的 `text`**；两者都是输入决定的合法空态、都可缓存，无需报错或重试 |
| `review_summary.fallback` | 总述的 **AI 稿**未通过服务端校验被整块弃用，`text` 改由**服务端中性兜底稿**填充（内容只有合同要素原文 + 意见条数分布 + "哪些节点写了字"，无评价性修饰、无诉求概括、**不提风险项**——风险由「重点关注」区单点承载）| **照常渲染 `text`**，前端无需特殊处理；如需排查可把该标记与 `source_refs` 一并提供给 AI 侧 |
| `review_summary.model` | 总述 AI 稿弃用后**连兜底素材都没有**（请求除提级原因等装配区已展示内容外无可引用事实），`text=null`。注：只要 `opinions` 非空，②结论分布句本身就是兜底素材，所以本标记在真实链路上极少出现（真实合同数据实测 **0 次**），前端保留"隐藏总述行"的处理即可，不必为它单独设计文案；`text=null` 的另一条来源是上面 `opinions=[]` 且未传 `contract_meta` 的空态，两者渲染动作相同 | 隐藏总述行或显示占位文案，**不影响其余区块渲染** |
| `review_summary.incomplete` | **覆盖不全，但内容仍是 AI 稿**：AI 的某几条主题句未通过结构校验（采信的意见引用不存在/指向空 `comment`、或句中点了本主题 `opinion_refs` 未背书的节点名），且定向重试一次后仍不改。服务端**整条丢弃该主题**（不删名、不改句、不替换成真名），其余合法主题照常保留并照常拼接 | **照常渲染 `text`**；该主题的内容在 `opinion_details` 里仍逐条原文可查，面板不丢信息，无需提示错误 |
| `opinion_details.model` | **模型漏交某条意见的 `index`**（未按"逐条对应"覆盖输入），该条 `summary=null`、其余条正常。`comment` 为空、或近空（"同意。"）而模型按 prompt 契约显式返回 `null` 的，属契约内正确输出：**不计丢弃、不打本标记、不旁路缓存** | 该条回落显示 `comment` 原文截断，或仅显示骨架（角色·姓名·动作）；`summary=null` 且无本标记时按"该节点没写实质内容"渲染即可 |

说明：数字抽验的"输入原文"除请求体字段外，还包含服务端为模型统计的派生事实（如意见条数分布"共 11 条：通过 9 条"），
模型照抄这类服务端给的数字不算编造。
总述的结构校验：模型不写"整段总述 + 引用清单"，
而是交 `overall`（一句态势）与 `themes[]`（主题句 + 每主题的 `opinion_refs`），①② 两句与节点名一律由服务端装配。
校验因此落在**指针层**而不是文字层：某条主题引用的意见不存在或越界 → 逐条剔除该引用，剩下 ≥1 条合法引用就照常采信；
剔除后一条不剩、或引用指向空 `comment`、或句中点了本主题 refs 未背书的节点名 → 定向重试一次；重试仍不改 → **整条丢弃该主题**
（打 `.incomplete`）。文字层不再做归属比对，因为节点名互为子串（如"行业商务评审"⊂"二级行业商务评审"）时文字比对不可靠。
`overall` 单独违规只丢这一句，不打标记、不触发重试。模型**漏纳了某条有字意见**属覆盖不足，服务端只记录观测、不判违规
（主题上限 4 条 × 每条 3 refs，面对上百条意见时不可能逐条收全）。
只有整段总述被判定不可信时才弃用 AI 稿，且弃用时由服务端中性兜底稿顶上——**面板不会拿到空白总述**
（宁可给一句不带任何评价的事实句，也不让最核心的区块缺席）。
兜底稿的每个数字、每条引用都出自请求体或服务端自算统计，天然通过同样的校验，不会把"防幻觉"换成"造幻觉"。
这类请求整体仍是 `code=0` 成功，装配区内容不受影响；带 `.model`、`.fallback` 或 `.incomplete` 标记的响应不写缓存
（同样的输入下次请求会重新给模型生成机会）。
**总述长度**：200 字是 prompt 目标值，服务端红线 300 字，红线量在**拼接后的全文**上；
超长时服务端**按整句从尾部裁**（一条主题一句，从最后一条起削）到红线内后照常返回，**不整段弃用、不打 `.fallback`/`.model`、
照常写缓存**，前端拿到的永远是完整句子（不留半句）。被裁掉的尾部主题在 `opinion_details` 里仍逐条原文可查，面板不丢信息；
极端情况下裁到只剩 ①② 两句、连一句 AI 成稿都没保住，才改用兜底稿。

**关于"存在不通过意见时禁止正面定性"这道兜底闸（铁律 5）的用词约定**：该闸的触发条件是服务端对
`action` 值做逐字比对，当前词表仅一个值——**`不通过`**。词表之外的结论用词（如"驳回""退回"）不会报错、
不会误伤，面板与总述照常生成，只是这道闸对这类单子**静默不生效**（fail-open 设计：兜底闸宁可漏放，
绝不错杀）。闸命中时作用在**主题句层**：含正面定性的那一条主题句被整条丢弃（不触发重试，因为重试只会让模型
换个说法再写一遍正面定性），其余中性主题照常保留。因此：① 请合同系统保持"通过 / 有条件通过 / 不通过"三个约定用词；② 将来若新增负面类
结论词，请**告知 AI 侧在词表中增补该词**（一行常量 + 一个用例即可生效），而不是默默传新词等闸自动
识别——闸不会自己学会新词。

**关于"替未填写意见的节点断言立场"这道兜底闸（铁律 5 的第二档）**：该闸与
`action` 分布**无关、常驻生效**。服务端把主题句与 `overall` 里的正面定性短语（无异议、一致认可、整体认可、
一致通过、充分肯定等）逐条拿去**所有 `opinions[].comment` 原文**比对，找不到逐字出处的即判内容违规：
主题整条丢弃、`overall` 只丢这一句，两者都**不触发重试**、不新增错误码、装配区内容不受影响。
空 `comment` 只代表该节点**没写字**，服务端不会把它转述成"无异议"，合法写法只有"其余节点未填写意见"。
调用方需要注意的是：**如果某位评审人确实想表达无异议，请把这几个字写进 `comment`**——原文有出处的转述
永远安全，反之一个没写字的节点不会被 AI 替他表态（真实样本里空意见常占到半数，这道闸的默认收益就是
不让"沉默"被读成"同意"）。判据只认 `comment`：`risk_register`/`contract_meta` 文本里恰好出现这些词，
不构成一句整体总结的出处。
同时也请理解这道闸的边界：它按**逐字出处**比对，模型若换一种词表外的说法，仍可能有一句漏网。
这类情况不需要调用方判别或拦截，**带 `traceId` 反馈给 AI 侧即可**，我们在服务端增补词表与判据。

**② 结论分布句尾部那句「其中 N 条填写了意见」**：存在空 `comment` 时由服务端追加（全员有字时不追加），
N = `comment` 非空的条数，未填写的条数由"共 X 条 − N 条"可推。这是服务端算得出的确定事实，由服务端直接
陈述而不留给模型推断——总述最容易出错的位置恰恰是收尾处交代"其余人怎么了"，这个事实一旦空缺，AI 就会
去补一个替沉默节点表态的句子。对调用方是**纯文本层**：字段形状、标记语义、前端渲染均零改动。实测增量
**+0～13 字**（全员有字时零增量），总述实测 145–228 字，距 300 字红线余量充足，正常情况下不改变渲染
形态；只有超长稿才可能因这十几个字让尾部主题被整句裁掉——裁尾不丢信息，被裁主题的原文仍在
`opinion_details` 里逐条可查。

## 7. 错误码

| code | HTTP | 含义 | 前端处理 |
|---|---|---|---|
| `0` | 200 | 成功（含部分 AI 字段降级的成功） | 正常渲染 |
| `10001` | 422 | 参数校验失败（`data` 为 `null`、`message` 为固定文案，**不返回逐字段错误明细**） | 视为调用方 bug：按 §3 字段表自查请求体；必要时凭 `traceId` 找 AI 侧查日志定位 |
| `10002` | 401 | 鉴权失败（key 缺失或不合法） | 检查 API Key |
| `20001` | 500 | 模型调用失败（重试耗尽） | 面板整体降级「智能总结暂不可用」或隐藏，**不阻塞审批** |
| `20002` | 504 | 模型调用超时 | 同上 |
| `20003` | 500（输入超长场景为 400） | 模型输出格式异常 | 同上 |

## 8. 缓存与性能

- 耗时实测（部门生产同规格 vLLM，Qwen3.6-35B）：缓存命中 **0.005–0.006s**；新生成 **2.86–12.58s**，随生成文本长度浮动而非单纯随意见条数（14 条意见的单子只要 4.9s，13 条的要 12.6s）。客户端 120s 超时预算的实测余量约十倍。
- token 实测（`GET /metrics` 免鉴权、`llm_tokens_total{model="Qwen3.6-35B"}` 前后差）：打开一次面板 = **prompt 6254 + completion 623 ≈ 6.9k token**，内部是 2 次模型调用（总述 + 逐条意见摘要批量），折算约 3.1k 输入 / 311 输出每次。**输入占九成，成本几乎完全由 prompt 体积决定**：意见更多或原文更长的单子会近线性推高这一项，输出侧基本恒定。命中缓存时**零模型调用、零 token 增量**（缓存由输入内容决定：改动输入任一个字即重新生成，原样重发则命中）。
- 一次未命中缓存的请求发几次模型调用：常规 **2 次**（总述主题稿 1 次 + 全部有字意见的摘要批量 1 次）；没有任何有字意见时**0 次**（总述只由服务端装配 ①② 两句，摘要没有对象）。仅当总述主题稿未通过**结构**校验（输出形状失守 / 某主题采信引用剔到剩 0 / 引用指向空 `comment` / 句中点了本主题未背书的节点名）时追加**至多 1 次**定向重试（上限 3 次，见 §6 的 `review_summary.incomplete`）。重试不改变响应结构，调用方无需处理。
- 超时口径：客户端 120s 是余量上限而非预期耗时；服务端单次模型调用超时现配置为 **30 秒**（既有全局配置，非本接口独立键），超时返回 `20002`，前端按整体降级处理即可。
- 一期缓存为服务进程内实现：服务重启、多副本部署时同一输入可能在个别副本上重新生成一次——调用方感知仅是耗时差异，结果始终由输入决定。
- 本接口与合同评审、预填共用同一 vLLM 实例；上线初期的并发节奏建议联调时同步沟通。

## 9. 调用方准备清单（合同系统侧）

1. 环境与凭据：AI 服务地址、API Key（找 AI 侧对接人领取）。
2. `action` 用词：按 §3.4 表**逐字**传合同系统审批界面的展示词（该表同时是服务端护栏的词表，"不通过"三个字必须逐字一致），有异议联调首日对齐。**首发即可自证**：看响应 `review_summary.text` 里那句「共 X 条意见：……」——它由服务端按传入的 `action` 原值逐字拼装，传进去什么就显示什么，一眼能确认线上实际发出去的字符。若里面出现英文或词表外的说法，说明取数链路传的不是展示原文，此时"有反对意见时总述只列事实"那道闸**不会报错但会静默不生效**（见 §6 铁律 5 用词约定）。
3. 样例数据（建议至少 4 组，直接给原始导出数据即可，AI 侧负责整理成请求体）：
   - 典型全集：提级 + ≥2 条高风险 + ≥3 条意见（含"有条件通过"）；
   - 含"不通过"意见的一组（验证总述中性化表现）；
   - `opinions=[]` 的一组（评审未完成态）；
   - 数字密集的一组（金额/比例/天数按展示原文）。
4. 回退重审传参口径确认（§3.4）。
5. 前端动作标签的映射表**键就用中文原值**（`通过 / 有条件通过 / 不通过`）：响应 `opinion_details[].action` 是输入原样回显，接口不做任何码值映射，键与值两边必须同源。
6. 不要加这两条前置校验（加了会让面板失真）：① "`comment` 为空就不传这条记录"；② "`opinions=[]` 当参数错误拦下"。两者都是合法输入，语义见 §3 通用约定 5 与 §6。

## 10. 文档信息

版本 v1.0。契约与字段以本文为准，实测性能见 §8；本文之后的修订由 AI 侧重新出具整份文件，不接受逐条
diff 说明。任何疑问、异常样例、总述文本问题，请带 `traceId` + 完整请求体原文 + 大致时间 + 期望结果反馈给 AI 侧对接人。

**值得报的情况**（都属 AI 侧问题，前端无需判别拦截）：传入的 `opinions` 非空却拿到 `code=0` + `review_summary.text=null`（按定义此时 ②结论分布句必然存在，`text=null` 只允许出现在"`opinions=[]` 且未传 `contract_meta`"）；总述出现请求体里任何评审人/合同字段都没写过的数字；命中缓存却返回了另一个合同的总述（按定义属数据正确性事故，最高优先级）；总述把没写字的节点写成"无异议"这类替沉默者表态的句子（这道闸按逐字出处比对，词表外说法仍可能漏网，反馈即可，我们在服务端补词表与判据）。

**不必报的正常外观**：`opinion_details` 行数恒等于传入的 `opinions` 条数，但有字的意见也可能 `summary=null`——像"同意。"这类无实质内容的原文，服务端判定无可摘要（与"其中 N 条填写了意见"里的 N 可以不等，两个口径都正确）；`themes[]` 条数可能少于模型原始产出（服务端已做同源合并，见 §5.4）；`degraded_sections` 非空（见 §6，`code=0` 仍是成功）。
