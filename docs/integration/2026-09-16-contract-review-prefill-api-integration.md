# 合同智能预填接口对接文档（`mode=prefill`）

> 版本：prefill-integration-v1
>
> 更新日期：2026-09-18
>
> 适用范围：`POST /api/v1/contract-review`（JSON）与 `POST /api/v1/contract-review/upload-md`（multipart 文件）的 `mode=prefill` 分支，用于合同系统 D-02（合同管理员）/ D-03（销售）表单的智能预填。两个入口的字段口径与响应结构完全一致。
>
> 📌 **2026-09-18 变更（对接方需知）**：`finance_info`（`contract_amount` + `currency`）**改为 `d02` 与 `d03` 共用** —— 先前 `d02` 只返回付款**比例**（如 `"50%"`）而无合同总额，消费方无法折算金额。现 `prefill_scope=d02` **也会返回该组**。**字段名、类型、取值口径与四组外层键均未变**，只需注意 `d02` 的返回多了这 2 个字段（见 §3.2、§4.5）。
>
> 配套文档：`2026-08-03-contract-review-legacy-api-temporary-integration.md`（评审接口，本文档的前置阅读）。

## 1. 接口概览

预填与评审**共用同一个入口**，靠请求里的 `mode` 分流。服务提供两个入口，**两者的 `mode` 语义、字段口径与响应结构完全一致**：

| 入口 | 方法与路径 | 请求类型 | `mode` 传在哪 |
|---|---|---|---|
| JSON 入口（推荐） | `POST /api/v1/contract-review` | `application/json` | 请求体字段 |
| Markdown 文件入口 | `POST /api/v1/contract-review/upload-md` | `multipart/form-data` | 表单字段 |

```text
POST <AI_BASE_URL>/api/v1/contract-review            # JSON：mode 在请求体
POST <AI_BASE_URL>/api/v1/contract-review/upload-md  # multipart：mode 在表单字段
```

| `mode` | 作用 | 返回内容 |
|---|---|---|
| `review`（默认） | 合同评审 | `overall_result` / `check_time` / `checks[]` / `metrics[]` |
| `prefill` | 智能预填 | `mode` / `prefill_status` / `prefill`（四组结构化字段） |

**要点**

- 不传 `mode` 等价于 `mode=review`。**合同系统如果是老调用方，不需要做任何改动**，行为与现在完全一致。
- 预填**不复用评审结果**：它只做结构化抽取，不返回 `checks[]`、不返回 `overall_result`、不返回 `metrics[]`。
- 两个入口**都支持预填**，按取文方式二选一：已有 Markdown 文本走 JSON 入口，手上是 `.md` 文件走 multipart 入口。文件入口的字段与示例见 §3.5。

## 2. 鉴权与请求头

与评审接口完全一致，沿用现有配置即可。

| 请求头 | 必填 | 说明 |
|---|---|---|
| `X-API-Key: <API_KEY>` | 视部署而定 | 任选一种；未配置 `LTC__AUTH__API_KEYS` 时鉴权中间件放行 |
| `Authorization: Bearer <API_KEY>` | 视部署而定 | 同上，二者取其一 |
| `X-Trace-Id: <追踪号>` | 否 | 建议传。不传时服务自动生成；响应里的 `traceId` 会原样回显，请记录以便排查 |
| `Content-Type: application/json` | 是 | — |

## 3. 请求

### 3.1 请求体

```json
{
  "contract_md": "# 合同标题\n\n合同正文 Markdown 全文",
  "mode": "prefill",
  "prefill_scope": "d02"
}
```

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `contract_md` | string | 是 | — | 合同正文 Markdown，最短 1 个字符。**建议传完整解析结果**，不要只传摘要。 |
| `mode` | string | 否 | `review` | 取 `prefill` 才会进入预填。只接受 `review` / `prefill` 两个值。 |
| `prefill_scope` | string | 否 | `all` | 取 `all` / `d02` / `d03`。只接受这三个值。**仅在 `mode=prefill` 时有意义**。⚠️ **请总是显式传 `d02` 或 `d03`** —— 默认值 `all` 无业务场景且是最慢路径，详见 §3.2。 |
| `attachments` | array | 否 | `[]` | **预填不读这个字段**。传了不会报错，但会被静默忽略（见 §3.4）。 |

### 3.2 `prefill_scope` 与返回分组的对应关系

**生产请按业务场景各调各的**：销售点按钮只传 `d03`、合同管理员只传 `d02`，**不要把两个场景合并成一次调用**（D-03 单独调用可省去约 2/3 耗时）。

| `prefill_scope` | 对应场景 | 抽取分组 | 实测耗时 |
|---|---|---|---|
| `d02` | 合同管理员预填 | `contract_info`（9 字段）+ `contract_plan`（数组）+ **`finance_info`（2 字段）** | 6.9s |
| `d03` | 销售预填 | `finance_info`（2 字段）+ `guarantee`（数组） | 3.1s |
| `all` | **无业务场景** —— 仅测试与兜底 | 上述四组全部 | 10.2s（**当前最慢**） |

> 📌 **`finance_info`（`contract_amount` + `currency`）同时出现在 `d02` 与 `d03` 中** —— 它按「基础信息」归属，不是某个场景专有。
> 原因：D-02 的 `contract_plan[].payment_amount` **多为比例**（实测样例返回 `"50%" / "40%" / "10%"`），
> 合同系统若只拿到比例而没有合同总额，**无法折算出金额**。所以 `d02` 也返回这一组，
> **两个场景各调各的、都拿得到，不需要为了拿总额额外再调一次 `d03`**。

> ⚠️ **`all` 是默认值，但没有任何业务场景需要它。** 不传 `prefill_scope` 就等于 `all`，会落到最慢的一条路径（`all` 10.2s vs `d03` 3.1s，慢约 3 倍），并发下还会显著放大超时风险（见 §11.4 第 5 条）。**请务必显式传 `d02` 或 `d03`。**

⚠️ **无论传哪个 scope，响应里四组键都会出现，一个都不省略**；未被本 scope 请求的组返回「空结构」（对象字段全 `null`、数组为 `[]`）。合同系统**必须按 scope 只取自己关心的组**，不要把空组当成"抽不到"。

```json
// prefill_scope=d02 时，未请求的一组如下（键存在但全空）
"guarantee": [],

// prefill_scope=d03 时，未请求的两组如下
"contract_info": { "payment_terms": null, "payment_method": null, ... },
"contract_plan": [],
```

### 3.3 请求示例

D-02（合同管理员）：

```json
{ "contract_md": "# 软件采购合同\n\n……", "mode": "prefill", "prefill_scope": "d02" }
```

D-03（销售）：

```json
{ "contract_md": "# 软件采购合同\n\n……", "mode": "prefill", "prefill_scope": "d03" }
```

curl：

```bash
curl -X POST "<AI_BASE_URL>/api/v1/contract-review" \
  -H "Content-Type: application/json" \
  -H "X-API-Key: <API_KEY>" \
  -H "X-Trace-Id: prefill-d03-001" \
  -d '{"contract_md":"# 服务合同\n\n……","mode":"prefill","prefill_scope":"d03"}'
```

### 3.4 请求注意事项

- **附件只认「在正文里的」**。预填的输入是 `contract_md` 全文，服务端**不做切分**：
  - ✅ **内嵌在正文里的附件**（正文中出现独立的 `附件一` / `附件二` 这类标题行）→ 与正文同等对待，**会**被抽取。
  - ❌ **单独上传的附件**（JSON 的 `attachments` / multipart 的 `attachment_files`）→ 预填**不读**，传了不报错但会被静默忽略。
  - 若合同金额、付款计划写在**外部附件**里（正文只写"详见附件2《技术协议》"这类引用），预填**抽不到** —— 请按「需人工填写」处理。
- **正文换行**：如果上游把整份正文拼成了一整行、换行被写成字面量 `\n`，服务会自动还原为真换行（仅当正文内不含任何真换行时才做替换，不会误改正文里本就存在的字面量 `\n`）。合同系统**不需要自己做这层处理**，按上游给的文本原样提交即可。（实测样例中确有一份是"全文 1 行 + 字面量 `\n`"的形态，正是这种输入会被还原。）
- **无跨请求版本控制**。合同内容变化时请重新提交完整正文；结果与业务版本的对应关系由合同系统自行维护。
- 与评审接口一样，JSON 入口对 `contract_md` 只做最短长度校验，**纯空白正文不算有效合同**，请自行保证。

### 3.5 Markdown 文件入口（multipart）

```bash
curl -X POST "<AI_BASE_URL>/api/v1/contract-review/upload-md" \
  -H "X-API-Key: <API_KEY>" \
  -H "X-Trace-Id: prefill-d03-002" \
  -F "contract_file=@./合同正文.md;type=text/markdown" \
  -F "mode=prefill" \
  -F "prefill_scope=d03"
```

| 表单字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `contract_file` | file | 是 | — | 合同正文，**必须是 UTF-8 编码的 `.md`** |
| `attachment_files` | file（可多个） | 否 | — | 附件，同样必须为 `.md`。**预填不读该字段**（见 §3.4） |
| `mode` | string | 否 | `review` | 取 `prefill` 才进入预填。只接受 `review` / `prefill` |
| `prefill_scope` | string | 否 | `all` | 同 §3.1。⚠️ **请总是显式传 `d02` 或 `d03`** |

- 响应结构与 JSON 入口**完全一致**，见 §4。
- `mode` 取值非法（例如写错成 `prefil`）会返回 **422 + `code=10001`**，**不会**静默落回评审。
- 该入口原先只服务评审；**不传 `mode` 时行为与改造前完全一致**，老调用方无需改动。

## 4. 成功响应

### 4.1 外层结构

```json
{
  "code": 0,
  "message": "ok",
  "data": { "...": "见 4.2" },
  "traceId": "prefill-d03-001",
  "duration_seconds": 3.1
}
```

`code=0` + HTTP 200 只代表**服务处理完成**，不代表抽取到内容。**必须同时检查 `data.prefill_status`**（见 §5）。

### 4.2 `data` 段

| 字段 | 类型 | 说明 |
|---|---|---|
| `mode` | string | 固定 `"prefill"`，便于合同系统区分两种响应形状 |
| `prefill_status` | string | `ok` / `failed`。**`failed` 时四组必为空结构** |
| `prefill` | object | 四组固定结构：`contract_info` / `contract_plan` / `finance_info` / `guarantee` |

> **⚠️ 取值口径：原文原样摘录，服务端不做任何加工（本接口最重要的一条约定）**
>
> **除 `milestone_seq`（阶段序号，整数）外，本响应所有业务字段都是字符串，内容为合同原文的原样摘录。**
> 服务端**不换算、不去符号、不改格式**：
>
> | 合同原文 | 响应返回 |
> |---|---|
> | `¥10,492,500.00` | `"¥10492500.00"`（符号与小数都保留） |
> | `¥ 4690000元` | `"¥ 4690000元"` |
> | 支付合同款总额的 **50%** | `"50%"` —— **不**折算成 5246250 |
> | 按中标金额的 **5%** 收取 | `"5%"` —— **不**折算成 524625 |
> | 履约保证金为 **¥ 130000 元** | `"¥ 130000 元"` |
> | **1年** | `"1年"` |
> | **13.5个月** | `"13.5个月"` |
> | **2025年3月1日** | `"2025年3月1日"` —— **不**归一成 `2025-03-01` |
> | 合同签订之日起120天内 | `"合同签订之日起120天内"` |
>
> **为什么这样做**：只要服务端把值声明成 JSON 数字或 ISO 日期，转换过程本身就会引入误差 ——
> 整数会被序列化成 `13.0`，`13.5` 按整型处理会直接失败，货币符号与千分位会被迫丢掉，
> 且原文写法被掩盖。**类型与展示格式交由合同系统自行定夺。**
>
> **对合同系统的要求**：
> 1. **全部按字符串接收**。金额**不要**声明为 `BigDecimal` / `Integer` / `Long`，日期**不要**声明为 `Date` —— 反序列化会失败。
> 2. 需要数值、需要绝对日期时，**由合同系统自行解析并界定换算规则**（`"50%"` 要不要折算成金额、`"1年"` 算几个月，属业务口径，应由你方决定）。
> 3. `milestone_seq` 是唯一例外，仍是**整数**，表示付款阶段顺序，可直接用于排序。
> 4. **服务端只摘录、不推算**。`plan_finish_date` / `plan_payment_date` 尤其如此 —— 它们的来源规则见 §4.4，值可能是相对表述，**日期计算请在你方完成**。

### 4.3 `prefill.contract_info`（D-02，9 字段，对象）

本组**不附 `evidence`**（原文出处挂在 `contract_plan` 每行上）。

下表"**原文写法**"表示该字段不做类型归一，返回合同里的原始文本（见上方取值口径）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `payment_terms` | string 或 null | 付款条件：分期与条件条款的**整段原文**，不是摘要 |
| `payment_method` | string 或 null | 付款方式，如 `转账` |
| `service_content` | string 或 null | 服务内容及方式，原文 |
| `service_valid_months` | string 或 null | 服务有效期限（月），**原文写法**（如 `"1年"`、`"13.5个月"`） |
| `service_sla` | string 或 null | 服务级别（SLA），原文 |
| `service_start_date` | string 或 null | 服务开始时间，**原文写法**。⚠️ **可能是绝对日期，也可能是相对/事件表述** —— 实测样例原文是「自系统上线并最终验收合格之日起计」，就照抄这一句 |
| `service_end_date` | string 或 null | 服务结束时间，**原文写法**，形态同上一行 |
| `onsite_service_count` | string 或 null | 现场服务次数，**原文写法** |
| `inspection_count` | string 或 null | 巡检次数，**原文写法** |

> ⚠️ 本组字段名带 `_date`，但**值一律是字符串、未必是日期**。请先尝试解析，解析失败就**原样展示**，不要直接丢给日期类型转换（会抛异常）。
> 这是刻意选择：原文怎么写就怎么给，怎么算由你方决定。

### 4.4 `prefill.contract_plan`（D-02，数组，每项 8 字段）

一个付款阶段一项。**数组已按 `milestone_seq` 升序排序，缺失序号的行排在最后**，合同系统可直接按顺序渲染。

| 字段 | 类型 | 说明 |
|---|---|---|
| `milestone_name` | string 或 null | 里程碑标准名，如 `启动` / `终验` / `维护期` |
| `milestone_code` | string 或 null | 与标准名对应的 code，如 `begin` / `finalaccept` / `end` |
| `milestone_text` | string 或 null | 里程碑原文描述 |
| `milestone_seq` | **integer** 或 null | 阶段序号，从 1 起。**全响应唯一的非字符串字段** |
| `plan_finish_date` | string 或 null | 计划完成时间，**原文写法**（可能是绝对日期，也可能是相对表述）。来源见下方 ⚠️ |
| `plan_payment_date` | string 或 null | 计划回款时间，**原文写法**。来源见下方 ⚠️ |
| `payment_amount` | string 或 null | 回款金额，**原文写法**。⚠️ 合同多以比例约定（实测样例返回 `"50%"` / `"20%"`），**原文写比例就返回比例，服务端不折算成金额** |
| `evidence` | array | 该行全部字段的原文出处，见 §4.7 |

> **⚠️ 两个时间字段的取值来源（2026-09-17 定）**
>
> **里程碑名称、描述、序号、金额只从付款条件拆**（其中名称与 `code` 需再按服务端标准清单映射，见 §8 第 9 条）；两个时间字段各有固定的**取值来源**（指「**读合同的哪一处**」是确定的，**不是「值被固定」** —— 取到什么都照抄原文），**服务端不做任何推算**。
>
> | 字段 | 来源（按顺序取到即止） |
> |---|---|
> | `plan_finish_date` | ① 原文有独立的「合同计划 / 进度计划」章节 → 取该章节里本阶段的预计完成时间<br>② 没有该章节 → 取「交付 / 验收」条款里本阶段的完成时间<br>③ 两处都没有 → `null` |
> | `plan_payment_date` | 只从**付款条件**里取本阶段对应的时间表述（如「初验后15个工作日内」）；付款条件里没有 → `null` |
>
> **服务端不计算** —— 不做日期加减、不把「120天」折成具体日期、**不用完成时间推算回款时间**。原文写绝对日期就给日期，写相对表述就照抄表述（如 `"自合同签订之日起120天（自然日）内"`），**怎么算由你方决定**。
>
> ⚠️ **该行 `plan_finish_date` 为 `null` 时，`plan_payment_date` 也无从推算** —— 请按「无法推算（缺预计完成时间）」呈现，而不是当成普通空值。

### 4.5 `prefill.finance_info`（D-02 **与** D-03，2 字段，对象）

本组**不附 `evidence`**。**`d02` 与 `d03` 都会返回它**（理由见 §3.2 的说明）—— `d02` 侧主要用于把
`contract_plan[].payment_amount` 的比例折算成金额。

| 字段 | 类型 | 说明 |
|---|---|---|
| `contract_amount` | string 或 null | 合同额，**原文写法**（实测样例返回 `"¥10492500.00"`、`"¥ 4690000元"`，符号与空格照原样） |
| `currency` | string 或 null | 币种，如 `CNY` |

### 4.6 `prefill.guarantee`（D-03，数组，每项 7 字段）

**支持多笔，不设上限；合同没有约定时为 `[]`。**

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | string 或 null | 只可能取 `履约保函` 或 `履约保证金` |
| `amount` | string 或 null | 申请金额，**原文写法**。原文写固定额则原样返回（如 `"¥ 130000 元"`）；原文写「按合同金额的 5% 收取」则返回 `"5%"`，**服务端不折算** |
| `payee` | string 或 null | 收款单位 / 受益人 |
| `bank_name` | string 或 null | 开户银行 |
| `bank_account` | string 或 null | 银行账号 |
| `return_clause` | string 或 null | 归还条款，原文 |
| `evidence` | array | 原文出处，结构同上 |

### 4.7 `evidence` 结构（`contract_plan` / `guarantee` 每行内）

```json
"evidence": [
  { "section": "第四条 付款方式及条件", "quote": "1. 预付款：本合同签订生效后 10 个工作日内，甲方向乙方支付合同总金额的 30%" },
  { "section": "第五条 合同计划", "quote": "1 | 启动 | 合同签订、项目组进场、实施方案确认 | 2026年1月20日" },
  { "section": "第三条 合同金额", "quote": "1. 本合同总金额为人民币 ¥3,860,000.00 元（大写：叁佰捌拾陆万元整），含税。" }
]
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `section` | string 或 null | 该片段所在的**顶层条款标题原文**；原文没有标题结构时（如整份正文无换行）为 `null` |
| `quote` | string 或 null | 原文片段，**最长 300 字**；常规条款不会被截断 |

**`contract_plan` 每行的 `evidence` 固定 3 条**，按出处各一条：

| # | 出处 | 覆盖的字段 |
|---|---|---|
| ① | 付款条件 | 里程碑名称 / 描述 / 序号 / 金额 |
| ② | 合同计划章节**或**交付 / 验收条款 | `plan_finish_date` |
| ③ | 合同金额条款 | 金额核对 |

**🔑 某个出处原文确实不存在时，该条固定返回 `{"section": null, "quote": "无"}`** —— `quote` 就是「无」两个字。

消费方判定规则：

| 情形 | 含义 | 建议动作 |
|---|---|---|
| `quote == "无"` | 服务端通读全文后确认**原文没有该处内容** | 该行 `plan_finish_date` 为 `null` 时属**正常缺失** —— 留空让用户手工填，**不要标红** |
| `quote` 是原文片段 | 有出处，可回原文核对 | 正常流程 |
| 该出处条目**根本没出现** | 属异常（与「无」不同义） | 提示人工核对 |

> ⚠️ **必须用全等比较**：`"无".equals(quote.trim())`。不要用「包含『无』」—— 原文里的「无违约条款」这类表述会被误判。

`evidence` 的用途是**让人工核对抽取是否可信**，不是给机器做校验的。同一出处只会出现一次。

> 📌 `guarantee` 的 `evidence` 结构相同，但**不强制 3 条** —— 保函信息通常集中在一个独立章节里，按实际出处给即可。
> 合同完全没有保函/保证金约定时 `guarantee` 直接是 `[]`：**没有行、也就没地方声明「无」**。这个歧义目前保留，见 §8 限制第 8 条。

## 5. 抽取失败：`prefill_status=failed`

**这是本文档最重要的一条。**预填链路的任何失败（模型超时、模型返回格式异常、内容过长、网络抖动）都会被**降级**处理：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "mode": "prefill",
    "prefill_status": "failed",
    "prefill": {
      "contract_info": { "payment_terms": null, "...": "全部为 null" },
      "contract_plan": [],
      "finance_info": { "contract_amount": null, "currency": null },
      "guarantee": []
    }
  },
  "traceId": "prefill-d03-007",
  "duration_seconds": 30.001
}
```

> 上例为**构造示意**（`prefill_status=failed` 的响应形状由代码保证，`duration_seconds` 仅示意"耗时接近超时阈值"这一典型形态）。

⚠️ **HTTP 仍是 200、`code` 仍是 0。**合同系统**不能只看 HTTP 状态码判断预填是否成功**，必须判断 `data.prefill_status`：| 判断 | 结论 | 建议动作 |
|---|---|---|
| `prefill_status == "ok"` | 抽取链路正常完成 | 取用字段；**注意字段仍可能是 `null`**（见 §8） |
| `prefill_status == "failed"` | 本次预填整体失败 | **把表单留空交给人工填写**，不要用空字段覆盖已有值；可带同一 `traceId` 重试一次 |

失败时返回的是**全空结构而不是部分结果**——不存在"抽到一半"的响应。合同系统不需要（也无法）做字段级的部分成功处理。

## 6. 错误响应

参数类错误与评审接口一致，仍是统一响应壳：

| HTTP | `code` | 含义 | 典型场景 |
|---:|---:|---|---|
| 422 | `10001` | 参数校验失败 | `mode` 传了 `review`/`prefill` 以外的值；`prefill_scope` 传了 `d02`/`d03`/`all` 以外的值；缺 `contract_md`；`contract_md` 为空串 |
| 400 | `10001` | 业务参数错误 | multipart 入口相关（预填不走此入口） |
| 401 | `10002` | API Key 无效或缺失 | 服务开启鉴权但未传有效 Key |
| 500 | `29999` | 内部错误 | 未捕获异常；请记录 `traceId` 反馈 |

```json
{
  "code": 10001,
  "message": "参数校验失败",
  "data": null,
  "traceId": "prefill-d03-007",
  "duration_seconds": 0.003
}
```

⚠️ **注意与评审接口的差异**：评审接口会返回的 `20001`（模型调用失败）/ `20002`（模型超时）/ `20003`（模型输出格式异常），在预填模式下**不会出现**——它们全部被降级成 §5 的 `prefill_status=failed`。所以合同系统在预填链路上**只需处理 `10001` / `10002` / `29999` 三个错误码**。

## 7. 性能与超时

在部门 vLLM（`Qwen3.6-35B` @ `192.168.16.10:8080`）上的实测值，**已包含预热**：

| `prefill_scope` | 短合同（10,632 字，3 个付款阶段） | 较长合同（12,541 字，6 个付款阶段） |
|---|---:|---:|
| `d03` | **3.1s** | 2.5s |
| `d02` | **6.9s** | 16.9s |
| `all` | **10.2s** | 18.6s |

> 上表为**同一批、同一环境重复 3 次取中位数**（2026-09-18 重测，`tmp/_repeat_timing.py`）。单次测量会有 **±2 秒以上波动**——推理服务是部门共享的，
> 别人在跑任务时你的请求也会变慢。判断"接口变快了还是变慢了"必须用重复测量的中位数，不能看单发，**更不能跨天比对绝对值**。
>
> 📌 **`d02` 行较上一版（5.2s / 11.6s）有上升**，原因有二：① `d02` 新增了 `finance_info` 组（见 §4.5），输出 token 略增（**影响 <0.5s**）；
> ② **主因是本次重测时推理服务负载较重** —— 同一份代码的 `all` 行也从 8.8s / 12.8s 抬到 10.2s / 18.6s，`d02` 与 `all` 的比值在两版里**完全一致（0.906）**，
> 说明这是**整体标度漂移**而非 `d02` 本身变慢。**请把上表当作同一批内的横向对比用，不要当作跨天基准。**
>
> 取值口径改为「原文原样」**不带来额外耗时**：金额从数字变短（`5246250.0` → `"50%"`）、
> 日期从 `2026-08-15` 变长，输出 token 总量大致持平。改口径前的 `all` 是 8.5s / 14.9s，同一量级。
> ⚠️ 但 **长合同 `all` 约 19 秒**这一绝对值，叠加并发后仍是超时风险的主要来源（见 §11）。

注意事项：

1. **首次调用有冷启动**。服务刚启动后的第一次请求会多花约 10–16 秒（链路初始化），之后恢复正常。**建议演示或压测前先打一发预热请求**，否则会把冷启动误判为接口慢。
2. **耗时与合同篇幅、付款阶段数量正相关**，不是固定值。合同越长、付款阶段越多，输出越多、越慢。上表"长合同"档的差异就是内容驱动的。
3. ⚠️ **超时配置必须覆盖实际耗时**。服务默认 `timeout: 30`（秒），`config-prod.yaml` 当前**只覆盖了 `base_url` / `model` / `log_level`，没有覆盖 `timeout`**，因此 **prod 实际生效的是默认的 30 秒**。**较长合同在 `all` 下已实测 18.6 秒，单请求就吃掉 60% 以上余量**；并发一上来（§11 实测并发 8 就 18s+）**必然击穿**。部署到 prod 前请确认 `llm.timeout` 已放宽（`dev` / `test` 现为 300，建议 prod ≥120），否则会出现 `prefill_status=failed` 而不是报错。
4. 请求是**同步阻塞**的，建议合同系统侧的超时设置大于 60 秒，并做好并发限流（单实例并发过高会明显拉高单请求延迟）。

## 8. 已知限制与使用建议

1. **抽取是概率性的**。同一份合同多次调用，个别字段的取值或 `evidence` 条数可能不同（例如某一项从 `null` 变为有值）。合同系统的定位应是**「智能预填 + 人工确认」**，不要把结果当作已确认数据直接落库。
   - **当前实现**已固定 `plan_finish_date` 的**取值来源**（指「**读合同的哪一处**」已确定，**不是「值被固定」** —— 取到的值仍然是合同原文照抄；来源见**本文档 §4.4**），实测**归属漂移已消除**：同一份合同连跑 3 次，取值与所在行完全一致（此前会出现"这次有、下次没有"的乱跳）。
2. **字段为 `null` ≠ 抽取失败**。大多数情况是**合同里确实没写**这项（如短合同里没有约定期限、SLA、巡检次数）。上例中 9 个 `contract_info` 字段只填出 4 个，是因为该合同本来就只约定了这 4 项。
   - `contract_plan` 每行可再看 `evidence`：出现 `{"section": null, "quote": "无"}` 即表示**该处出处在原文里确实不存在**（判定规则见 §4.7）。
3. **`evidence` 一定与字段同源**，`quote` 最长为 300 字，常规条款可整句容纳；只有超长段落才会截断，需要完整原文时回正文检索 `section` 对应的条款。
4. **`*_date` 不一定真的是日期** —— 一律字符串，可能是绝对日期，也可能是相对/事件表述：
   - `plan_finish_date`：来源固定为「合同计划章节 → 交付/验收条款 → `null`」（见**本文档 §4.4**；「固定」指的是**读取位置**，取到的值仍是该处的原文照抄）。合同写"自合同签订之日起120天（自然日）内"，就原样返回这句。
   - `plan_payment_date`：只取自付款条件的原文表述（如"验收合格后10个工作日内"）。
   - `service_start_date` / `service_end_date`：可能是"自系统上线并最终验收合格之日起计"这类**事件起算**。
   - ⚠️ **服务端不算，也不应被指望算**。请先尝试解析，解析失败就**原样展示**。需要绝对日期时由合同系统按自己的业务规则推算。
   - ⚠️ 该行 `plan_finish_date` 为 `null` 时，`plan_payment_date` 也无从推算 —— 请按**「无法推算（缺预计完成时间）」**呈现，而不是当普通空值。
5. **所有业务字段都是字符串，且不做取值加工**（详见 §4.2）。金额连货币符号与千分位一起返回（`"¥ 4690000元"`），比例原样返回（`"50%"`）。
   - **合同系统请全部按 `String` 接收**：金额**不要**用 `BigDecimal` / `Integer` / `Long`，日期**不要**用 `Date`，否则反序列化会失败。
   - 需要数值时由你方自行解析，**并自行界定口径**（`"50%"` 要不要折成金额、`"1年"` 算几个月）。
   - 例外只有 `milestone_seq`，它是整数。
6. **预填不做任何评审结论**，不产生 `checks[]`，不会因为金额大小写不一致、付款方式异常等给出 `PASS/WARN/FAIL`。需要评审请另行调用 `mode=review`。
7. **建议合同系统保存每次请求的完整输入、完整响应与 `traceId`**，便于人工复核与问题定位。
8. **`contract_plan: []` 与 `guarantee: []` 仍有歧义**：无法区分"原文确实没有"与"抽取漏掉"—— `guarantee` 为空时没有行、也就没有地方声明「无」。这个歧义目前**刻意保留**（对象组的字段级状态同理不做，避免引入字段级证据索引）。请在 UI 上把这类空数组当作**待人工确认**，而不是确定结论。
9. **🔴 `milestone_name` / `milestone_code` 是按标准清单「映射」出来的，不是原文摘录**（同类例外还有 `currency`）。该清单目前**固化在服务端**，共 13 个：
   `begin` 启动 / `confirm` 环境确认 / `deliver` 交付 / `design` 设计 / `develop` 开发 / `end` 维护期 / `finalaccept` 终验 / `midmaintain` 阶段维护 / `plan` 策划 / `preaccept` 初验 / `require` 需求 / `test` 测试 / `testrun` 试运行。
   语义相近但不在清单内的里程碑**一律返回 `null`**（`milestone_text` 仍保留原文描述，可据此人工选填）。
   - ⚠️ **若你方里程碑字典发生调整，请同步知会服务端** —— 否则我方会继续输出旧 `code`，你方按自己的字典匹配会**落空**，而**接口不会报错**（`prefill_status=ok`、HTTP 200），属静默不一致。
   - 匹配失败时请按「**需人工核对**」呈现，不要当成"合同没写"。清单与合同系统的自动同步（配置化 / 字典接口驱动）**当前版本尚未支持，将在后续版本提供**。
10. **附件只认「在正文里的」**（规则细节见 §3.4）：预填只读 `contract_md` 全文，**单独上传的 `attachments` / `attachment_files` 一律不参与抽取**。正文里内嵌的 `附件一` / `附件二` 章节会被当作正文一并抽取；正文只写"详见附件2"、附件在外部时，相关字段**抽不到**，请按需人工填写。

## 9. 最小联调验收清单

1. **老调用方零影响**：不传 `mode` 或传 `mode=review`，响应 `data` 的键集合仍为 `overall_result` / `check_time` / `checks` / `metrics`，**且不含 `mode` 键**。
2. `mode=prefill` + `prefill_scope=d03`，返回 HTTP 200、`code=0`、`data.prefill_status=ok`、`data.mode="prefill"`。
3. 确认响应里 **`prefill` 的四个组键全部存在**，未请求的组为空结构而非缺失。
4. **金额形态自检（口径已变，注意）**：`payment_amount` 返回的是**原文写法**，**不能直接求和**。合同按比例约定时，校验**各阶段百分比之和 = 100%**（实测样例 `50% + 40% + 10%`）；合同按固定金额约定时，才是"各行求和 = `contract_amount`"。两种都需**先按你方口径把字符串解析成数值**，但**金额与计划现在在 `d02` 里就能同时看到** —— `finance_info`（含 `contract_amount`）与 `contract_plan` 同属 `prefill_scope=d02`，**不必再退到 `all`** 才能凑齐两侧数据。
5. 确认 `contract_plan` 已按 `milestone_seq` 升序排列（**该字段是整数**，可直接排序）。
6. **反序列化类型自检（联调第一发就要过）**：确认你方的响应模型把金额、日期、次数类字段**全部声明为 `String`**，只有 `milestone_seq` 是整数。声明成 `BigDecimal` / `Integer` / `Long` / `Date` 会在第一发就抛类型异常。
7. `prefill_scope` 传 `d99`，返回 HTTP 422、`code=10001`。
8. `mode` 传 `others`，返回 HTTP 422、`code=10001`。
9. 传 `X-Trace-Id`，确认响应 `traceId` 原样回显。
10. 在服务开启鉴权时不传 API Key，返回 HTTP 401、`code=10002`。
11. 故意传一段**没有付款条款的正文**，确认返回 `prefill_status=ok` 但 `contract_plan=[]`——**即"抽不到"走成功分支，不要把这类情况当成接口故障**。
12. **两个时间字段的来源自检**：用一份**没有独立「合同计划」章节**的合同（如 c1），确认 `plan_finish_date` 从**交付/验收条款**摘到值；只有确实取不到的行才是 `null`，且该行第 2 条 `evidence` 为 `{"section": null, "quote": "无"}`。若整份合同都返回 `null` 且没有「无」，说明规则没生效。
13. **`"无"` 判定自检**：确认你方用**全等**判断（`"无".equals(quote.trim())`），不要用包含 —— 否则原文里的「无违约条款」会被误判成缺失。
14. **`evidence` 条数自检**：`contract_plan` 每行应固定 **3 条**；少于 3 条说明该出处既没给原文也没标「无」，属异常。
15. **里程碑映射自检**：确认返回的 `milestone_code` 能匹配上**你方的里程碑字典**。匹配不上的**按「需人工核对」处理**，并把该名称**反馈给服务端** —— 清单固化在服务端、不会自动同步（见 §8 第 9 条）；也可结合同一行的 `milestone_text`（原文描述）人工判断。
16. **文件入口自检**：用 `POST /api/v1/contract-review/upload-md` 上传 `.md` 文件，表单带 `mode=prefill` + `prefill_scope=d03`，确认返回结构与 JSON 入口**完全一致**；再试一次**不带 `mode`** 的同一次上传，确认仍返回评审的 `checks[]`（老行为不变）；`mode` 写错（如 `prefil`）应返回 **422**，而不是评审结果。

## 10. 附：预填链路的处理边界

接口收到 `mode=prefill` 后同步执行：

1. 校正正文换行（仅当整份正文无真换行时，把字面量 `\n` 还原）；
2. 按 `prefill_scope` 选定分组，构造该场景的抽取提示与结构化输出约束；
3. 调用大模型一次，强制输出符合该 scope 的 JSON（`strict` schema）。**该 schema 已把除
   `milestone_seq` 外的全部字段声明为字符串**，并要求模型**照抄原文写法**（不换算比例、
   不去货币符号、不归一日期），口径见 §4.2。两个时间字段的来源也在提示里写死：
   `plan_finish_date` 按「合同计划章节 → 交付/验收条款 → `null`」取，
   `plan_payment_date` 只取自付款条件；**模型被明确禁止做日期加减或推算**；
4. 组装四组固定结构，`contract_plan` 按 `milestone_seq` 升序。**服务端不对取值做任何二次加工**
   —— 拿到的字符串原样放进响应；
5. 任何异常降级为 `prefill_status=failed` + 全空结构。

⚠️ **预填链路不查询签署地预设值服务**，因此**不受该服务可用性影响**——评审链路的这一依赖在预填这里不存在。

## 11. 并发与容量（生产上线前必读）

### 11.1 实测数据

在现有推理服务（单卡 vLLM，`Qwen3.6-35B`）上，用 `prefill_scope=all`、中等长度合同（约 1.1 万字）实测，**同一时刻**提交 N 个请求：

| 同时提交数 | 全部完成耗时 | 单请求耗时（中位） | 吞吐 | 延迟放大 |
|---:|---:|---:|---:|---:|
| 1 | 8.7s | 8.7s | 0.12 份/秒 | 1.00x |
| 2 | 11.2s | 11.2s | 0.18 份/秒 | 1.29x |
| 4 | 13.2s | 12.5s | 0.30 份/秒 | 1.44x |
| 8 | 20.4s | 19.7s | 0.39 份/秒 | 2.26x |
| 16 | 28.4s | 26.7s | 0.56 份/秒 | 3.07x |

> 📌 本表基线与 §7 表同源（`all`、约 1.1 万字）。2026-09-18 在 GPU 负载较重时段重测，`all` 单请求中位升至 10.2s（c1）/ 18.6s（c2）——
> **差异属共享推理服务的负载波动，不是代码变化**。本表用于说明**并发导致的相对放大**（1.00x → 3.07x），该结论与绝对基线无关。

**两条必须记住的规律：**

1. **吞吐涨得远慢于并发涨的速度。** 16 个并发只把吞吐从 0.12 提到 0.56 份/秒（**4.7 倍**），并行效率约 **29%** —— 加并发并不能等比例提升处理能力。
2. **单请求耗时是被"拉长"，而不是"排队后依次快速跑完"。** 并发 16 时**每一个**请求都要等约 27s，而不是前几个 8.7s、后几个也 8.7s。这是推理服务连续批处理的特性：同一批请求一起推进、一起变慢。**并发越高，每个销售等得越久。**

### 11.2 风险提示

1. **🔴 生产 `timeout` 当前是默认 30 秒，并发下会大面积失败。** `config-prod.yaml` 未覆盖 `llm.timeout`，落回 `config.yaml` 的 30 秒。按上表，**并发 8 就已 20.4s、并发 16 直接 28.4s**，再叠加合同更长（长合同单请求 `all` 本身约 18.6s），30 秒必然击穿。
2. **🔴 超时的表现是"静默失败"，不是报错。** 一旦击穿超时，返回的仍是 **HTTP 200 + `code=0`**，只是 `data.prefill_status=failed`、四组字段全空。合同系统若不检查该字段，会把它当成"抽到空值"直接回填表单（详见 §5）。
3. **🟡 预填会拖慢评审接口。** 预填与评审**共用同一个推理服务实例**。批量预填占满推理服务时，同时段的评审请求也会变慢甚至超时——影响的不只是预填功能。
4. **🟡 客户端自带的超时可能比服务端更早触发。** 网关 / HTTP 客户端常见默认 30s 或 60s，会先于服务端断开，用户看到的是"接口超时"而非"预填失败"，且**同一批请求很可能被重试**，进一步加剧拥堵。
5. **🟡 首次调用有额外预热开销。** 进程或推理链路冷启动时，第一次调用会多出约 **4~20s**（取决于当时 GPU 负载）。演示或压测的第一发数据不代表稳态。
6. **🟡 目前无法直接观测推理服务排队情况**：该服务的 `/metrics` 端点未开放（实测 404/拒绝），应用侧也没有并发闸门，**过载时排在哪里、排了多久看不到**。

### 11.3 预估后果（外推到"几十份"）

| 场景 | 预估单请求耗时 | 预估全部完成 | 后果 |
|---|---|---|---|
| 5 份同时提交（中等合同） | 约 14~15s | 约 16s | 可用，但已明显慢于串行的 8.7s |
| 30 份同时提交（中等合同） | 约 40~50s | 约 50s | **prod 30s 超时下全部 `prefill_status=failed`** |
| 30 份同时提交（长合同，12,541 字 / 6 个付款阶段） | 约 70~90s | 约 90s | 超时 + 客户端先断连 + 重试放大拥堵 |

> 上表按实测趋势外推（单请求输出约 1,200 token，批处理输出吞吐上限约 **670 token/秒**，由并发 16 实测反算）。**演示阶段按串行调用即可，不受此影响**；但生产上线前必须处理。

### 11.4 应对方案

**A. 上线前必做（配置层，成本最低）**

1. 把生产 `llm.timeout` 从 30 提到 **≥120 秒**（`config-prod.yaml` 增加 `timeout: 120`；dev/test 现为 300）。**这是当前最大的单点风险，不改必然出故障。**
2. 请求 `X-Trace-Id` 并落库，便于事后定位是"抽不到"还是"超时降级"。

**B. 调用方建议（合同系统侧，零服务端改动）**

3. **批量场景不要一次性并发提交**。建议同时最多 **4 份**在飞，其余排队；实测 4 并发单请求仅 12.7s，性价比最高。
4. **客户端超时设 ≥180 秒**，且**读到 `prefill_status=failed` 时不要立即自动重试**（避免把超时变成雪崩）；建议退避后重试或转人工。
5. **交互优化（强烈建议）**：点"预填"后先用 `prefill_scope=d03`（销售关心的 9 字段，实测 **3.1 秒**）把关键字段铺上屏，再后台补 `d02`（19 字段，6.9 秒）。**用户感知延迟从 10.2s 降到 3.1s**，且把一次大请求拆成两次小请求，对推理服务更友好。
   > 前提是**按业务场景选 scope**：销售点按钮就只调 `d03`、管理员只调 `d02`。`all` 只是为测试与兜底保留的路径，**却是当前最慢的一种**——只要调用方按场景各调各的，并发压力与超时风险都会显著下降。
6. **批量补数据选低峰期**（如夜间），避开与评审业务的高峰重叠。

**C. 服务端改进（需改代码，建议另开 change）**

7. **加并发闸门**：在预填入口限制同时在飞请求数，超出时快速返回一个明确的"繁忙"状态（而不是让所有请求一起变慢到超时）。这样超时被挡在应用层，不会传导到推理服务。
8. **开启 `/metrics`**：观测排队与批大小，为容量规划提供依据。

**D. 容量规划（长期）**

9. 按峰值并发评估推理服务副本数；若预填批量吞吐是刚性需求，**建议给预填分配独立实例**，避免与评审互相拖累。

### 11.5 演示期注意事项

- **串行调用**，不要并发演示。
- **演示前先打一发预热请求**（否则第一发可能慢 10~20s），正式演示的响应时间才代表稳态。
- 演示前确认 `timeout` 已放宽（若演示环境仍是 30 秒，长合同 `all` 有失败风险）。
