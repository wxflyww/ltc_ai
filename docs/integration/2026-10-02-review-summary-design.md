# 评审智能总结 0.2 · 设计文档

> 状态：设计定稿（2026-10-02）。CRM 字段暂缓接入，契约已预留扩展。  
> 下一步：按本文走 OpenSpec change 立项（explore → propose），接口路径等以立项产物为准。

## 1. 定位与职责边界

### 1.1 这是什么

「评审智能总结」是合同审批详情页上的一个总结面板。审批人打开页面时，合同系统调用本接口，传入评审环节的结构化数据；接口返回整包面板 JSON，合同系统按区块渲染。

**覆盖范围（0.2）**：只覆盖评审内容总结，审批侧的路由、会签、高管提级等流程逻辑不在本方案内；所有审批人看到的总结内容相同，无角色视角、无当前节点概念。

### 1.2 第一原则：整包输出

**接口交付物 = 「评审智能总结」面板这个产品，而非裸模型能力。**

| 方     | 职责                                                      |
| ----- | ------------------------------------------------------- |
| 合同系统  | 业务数据的**生产者与筛选者**：传什么（只传高风险项、只传当前有效轮意见）、保证数据正确性与一致性      |
| AI 接口 | 总结产品的**组织者、写作者与兜底者**：怎么组织（面板结构）、怎么写（总述与摘要）、空了怎么降级（空态矩阵） |

- 响应为整包 JSON，含原文装配字段；合同系统可**整包渲染**，也可对已有组件覆盖的模块选择忽略对应字段。
- 理由：① AI 生成总述本就需要全量输入上下文，"传进来"省不掉，整包只多"回传"这一步、代价≈0；② 空态矩阵、事实单点归属、总述与重点关注联动、source_refs 校验等展示规则归接口侧单一实现，合同系统零业务理解渲染；③ 缓存与溯源以整包为单位最简单；④ 避免双数据源的时序问题（原文即时、AI 数秒）。

### 1.3 责任边界红线

1. **AI 不出具决策建议**：不输出「建议通过 / 建议驳回」类结论，只做事实定调。行动类内容称「**处置参考**」，且一律**引用风险管理清单应对措施原文**，AI 对动作零生成。
2. **不做业务加工**：接口不关心业务对错。传什么顺序就按什么顺序展示、传什么意见就按什么意见总结、传什么风险就展示什么风险。一致性、历史轮次、数据准确性由合同系统在传参前保障。
3. **合同系统无 AI 能力**（硬约束）：凡需"生成 / 整理 / 提炼"的文本，对方只能照搬现成字段；需要生成的一律由本接口做，或不做。

### 1.4 展示假设

- 面板数据 = **评审完成时点**的快照（评审完成后才进入审批，展示时评审数据已稳定）。
- `opinions[]` / `risk_register[]` 按**传入数组顺序**展示，接口不重排（评审节点并行，node_seq 无全序意义）。
- 数据筛选已在合同系统侧完成：`risk_register` 只含高风险项，`opinions` 为评审环节全部节点意见全集。

## 2. 面板结构与生成规则

### 2.1 三部分结构

```
┌─ 评审智能总结 ─────────────────────┐
│ 一、评审总结（一段话）              │
│   服务端拼接总述（目标 ≤200 字）点出卡点 │
│ 二、重点关注（编号 1/2/3 …）        │
│   1 提级原因（如传入）              │
│   2 高风险项 A + 处置参考           │
│   3 高风险项 B + 处置参考           │
│ 三、各节点意见详情（默认折叠）      │
│   ▸ 销售 · 张某 · 通过 …            │
│   ▸ 法务 · 陈某 · 有条件通过 …      │
└────────────────────────────────────┘
```

页面样式以双方确认的 demo 为准（demo 文件不在本仓维护，由设计侧另行提供）；接口只提供内容 JSON。

### 2.2 AI 含量盘点

整个接口的 AI 生成**只有两处**，其余全部为原文装配：

| 模块        | 内容来源                  | AI 生成？                |
| --------- | --------------------- | --------------------- |
| 评审总结      | 总述（①合同要素句 + ②结论分布句由服务端装配，③主题层与 overall 由 AI 生成） | ✅ 生成（受 §2.3 全部规则约束）   |
| 重点关注·提级原因 | `route_reason` 原文     | ❌ 照搬                  |
| 重点关注·风险项  | `risk_register[]` 全字段 | ❌ 照搬                  |
| 重点关注·处置参考 | `measure_desc` 原文     | ❌ 照搬                  |
| 各节点意见详情   | 每条意见的摘要               | ✅ 生成（压缩 `comment` 原文） |

风险项中的数字、条款、决策**全部零生成**——这是防幻觉的基本盘。

### 2.3 生成规则（防幻觉五条铁律）

1. **数字零生成**：金额、比例、期限等一律原文引用，AI 不解析、不换算、不四舍五入、不润色。服务端做阿拉伯数字 token 抽验，核对原文 = 规范化请求体 + 服务端自己注入 Prompt 的派生文本（如「结论分布」里的条数）；模型照抄服务端给的数字不算编造（change design.md D9）。**"照抄"包含保持写法**：原文的阿拉伯数字必须原样出现，禁止转写成中文数字（"五十万""百分之二点二四"）——抽验只认阿拉伯 token，转写等于绕开这道闸（change design.md D16.5，真机 s05 已出现该形态；当前处置 = Prompt 硬禁令 + 服务端中文数字观测日志，不扳闸）。
2. **事实单点归属**：装配区（重点关注、意见详情骨架）为事实的唯一完整呈现处——每个输入字段只被原文回显一次，结构上无重复；本规则的约束对象是**两处 AI 生成文本**（总述、意见摘要）——只做话题级引用（如"主要关注点集中在预付款比例"），不重复展开装配区已有的数字、条款与影响（如不写"预付款 15% 低于标准 30%、占用资金 96 天"）。注意边界：规则管**事实**不管**观点**——意见摘要照写人的主张（"要求提至 20% 或确认垫资"），与风险块的客观事实同话题不算重复。
3. **引用溯源**：每条 AI 结论都必须携带来源引用。**总述**的引用粒度是**主题**（change design.md D16）：每条主题句自带 `opinion_refs`（指向 `opinions[i]` 的意见整下标），服务端校验——逐条剔除清单外引用（G1），剩余 ≥1 条合法引用即照常采信该主题；剔空则该主题弃用。整段总述的 `source_refs` 由服务端汇总（合同要素字段路径 + `opinions` 聚合 + 各主题采信的 refs），前端与合同系统拿到的仍是可溯源路径。**意见摘要**无引用或引用悬空即丢弃该条。弃用/丢弃均不阻塞装配区（总述的兜底见 §5.3，change design.md D10）。
4. **总述形容词铁律**：总述中的评价性修饰必须可溯源到输入字段原文（如"客户信誉良好"须有 CRM 评级类字段支撑）；溯源不到就只说事实。CRM 字段暂缓接入期间，总述**不写客户评价**。
5. **总述与结论分布一致性**：`opinions` 中存在 `action` 逐字为「不通过」的意见时，总述退化为**中性陈述**（只列事实 + "评审意见存在分歧"类客观描述），不得出现"整体认可""一致看好"等正面定性。action 废除枚举后扳机词仅「不通过」一词，词表外动作词（如"驳回"）不触发本闸（fail-open，口径见 change design.md D7）。本闸另有**与结论分布无关的第二档：代答抽验**（change design.md D16.4）——主题句或 `overall` 里的正面定性短语若在**任何一条 `comment` 原文**中都找不到逐字出处，即判"替没写字的节点断言立场"（空 `comment` 只证明未填写意见，证明不了无异议；提及未表态节点的合法写法只有"其余节点未填写意见"），处置同内容违规档：主题整条丢弃、`overall` 只丢这一句、不触发重试。两档互不替换：reject 档不管出处，代答档不管分布。**已知宽松面（如实登记，不装作有闸）**：代答档的判据是既有禁用语表的**逐字子串**比对，插字变体——如 s05 真机第四枪的"其余节点**无实质异议**"（"无异议"被"实质"断开）——不在射程内，此类句子仍会原样出稿并落缓存；服务端对"其余/其他 + 节点"这类集体指代片段只做**观测日志**（`review-summary 代答观测`），不丢句、不打标记、不旁路缓存，等一轮真实分布再定是否升闸（change design.md D16.6）。**D18（2026-10-10）补了两处、但仍不升闸**：① 观测正则原先要求"其余/其他"后 ≤4 字内出现集体名词，而 s09 把"其余"**当代词**直接用（"其余为执行层面提醒"）→ 正则零命中，观测面已放宽（代词分支须紧跟立场谓词提示词才算嫌疑，"其他付款条款按模板执行"这类正当名词短语仍不记）；② 该句的病根是**事实真空**——prompt 从不告知有几条意见写了字，三例真机代答全在填这个洞，所以"其中 N 条填写了意见"改由服务端在 ② 段陈述（见 §2.2；陈述方向同日按用户口令取正向计数，缺席条数由减法可推），范例里那句"其余为执行层面提醒"也从 prompt 删除（禁令与范例同页打架时模型跟范例走）。

### 2.4 各模块生成细则

**一、评审总结**：三段结构、连贯语句，目标 ≤200 字（服务端红线 300 字，超红线按整句裁尾而不整段弃用，见 change design.md D13/D16.1-I5）。
**三段里有两段是服务端装配的**（D16）：`review_summary.text` = ①合同要素句。②结论分布句。overall。主题1（名A、名B）；主题2（名C）……，模型只交 ③ 主题层与 overall。

- **① 合同要素**（服务端装配）：`contract_meta` 已传字段（合同类型、合同总额、综合毛利率）**原样融入**自然语句，不用「字段：值」罗列（写"该合同为硬件集成合同"，不写"合同类型：硬件集成"）；模型不参与、也不得重复写这一句；
- **② 结论分布**（服务端装配）：条数与动作原值由服务端统计后注入 Prompt，模型照抄不换算（铁律 1 的语料因此含这一句）；**存在 `comment` 为空的意见时，句尾由服务端追加"其中 N 条填写了意见"**（change design.md D18/D18.1）——真机三例代答全部落在"收尾处交代其余人怎么了"的位置，而 prompt 从不提有几条意见写了字，这个事实真空正是代答填进去的地方；事实改由服务端陈述之后，**陈述方向取正向计数**（用户 2026-10-10 口令：审批人读这句要的是"这份评审有多少实质内容"，缺席条数由"共 X 条 − N 条"确定可推，真空照样补上而服务端一个字也不替未表态节点断言立场），全员有字时整句不追加（既有口径逐字不变）。数字与"共 N 条"同经注记进入抽验语料，模型照抄属溯源成功；反过来"未填写"的条数不再逐字出现在语料里，模型自写那个数字会被数字闸按语料外数字拦下（闸只逐字比对、不做减法），合法句式"其余节点未填写意见"不带数字因此不受影响。
- **③ 各方关注点**（AI 生成，最多 4 条主题句）：每条主题 = 一句 `text`（≤40 字）+ 一组 `opinion_refs`（1–3 个 `opinions[i]` 整下标）。**主题句后面附的节点名由服务端按 `opinion_refs` 反查 `opinions[i].node_name` 派生**（去重、保序，句内已逐字点过的名不重复附）——归属因此在结构上不可能错，模型可以完全不点名。归并范围覆盖**所有写了实质内容的意见——投「通过」但写了实质内容的同样进来**（那些话里常是关键事实，如"增补金额由 50 万改为 48 万"）；`comment` 为空或只写"同意/无异议"的不进归并，`opinion_refs` 也不得指向空意见（G2）。「有条件通过」「不通过」的诉求优先成主题，只写"存在分歧"不合格。主题名只作概括词，句内诉求从 `comment` 原文**提炼**（change design.md D16.3：主题句必须是模型自己概括的一句话，逐字或近似逐字搬运原文判不合格；允许压缩改写，但不升级、不引申、不替评审人补理由），数字照抄；同一条意见的多个编号诉求合并为**同一个主题的一句概括**、不得拆成多个主题，跨意见的同类诉求才叫归并。**服务端同源合并兜底**（change design.md D17；真机 s06 第五枪把 `opinions[5][6][7]` 各拆成两条，交出 6 条主题 > 契约上限 4，而服务端此前完全不数条数）：`opinion_refs` **集合完全相同**的主题，服务端在**首次出现的位置**合并为一条——各主题句去掉结尾标点后以"，"相连、末尾补句号，**逐字保留、不删句、不改写**；合并后超过 100 字则原样不合并，超长交回 D13 的整句裁尾（见 §5.3）。合并只发生在逐主题复检与两稿取优**之后**，所以它只会省掉重复的节点名后缀，不会绕过任何闸门：G1/G2 看 refs 集合、G3 看句内逐字点名、数字抽验看 token，四道闸对合并结果的判定与对单条主题一致。合并后仍超过 4 条只落一条容量观测日志，绝不因此重试、打标记或旁路缓存。全部意见都没写字时模型不被调用，总述只有 ①②。**反罗列禁令**（s06 的失败形态）：一个主题只写一句、句内最多 2 个节点、每节点最多转述 1 条最关键诉求，禁止把一条 `comment` 的多个细项用顿号串进主题句——细项的完整展开归「各节点意见详情」，主题句重复它既超长又让审批人抓不到重点；装不下就减主题、减节点，不减成罗列。
- **overall**（AI 生成，≤40 字，可为 `null`）：一句整体态势与焦点判断，禁止出现任何节点名；它单独违规只丢这一句，不牵连主题、不打降级标记。

示例（服务端拼接后的 `review_summary.text`；①② 由服务端装配，括号里的节点名同样由服务端按 `opinion_refs` 附上）：

> *该合同为软件集成合同，合同总额 14480000 CNY，综合毛利率 5.05%。共 13 条意见：通过 10 条、有条件通过 3 条，其中 6 条填写了意见。意见集中在金额利润变更与开票口径两处。增补金额由 50 万改为 48 万、利润率由 2.24% 提升至 5.05%（财经复核）；软件产品按登记证书标准名称开票且不得分包外采（税务评审）；争议解决条款须约定我司所在地（法务评审）。*

（2026-10-08 起的口径调整：D11 把"一句话 ≤120 字 + 只做话题级引用"放宽到"≤160 字 + 点名到节点复述诉求"，因为审批人看不出具体卡在哪；D12 再改为三段式 ≤200 字**按主题归并**，因为只点「有条件通过/不通过」会漏掉投「通过」却写了实质内容的意见，且逐节点点名不如按主题聚合好读。风险项的数字与条款仍受铁律 2 约束不得展开，观点类内容不受此限。"存在不通过意见时退化为中性陈述"只禁正面评价，不禁复述否决与附条件的诉求。D13 针对 s06 实测的 406 字罗列型失控稿定下长度口径：200 字是 prompt 目标值，服务端红线 300 字，超红线**按整句从尾部裁**而不整段弃用——用户口径是"担心限制字数又被弃用，那仅有的 AI 能力就没有了"。D15 曾试图在文本空间做归属校验（点名的节点必须逐字取自写过字那条的 `node_name`），但 s05 证明节点名互成子串（`行业商务评审` ⊂ `二级行业商务评审`）时，文本空间里误判与漏判数学上不可兼得；**D16 因此把归属搬到结构层**：①② 改由服务端装配、主题只交 `opinion_refs` 指针、节点名由服务端反查派生，D15 的沉默节点名匹配与"删名"补救整体拆除（详见 §5.3）。）

**二、重点关注**：有序列表，编号呈现。

- `route_reason` 传入时，**提级原因块固定置首**（这是装配规则，非业务加工）；
- 风险项按传入数组顺序跟排；
- 每个风险块展示：`title` + `level` + `source` + `description` + `standard_clause` + `potential_impact` + 决策状态（`decision_type` / `decision_by` / `decision_note`）+「处置参考」（`measure_type` + `measure_desc`）。缺字段的对应行不渲染（"不渲染"是前端职责；JSON 层缺值字段以 `null` 回显、键不省略，与入参"缺值给空不省键"对称）。

**三、各节点意见详情**：默认折叠。每条 = 角色 · 姓名 · 动作标签（`action` 原样展示，展示色由前端自行映射）+ AI 摘要（压缩 `comment`，保留其主张与条件）。

## 3. 输入契约

四组数据。通用约定：**缺值给空不省键**（`null` / `[]`）；**所有文本原样传递**，接口只引用不加工。

### 3.1 `contract_meta` 合同要素（整组可选，可扩展）

```json
"contract_meta": {
  "contract_type": "硬件集成",
  "contract_amount": "¥126 万元",
  "gross_margin": "27.7%"
}
```

| 约定            | 说明                                                |
| ------------- | ------------------------------------------------- |
| 整组可选          | 缺省时总述退化为"该合同…"开头的事实句，仅基于已传信息                      |
| 字段全部 optional | 总述只引用**已传入**的字段，缺位不补不问                            |
| 可扩展           | 后续 CRM 客户字段（评级、信誉等）确定后**直接新增可选字段**，向后兼容，接口与页面无需改版 |
| 多口径并列         | 同类指标多口径（综合/硬件/软件毛利率）**合并写入对应字段的字符串**（如 `gross_margin`="综合 27.7% / 硬件 21% / 软件 45%"），接口不做取舍；字段扩展落地前勿另起新键传数——未定义新键只保证不被拒绝，会被忽略、不进面板与总述                   |

> ⏸ CRM 客户相关字段**暂缓接入**（CRM 侧业务规则讨论中），契约以上述扩展点预留。

### 3.2 `route_reason` 提级原因（可选）

```json
"route_reason": { "text": "合同总额超过 ¥100 万，按权限规则触发副总经理终审节点" }
```

- `text` 为合同系统侧**已生成好的人话原文**（提级审批时业务人填写 / 规则引擎产出的现成文本），接口照搬，不润色、不推断权限规则。
- 传入 `route_reason` 时 `text` 必须非空：空串属未定义格，按非法请求拒绝（422 / 10001）。此为 2026-10-03 归档前补强（OpenSpec change `review-summary-api` design D6），已入 spec 与实现。
- 缺省时重点关注无提级块。

### 3.3 `risk_register[]` 高风险项（合同系统预选）

**只传高风险项**——非高风险不进入本数组，接口零过滤。12 个字段全部"**有就照搬、没有就不传（null）**"：

| 字段                 | 来源（清单页面列） | 示例                               |
| ------------------ | --------- | -------------------------------- |
| `risk_id`          | 风险编号      | `"RSK-001"`                      |
| `title`            | 风险标题      | `"付款风险"`                         |
| `level`            | 等级徽章      | `"高"`（原样展示，不做枚举映射）               |
| `source`           | 来源        | `"财经评审"`                         |
| `description`      | 风险描述      | `"客户预付款比例 15%，低于我司标准 30%"`       |
| `standard_clause`  | 标准条款      | `"《合同签订标准》第 3.2 条：预付款比例不低于 30%"` |
| `potential_impact` | 潜在影响      | `"项目前期资金压力较大，资金占用 96 天…"`        |
| `measure_type`     | 措施类别      | `"缓解"` / `"预防"`                  |
| `measure_desc`     | 措施描述      | `"要求客户签署补充付款承诺函，并将首付款拆分为两期"`     |
| `decision_type`    | 决策类型      | `"接受风险"` / `"不接受"`（中文文本原样展示）     |
| `decision_note`    | 决策说明      | `"考虑客户战略价值，同意让步"`                |
| `decision_by`      | 决策人       | `"陈总"`（optional）                 |

> 识别部门 / 识别人 / 识别日期 / 计划完成 / 完成状态为执行跟踪字段，**不进**审批视图。

### 3.4 `opinions[]` 评审意见全集（必填，可为 `[]`）

评审环节**全部节点**的意见（并行评审，无先后顺序语义），所有审批人共享同一份：

```json
"opinions": [
  {
    "node_name": "法务评审",
    "approver_name": "陈某",
    "role": "法务",
    "action": "有条件通过",
    "comment": "付款争议解决条款约定不明确，建议补充仲裁地后方可通过。其余条款无重大障碍。",
    "submitted_at": "2026-09-25T14:32:00+08:00"
  }
]
```

| 字段              | 必填 | 说明                                                                      |
| --------------- | -- | ----------------------------------------------------------------------- |
| `node_name`     | 是  | 评审节点名                                                                   |
| `approver_name` | 是  | 评审人姓名                                                                   |
| `role`          | 是  | 角色，自由文本（有啥传啥；同一角色保持称谓稳定）                                                |
| `action`        | 是  | **原样照搬**：非空字符串，传过来是啥就是啥——不枚举、不翻译、不映射，响应原样回显（5.4 真实联调后的契约转向，change design.md D7）；结论分布统计与动作标签直接消费传入原值 |
| `comment`       | 是  | 综合评审意见**原文**，不要预先摘要；超约 2000 字截断并标注「（原文有截断）」                             |
| `submitted_at`  | 建议 | ISO 8601 带时区                                                            |

约定：**一人多角色**拆多条记录；`[]` 为合法空态（评审未完成）。

> 📌 **回退重审提醒**：若评审发生回退重审，同一评审人可能存在多轮意见。接口按传入内容原样总结、不做新旧甄别——**请合同系统侧定义传参口径**：只传当前有效轮（推荐），或全量传入并为每条附加轮次标记。

## 4. 输出 JSON Schema 与示例

### 4.1 结构

```text

├── review_summary          评审总结
```

## 5. 降级与空态

### 5.1 空态矩阵

| 场景 | 面板表现 | `degraded_sections` |
| -- | ---- | ------------------- |

| `risk_register=[]` 且无 `route_reason` | 重点关注模块显示「无重点关注事项」                     | `["key_concerns"]`                               |  
| 仅 `route_reason` 缺                   | 重点关注无提级块，仅风险项                         | `[]`（非降级）                                        |


| `contract_meta` 部分字段缺                | 总述只引用已传字段，缺位不提                        | `[]`（非降级）                                        |

| `opinions=[]`（评审未完成）                 | 总述只有服务端装配的 ①合同要素句 + ②结论分布句（无有字意见时**根本不触模型**，它也确实没题材可写）；意见详情空态文案「评审意见尚未提交」 | `["opinion_details", "review_summary.opinions"]` |  
| 某风险项缺 `measure_*`                    | 该风险块不出「处置参考」行                         | `[]`（非降级）                                        |  
| 某风险项缺 `decision_*`                   | 不显示决策状态标签                             | `[]`（非降级）                                        |

### 5.2 模型调用失败

- 走统一错误码体系：重试耗尽 `20001` / 超时 `20002` / 格式异常 `20003`。
- 建议合同系统前端：调用失败时面板整体降级为「智能总结暂不可用」或隐藏面板，**不阻塞审批操作**；页面异步加载该面板。

### 5.3 总述的内容质量降级（2026-10-08 契约调整，change design.md D10）

总述是面板最核心的区块，**SHALL NOT 因安全闸拦截而空白**。AI 稿未通过服务端校验时按下面的阶梯处置（change design.md D16 / D16.1 / D16.2）：

| 层次 | 条件 | 输出 | `degraded_sections` |
| --- | --- | --- | --- |
| 定向重试 ×1 | **结构违规**：输出形状失守 / 某主题的 `opinion_refs` 被剔到一条不剩（G1）/ 引用指向空意见（G2）/ 主题句点了自己 refs 之外的节点名（G3 未背书） | 话术只列可核验事实（哪条主题、哪条引用、哪个名没背书），其余主题与用词要求保持不变 | —— |
| 两稿取优 | 重试后 | 各跑一遍逐主题复检，取合法主题数**多**者；并列取首稿 | —— |
| 主题丢弃 | 复检后仍违规的主题 | **整条丢弃**（不删名、不改句），其余主题照常返回 | `["review_summary.incomplete"]`（覆盖不全，内容仍是 AI 稿） |
| 兜底稿 | 一条合法主题都不剩，且请求体里确有可引用素材（合同要素、意见任一） | 服务端中性稿：合同要素原文 + 意见条数分布 + 已写意见的节点名，零评价性修饰（**不代模型概括诉求**，也**不提风险项标题**——风险由「重点关注」单点承载，D16.1-I2） | `["review_summary.fallback"]`（内容在、非 AI 写） |
| 置空 | 除装配区已展示内容外无可引用素材（无合同要素、无有字意见） | `text=null` | 属输入决定的空态：`["review_summary.opinions"]`，可缓存 |

- **内容违规不扳重试**：数字抽验违规、无出处的正面定性代答（D16.4）、「不通过」场景含正面定性属内容闸，沿用既有"内容违规不消耗重试次数"口径——
  该主题直接丢弃，违规事实只在一个重试**本就发生**时搭车进话术（多一次改对的机会，零额外调用）。
- **overall 单独违规只丢这一句**（含节点名 / 语料外数字 / 正面定性）：不牵连主题、不打标记、不重试（D16.2-R7）。
- **漏纳只观测不扳闸**（D16.1-R1）：主题容量 ≤4、每主题 refs ≤3，真实面板常有十几条有字意见装不下——
  这是契约里的取舍，不是违约。服务端只记一条覆盖观测日志，绝不因此重试、打标记或旁路缓存。
- **同源合并不是闸门**（D17）：模型把同一条意见拆成多条主题时，服务端按 `opinion_refs` 集合把重复项拼成一条（位置取首次出现、句子逐字保留、连接符用"，"而不是"；"——后者是 D13 的整句边界，合并句必须保持"一句一主题"才可裁）。它发生在复检与取优**之后**，因此不参与任何弃用判定，也不会让本该丢弃的违规主题搭车存活；合并结果照常参与渲染、抽验与缓存。唯一例外是**合并预算**：拼完超过 100 字就保持原样，因为一条无句读的近 200 字长句会让裁尾切不开、把整份 AI 稿打成 `.fallback`——这条是既有 D13 裁尾用例逼出来的取舍，不是放宽任何闸。
- 兜底稿的每个数字与每条引用都出自请求体或服务端自算统计，天然通过全部铁律校验——兜底不等于放宽防幻觉。
- `.fallback` / `.incomplete` / 任一 `*.model` 同属"AI 质量降级"，此类响应 SHALL NOT 写入缓存，同一输入下次请求重新给模型机会；
  输入决定的空态（含 §5.1 各行）可安全缓存。
- 意见摘要的降级语义不变：违规只丢该条（`summary=null` + `opinion_details.model`），前端可回落展示 `comment` 原文。
- **超长 AI 稿不在此表射程**（change design.md D13 / D16.1-I5）：通过全部铁律、只是字数超红线 300 的总述，服务端**按整句从尾部裁**后照常返回 AI 文本，
  不打 `.fallback`/`.incomplete`、不旁路缓存——红线作用于**服务端拼接后的全文**（含 ①② 装配句与节点名后缀），
  主题之间以"；"相连而"；"本就是整句边界，所以裁的粒度恰好是"整条主题"，不会把中间的主题砍成半句（D17 的同源合并句内部只用"，"、不带句读，正是为了保住这条边界，合并后的主题被裁时仍是整条一起出稿或整条一起裁掉）；
  只有切不开（首句即超限、或裁完不足两句）才退回兜底稿。被砍的尾部主题在「各节点意见详情」里仍逐条原文可查，面板不丢信息。
- **`opinion_details.model` 只在模型漏交 index 时出现**（缺陷 D，change design.md D14）：`comment` 为空、
  或近空（"同意。"）而模型按 prompt 契约显式返回 `summary=null` 的，都是契约内的正确输出，SHALL NOT 计为丢弃、
  SHALL NOT 打标记、SHALL NOT 旁路缓存。真实面板多数评审人只写"同意。"，误计会让缓存基本无法命中。
- **代答的病根是事实真空，不是模型纪律**（D18，2026-10-10）：有字意见的条数改由服务端在 ② 段陈述（"其中 N 条填写了意见"——同日用户口令把陈述方向从"未填写"翻成"填写"，缺席条数由减法可推，见 D18.1），prompt 的 overall 范例里那句会被逐字照抄的"其余为执行层面提醒"一并删除；观测正则补代词分支。**本条不新增任何拦截、标记或缓存旁路**——词表外变体仍会原样出稿，是否升 `overall` 档闸等下一轮真实分布（判据：放宽后的观测片段里"替空 comment 断言立场"是否仍占绝对多数）。**第九枪真机五连发（s05–s09）的分布已回齐：带空意见的四发无一写"其余…"收尾，观测片段集合为空集，裁尾与容量观测亦零触发 → 按本条自己的判据，升闸被否（动机已被装配消掉、代答真实分布为零，代价没有收益可换）；观测档保留，因为词表与正则都仍可能滞后于模型下一次换词。第十枪把 D18.1 翻转后的口径复跑一遍，同一判据第二次给出零命中（5 个 `overall` + 10 条主题句连续两轮十发全零），本条关闭。**
- **张冠李戴在结构层消解**（缺陷 E → 缺陷 F，change design.md D16 / D16.2）：s06 实测出现过把 `合同复核` 的话转给
  一字未写的 `财经复核` 的张冠李戴——数字、引用、长度三道闸都拦不住编归属的输出。D15 曾在文本空间做"沉默节点名匹配"，
  但 s05 证明节点名互成子串（`行业商务评审` ⊂ `二级行业商务评审`），文本空间里误判与漏判数学上不可兼得。
  D16 因此把归属变成结构事实：主题句后面的节点名由服务端按 `opinion_refs` 反查派生，**模型想张冠李戴也没有通道**；
  文本层只保留负向校验 G3——句内逐字点了名（最大匹配扫描，长名优先、不留半截名），该名字就必须在这条主题自己的
  `opinion_refs` 覆盖的节点里（背书），否则算未背书 → 定向重试一次 → 仍违规**整条主题丢弃**（不删名不改句）并打
  `.incomplete`。前端建议：见到 `.incomplete` 时照常展示 AI 文本，可在标题处加"要点覆盖不全"的中性角标；
  见到 `.fallback` 时才需要说明"智能总结暂不可用，以下为系统摘要"。

## 6. 缓存与性能

- **实时生成 + 输入 hash 缓存**：对规范化后的请求体计算内容哈希作为缓存键；`opinions` / `risk_register` 任何新增变更自动失效，合同系统无需通知。
- **耗时与 token（2026-10-10 真 vLLM 实测，不再只是预估）**：缓存命中 **0.005–0.006s**；新生成 **2.86–12.58s**，随生成文本长度而非意见条数浮动（14 条意见的 s08 4.9s，13 条的 s05 12.6s）。一次面板打开 = 2 次模型调用（总述 + 摘要批量），实测 `llm_tokens_total` 差 = **prompt 6254 / completion 623**，折算约 3.1k in / 311 out per 调用——**输入占九成，成本主要由喂进 prompt 的意见原文长度决定**，输出侧基本恒定；命中路径零模型调用、零 token 增量。据此 120s 客户端预算余量约十倍，仍建议页面异步加载面板并显示加载态。
- **服务端超时**：建议 120s（生成规模小于现行评审接口的逐项检查，余量充足）。口径注：120s 指网关/客户端侧预算；服务端单次模型调用超时现受既有 `config llm.timeout=30s` 控制（现有键，红线不改），超 30s 即返回 20002。
- **模型调用**：与现行能力共用 vLLM 实例与 `get_chat_model()` 单例；**关闭思考**走 `model.bind(extra_body={"chat_template_kwargs": {"enable_thinking": False}})`；SDK 层 `max_retries=0`，业务层仅解析失败重试 1 次。
- **一次未命中缓存的请求发几次模型调用**：常规 **2 次**（总述主题层 1 次 + 全部有字意见的摘要批量 1 次）；
  仅当总述主题被判定**结构违规**（形状失守 / 引用剔空 / 引用指空意见 / 点名未背书，见 §5.3）时追加**至多 1 次**定向重试，上限 3 次。
  内容违规（数字、正面定性）不扳重试。全部意见都没写字时总述不触模型，只剩摘要批量那 1 次（该场景下为 0 次）。
  重试不改变对外契约与响应结构。
