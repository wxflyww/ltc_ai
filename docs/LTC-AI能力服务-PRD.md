## 1. 背景与目标

### 1.1 背景
LTC（Lead to Cash）系统当前流程中存在大量依赖人工处理的环节，如合同文档识别与结构化、多语言翻译、审批意见摘要等，缺乏统一的AI能力支撑层。随着PISA BU私有化大模型基础设施（Qwen3.6-35B-A3B / DeepSeek V4-Flash，vLLM部署）逐步落地，具备了为业务系统提供标准化AI能力服务的条件。

### 1.2 目标
构建一个**全新的、独立部署的AI能力/Agent服务**，作为LTC系统的AI中台能力层，对外提供统一的API接口，内部通过LangChain编排调用私有化部署的大模型，覆盖OCR识别、合同结构化、多语言翻译、审批摘要等场景，并支持后续Agent能力的持续扩展。

### 1.3 非目标
- 本期不涉及LTC系统前端界面改造，仅提供后端AI能力API。
- 不涉及大模型本身的训练/微调，仅作为模型服务的调用方。
- 不涉及RPA自动化执行逻辑（如有依赖，通过接口对接现有RPA平台）。

## 2. 用户与场景

| 角色 | 说明 |
|---|---|
| LTC业务系统（Java/Spring Boot） | 主要调用方，通过HTTP API调用AI能力 |
| 业务运营/审批人员 | 间接使用者，在LTC流程中感知AI辅助结果（如自动摘要、翻译） |
| AI平台/运维团队 | 服务的部署、监控、多环境配置维护方 |

### 核心使用场景
1. **多语言翻译**：合同或审批内容的中外文互译。
2. **Agent编排能力（可扩展）**：基于LangChain构建的多步骤Agent，串联OCR→结构化→校验→摘要等流程，支持未来新增AI能力场景快速接入。

## 3. 总体方案

### 3.1 技术选型

| 类别 | 选型 | 说明 |
|---|---|---|
| 语言/运行时 | Python 3.11 | 统一基础镜像版本 |
| Web框架 | FastAPI | 待确认，异步、高性能，便于对接OCR/LLM等IO密集型调用（可根据团队现有技术栈调整） |
| AI编排框架 | LangChain | 负责Prompt编排、Chain/Agent构建、模型调用抽象 |
| 大模型 | 私有化部署 Qwen3.6-35B-A3B / DeepSeek V4-Flash（vLLM Serving） | 通过LangChain自定义LLM/ChatModel适配 vLLM OpenAI兼容接口 |
| 容器化 | Docker | 支持多环境镜像构建与部署，宿主机/Docker Compose方式运行 |
| 配置管理 | 多环境YAML/环境变量（.env + config-{env}.yaml） | 支持 dev/test/prod 隔离 |

### 3.2 系统架构（逻辑视图）

```
LTC系统 (Java/Spring Boot)
        │  HTTP/REST (JSON)
        ▼
┌─────────────────────────────┐
│   AI能力服务 (Python 3.11)    │
│  ┌─────────────────────────┐ │
│  │  API层 (FastAPI)         │ │
│  ├─────────────────────────┤ │
│  │  能力编排层 (LangChain)   │ │
│  │  - 翻译 Chain             │ │
│  │  - Agent 编排（可扩展）   │ │
│  ├─────────────────────────┤ │
│  │  模型适配层                │ │
│  │  (LangChain LLM Wrapper) │ │
│  └───────────┬─────────────┘ │
└──────────────┼───────────────┘
               ▼
  私有化大模型服务 (vLLM, OpenAI兼容接口)
  Qwen3.6-35B-A3B / DeepSeek V4-Flash
```

## 4. 功能需求

### 4.1 API能力清单（首期）

| 能力 | 接口（示例） | 说明 |
|---|---|---|
| 健康检查 | `GET /health` | 存活/就绪探针 |
| 文本翻译 | `POST /api/v1/translate` | 输入文本+目标语言，输出译文 |

> 说明：以上接口的详细字段（请求/响应Schema）需在详设阶段与LTC系统对接方进一步确认。

### 4.2 通用能力要求
- 统一的请求/响应格式（含 `traceId`` 风格的关联ID，便于跨系统日志追踪）。
- 统一错误码与异常处理机制。
- 支持Prompt模板集中管理，便于迭代与A/B。
- 调用大模型失败时具备重试（指数退避）与降级策略。

## 5. 非功能需求

### 5.1 多环境支持
- 环境划分：`dev`（开发）/ `test`（测试）/ `prod`（生产）。
- 每个环境独立配置文件，包含：
  - 大模型服务地址（vLLM endpoint）、模型名称
  - 服务端口、日志级别
  - 密钥/凭证通过环境变量或密钥管理服务注入，**不进入代码库**
- 配置加载优先级：环境变量 > 环境专属配置文件 > 默认配置文件。

### 5.2 容器化部署
- 提供标准 `Dockerfile`（基于 `python:3.11-slim`），多阶段构建，减小镜像体积。
- 提供 `docker-compose.yml`，分别维护 `docker-compose.test.yml` / `docker-compose.prod.yml`（或通过 `.env` 文件区分环境变量），用于测试/生产环境启动。
- 镜像通过CI流水线构建并打标签（区分环境/版本号），推送至私有镜像仓库，部署时在目标宿主机 `docker pull` + `docker compose up -d`。
- 支持通过挂载环境专属配置文件或环境变量切换运行环境，无需重新构建镜像。
- 容器resource限制（CPU/内存）通过 `docker-compose` 的 `deploy.resources` 或 `docker run --cpus/--memory` 配置。


### 5.3 可观测性
- 结构化日志（JSON格式），包含 traceId、接口耗时、模型调用耗时。
- 关键指标暴露（Prometheus格式）：QPS、错误率、模型调用延迟、Token消耗。
- 接入现有监控告警体系（如有）。

### 5.4 安全
- 服务间调用鉴权（如API Key）。
